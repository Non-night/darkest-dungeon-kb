## 目标顺序

知识库写入按以下优先级处理：准确性与可追溯性 > 不引入冲突或索引漂移 > 最小读取和最小修改 > token 与执行时间。

## 身份术语与授权归属

- **当前用户**：正在与当前 Agent 对话的人。当前任务的授权、设计、目标、约束与纠正只取自当前用户的明确表达；历史记录不能替代当前授权。
- **知识库编写者**：维护本库并在入库时提供历史实测、解释、设计确认或修正的人。文档中没有明确标注当前会话的“用户提供”“用户明确补充”“用户实测”等历史措辞，一律按知识库编写者提供的证据或确认读取，不能误作当前用户的指令、授权或需求。
- **外部来源作者**：工作簿、文档、Mod、原版或官方 DLC 等资料的作者；材料只按记录的证据等级使用，不等同于知识库编写者或当前用户。
- **游戏玩家**：游戏内操作者，不等同于当前用户。

Agent 在回答、证据账本、路由和机制正文中遇到身份有关的说法，必须写“当前用户”或“知识库编写者”，不得用无修饰的“用户”把实时指令和历史证据混为一谈。若历史措辞与当前用户的新要求冲突，当前任务先遵从当前用户的要求；涉及已有机制事实时，再把冲突按证据等级明确记录。

## 写入前：证据账本

先把请求归类为新增、修正、合并、废弃或索引维护，并为每条拟写结论建立短账本：结论、适用条件、时序与生命周期、`source_refs`、来源等级、状态（已确认/未确认/未知/冲突）以及受影响的字段、路由、锚点和依赖。

没有来源定位的内容只能写成检索线索或待验证项，不能写成确定引擎规则。单个 Mod 案例只能证明该 Mod 存在该写法，不能单独提升为通用语义。

## 写入前：最小检索与冲突检查

先用 `kb_query.py` 查询拟新增结论的关键词、字段名、代码信号和同义词。只读取命中的精确词条、相关机制卡及一跳依赖，检查：已有结论是否覆盖、新结论是否冲突、冲突是否来自不同条件/对象/证据等级，以及旧结论是否需要修正或降级。

若是纠错，优先修改唯一生成源，不用相反小卡掩盖旧结论。证据确实冲突时，保留双方条件和来源，并明确当前资料不能统一确认。

## 写入：源头和最小闭包

- 机制正文写入 `Sources/mechanics/<原专题名>.md`；导航写入 `Sources/navigation/`，运行协议写入 `Sources/protocol/`，`Sources/agent_index_source.json` 只作为生成的兼容视图；Effect、Buff、Info 和 Reference 遵循各自生成器的源数据入口。
- 只有新机制会改变检索入口、跨字段推理或高风险边界时，才新增路由、锚点和关系边；每个新路由必须有真实 `exact_sources`，每个新锚点必须有 `source_refs`、`evidence_level`、`requires` 和冲突描述。
- 新小节必须有实质正文，至少包含结论、条件/范围和证据或未知边界；标题-only 小节不会生成有效机制卡。
- 不手改 `RAG/*.jsonl`、`manifest.json`、`Mechanics/index.md` 或生成的 Agent 协议。

## 写入后：四层验证

1. 结构：运行 `python tools/build_knowledge_base.py`，解析生成 JSON/JSONL，确认计数和新文件进入 manifest。
2. 编码：检查新建或改写的 JSON、JSONL、Darkest 文件为 UTF-8 无 BOM。
3. 召回：用新增结论的真实关键词查询，确认命中新路由、锚点和机制卡，且结果没有超出预算。
4. 回归：再查询至少一个相邻旧结论，确认旧路由仍命中、原有精确字段未被泛化召回覆盖；查看 `git diff` 确认修改范围。

构建成功只说明生成器运行完毕，不等于语义正确；任一层失败都不能视为写入完成。

## Token 控制

先用短证据账本和精确查询定位，再读取正文。默认每个新结论最多读取一张精确卡、两张相关机制卡和一跳依赖。验证阶段只保留查询结果中的 ID、结论、来源和冲突；只有发生冲突、跨字段影响或高风险时序变化，才扩大读取范围。

## 现行维护导航

详细维护入口、自动摘要与定制摘要的分工、撤回和关联维护见 [维护地图](../Reference/agent_guides/maintenance.md)。在当前用户已明确授权范围内推进维护，不重复请求已取得的授权。
