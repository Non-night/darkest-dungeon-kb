## 新版清除与前置条件（2026-11-05采纳）

- `.cure_mortality 1`：清除目标的死门恢复与心衰恢复减益，不是复活、清除死亡之门本身或重置死抗。
- `.cure_quirk_tags "tag_id"`：移除指定标签的所有正面怪癖、负面怪癖及疾病。参数是标签；锁定与特殊疾病的例外未说明。
- `.requires_status "status_id"`：检查目标指定keyStatus，如bleeding。`.requires_bsrc "bsrc_id"`检查目标是否具有指定Buff来源，如bsrc_crit；后者不是按Buff ID检测。
- 两个requires字段与swap组合的检查对象等未明细，不从requires_burning_target或旧keyStatus简写直接外推。
- 强制过抗指定类型替代原判定的实测结论见[概率与抗性](03-chance与抗性.md)。来源：新版文档B027–B036及Sources/modding_update_20261105_effects.json；当前用户2026-11-05采纳，无新增实机测试。

## 新版战后战利品与最大生命比例伤害（2026-11-05采纳）

- `.gain_loot "example_loot_table_id"`：战斗中触发时从指定战利品表掷取战后战利品；战斗外不触发。此处引用 loot table ID，不是物品 ID；不能当作即时入包功能。撤退／战败、重复调用、容量与战利品加成的边界未由文档说明。
- `.health_damage_percent 0.1`：与 `.health_damage` 相似，以目标最大生命为基准造成比例伤害；0.1表示目标最大生命的10%，不是当前生命或施术者生命。护甲、硬减、护体格挡、取整、死亡反馈及击杀归属未说明，不直接继承 `.health_damage` 的全部专项结论。
- 证据：新版《Darkest Dungeon Modding Update | Feature List》B019–B022，原文与译文见 Sources/modding_update_20261105_effects.json。当前用户2026-11-05明确要求采纳，且已指定新版优先；无本轮实机测试。字段语法是文档证据，不伪造完整技能或原版配置案例。

## `.chance`
- 通用数值范围、Buff 异侧抗性、条件概率门，以及 `.keyStatus`、`.skill_instant`、`.monsterType` 的特殊概率已经整理到 `03-chance与抗性.md`。
- 尚未确认的主要边界是攻击暴击对 DOT 的额外变化，以及该变化是否受 `.crit_doesnt_apply_to_roll` 控制。

## `.capture` 与 `.capture_remove_from_party`
- 这两个关键字已确认存在原版实例，但完整行为边界尚未整理完毕。
- 当前不要仅凭字段名推断捕获对象的生命周期、目标限制、失败结果或与队伍移除之间的全部关系。

## `.guard`、`.clearguarded` 与 `.clearguarding`
- 三个字段在参数为 `1` 时无视 `.chance`；命中/未命中语义有效时可用双 false 抑制，但在 actout、道具 Effect、spawn Effect 等场合不能靠双 false 抑制。
- `.clearguarding 1` 对跨侧守护的守护者无效；其“守护源追溯失败”原因目前仅为推测。

## `.clearDotStress`
- 只有 `.clearDotStress 1` 才清除持续压力，写 `0` 等同于未写。

## `.clearvirtue`
- 只有 `.clearvirtue 1` 才清除美德，写 `0` 等同于未写。
- 清除美德后压力值保持不变；压力高于 `100` 时会暂时出现既无美德也无折磨的状态。
- 已有测试记录观察到下次受压会将压力复位为 `100` 并重新判定，但具体判定压力处理尚未完全确认。
- `.clearvirtue` 是否等同于驱散美德源，尚未确认。
- 清除后进行不足以使压力低于 `100` 的减压时，是否同样复位并重新判定，尚未确认。

## `.clear_rank_target`
- 参数已明确为站位表达式；当前资料记载本字段接受 `@` 与 `~`，不接受 `?`。
- 在 `*.info.darkest` 的技能定义中，`12`、`1234` 与 `@12` 表示可选范围而不是 AOE；该语义是否完整适用于 `.clear_rank_target` 尚未确认。

## `.combat_stat_buff`
- `.combat_stat_buff` 属于 Effect 简写 Buff，可与战斗属性改变量关键字共同使用。
- 各战斗属性字段、`.buff_amount`、`.buff_type`、Buff 源及其组合的完整规则尚未全部确认；不要把已收录的组合案例扩展为所有字段都能独立或等价工作的结论。

## `.actor_dot`
- 不同 ActorDot 之间的触发顺序目前只能暂按“后施加者先触发”处理，该顺序尚未完全确认。

## `.affliction_blockable_chance`
- 有效阻挡值必须大于 `0`。
- 写入小于等于 `0` 时是否一定不会造成崩溃，目前只是推测；已知这种值不会让折磨阻挡该 Effect。

## `.virtue_blockable_chance`
- 原版美德的 `block_effect.chance` 为 `1`，因此原版配置下可以正常配合。
- Trait 侧 `block_effect.chance` 的精确要求尚未确认：目前不确定只需大于 `0`，还是必须写为 `1`；创作时使用 `1`。

## `.apply_once`
- “单次技能内同名 Effect 最多实际生效一次”是当前推定规则，内部去重范围尚未完全确认。

- 饰品 Trigger 等非技能流程也会受到 `.apply_once` 的同名去重影响，但其调用流程边界尚未完整确认。

- 不确定字符串两侧的引号是否计入 `64` 的长度限制。

## `.daze`
- `.daze <duration>` 施加迷乱（官方译名“晕眩”，亦称“小晕”），数值表示持续时间，不是数字布尔；`.daze 1` 的 1 可提高，`.daze 0` 不构成有效 daze 技能标志。
- 新版施加迷乱时不重排行动队列；在目标个人回合开始时触发，将该次行动移至本整轮末尾，不等于把目标所有行动立即一起移后。
- 知识库编写者于2026-11-05确认：处于 daze（迷乱）状态的单位触发反击时，会提前触发并结算原本在个人回合开始时处理的行动延后效果；不能再把正常个人回合开始视为唯一触发入口。
- 本次确认只补充反击会提前触发并结算 daze；反击是否取消、是否消耗正常行动、状态清除方式及多行动点的具体处理均未在本次说明，不据此扩展；也不推广到其他回合外调用。
- 来源：知识库编写者于2026-11-05在当前会话补充并确认入库：daze 的效果为回合开始时移至行动轴末尾，触发反击会提前触发并结算该效果。本条为知识库编写者确认，不冒称新增实机测试或新版文档原文。
- 施加率使用施术者的眩晕施加率，并检查目标眩晕抗性；`.undaze 1` 可以清除迷乱。
- `dazed` 可作为 `keyStatus`，包括 Buff 的 `actorStatus` Rule。
- 眩晕自动清除迷乱；已经眩晕的目标免疫迷乱。再次迷乱已迷乱的目标不会自动升级为眩晕，需由 Mod 自行实现。
- 新版不再沿用“单机部分失效”及额外Daze动画依赖的旧限制；但.stun／.daze组合卡死未完全修复，须继续遵守后续2026-11-07对照测试的具体时序边界。不能把旧动画要求撤销理解成全部组合安全。
- 当前用户于2026-11-05根据新版状态互斥与清除说明判断：旧版那种“Daze 与眩晕只要同技能／同组合出现就必然触发旧崩溃”的普遍规则不再沿用，也不再要求额外准备 Daze 动画素材；但这不等于新版所有 Daze／眩晕时序组合都安全，也不代表两状态可同时保留。
- 当前用户于2026-11-07转述外部来源作者无夜的攻击技能实测：两个目标 Effect 都为 `queue true` 时，先施加眩晕、后施加迷乱可以正常结束回合；先施加迷乱、后施加眩晕会使回合卡死。将迷乱改为 `queue false`、眩晕保持 `queue true` 时，本次测试正常。上述三项均为技能直接引用 Effect、目标为攻击目标的结果。
- 当前用户补充：测试 Mod 中，AWR 自附魔（Rule 为 `always`）引出的 `queue true` 眩晕，加上技能 `queue false` 迷乱，在目标原本没有迷乱时测试正常；但当前用户曾观察到目标已有 `daze` 时，先由技能 `queue false` 再由 AWR 自附魔的 `queue true` 施加眩晕后回合卡死，正在尝试复现。因此“已有 daze 状态”是否为必要条件、AWR 自附魔是否改变该边界，以及该现象是否稳定，均暂未确认。
- 旧有技能属性标签用途保留：即使正值 `.daze` 因概率、命中条件等未实际施加，仍可配合 `disable_combat_skill_attribute/daze` 检查技能属性；`.daze 0` 不构成该标签。
- 来源：新版《Darkest Dungeon Modding Update | Feature List》B002–B009（2026-11-05读取，当前用户明确指定新版优先）；原文快照：Review/2026-11-05-Modding-Update/source.md。文档未给出精确适用构建号；本次仅采纳 Daze 更新，不自动采纳同文档其他功能。

## `.damage_source_data`、`.damage_source_type` 与 `.damage_type`
- `.damage_source_data` 只接受一个字符串参数，可带引号或不带引号；当 `.damage_source_type monster` 时，填写怪物小类 ID，不填写大类 ID。
- 怪物小类 ID 格式为 `<大类ID>_<单字符差分>`；下划线后必须恰好一个字符，多字符后缀不合法。A-Z 大写字母与 0-9 数字已确认可用；`@`、`#` 疑似可用但待确认，其他字符形式也待确认。
- Size-0 首先属于怪物，因此此处怪物来源规则也包含 Size-0，除非具体机制另有明确例外。
- `.damage_source_type` 与 `.damage_type` 均可带引号或不带引号，但合法值仅限各自候选表；非法参数行为尚未确认。

## 真伤与护体格挡的 `damage_type` 例外

当前用户确认（2026-10-07）：真伤的数值会在最终结算前先进行四舍五入；因此涉及“最终值大于等于 `1`”的判断时，应以四舍五入后的值为准。四舍五入的具体底层边界（例如负数、恰好处于中间值时的实现细节）当前未专项确认。

正常情况下，四舍五入后的最终值大于等于 `1` 的真伤会被目标的护体格挡挡住，并消耗一层护体格挡。

如果同一真伤 Effect 使用 `.damage_type` 将伤害类型声明为以下任一值：

```text
bleed
poisoned
burn
captor
```

则该真伤会无视目标的护体格挡，且不会消耗护体格挡；这一例外与真伤数值大小无关。这里的“护体格挡”严格指 `.health_damage_blocks`，不等同于其他减伤、守护或抗性机制。

本条只记录当前用户确认的“真伤—护体格挡”交互，不外推到其他 `.damage_type` 值、最终结算值小于 `1` 的真伤、普通 DOT 或其他挡伤机制。


## 声明类型的真伤、尸体生成与死亡变身

当前用户于 2026-10-08 补充：声明了特定 `.damage_type` 的真伤，具有该类型对应的伤害性质。

在原版环境下，具有尸体阶段的常规怪物都是通过死亡变身生成尸体；其 `death_class:` 通常定义了对应 DOT 致死时是否允许执行：

- `.is_valid_on_bleed_dot`：流血致死是否允许死亡变身；默认值为 `true`；
- `.is_valid_on_blight_dot`：腐蚀致死是否允许死亡变身；默认值为 `true`；
- `.is_valid_on_burn_dot`：燃烧致死是否允许死亡变身；默认值为 `false`。

因此，把真伤声明为 `.damage_type bleed` 后，若常规怪物因该真伤死亡，会被视为因流血而死，死亡变身不会触发，因而不会产生尸体。这里的说明限定在原版环境下“有尸体的常规怪物均通过死亡变身生成尸体”的前提；自定义死亡流程和特殊实体不能直接套用。

上述 `damage_type` 类型性质也意味着，不能只把声明类型当作显示标签；判断伤害与死亡变身交互时，应按其对应伤害性质检查。

当前用户于 2026-10-08 进一步确认：因真伤而死的怪物不会触发英雄身上的击杀 Trigger，因此也不参与“因 DOT 而死的怪物最终归属于最后一个成功对其施加 DOT 的英雄，并触发该英雄击杀 Trigger”的判定。这里所说的 DOT 归属规则只特指流血和腐蚀；燃烧致死的怪物同样不会触发英雄击杀 Trigger。

## `.requires_kill_target` 在英雄攻击技能中的已确认边界

当前用户于 2026-10-08 补充：如果带有 `.requires_kill_target true` 的 Effect 被英雄攻击技能引用，只要该 Effect 发生前技能目标已经死亡，该 Effect 就会生效；目标可以是因普通直伤死亡，也可以是因真伤死亡。这里当前确认的是英雄攻击技能调用场景，并不要求该 Effect 本身就是致死 Effect。

被怪物使用、被友方技能使用时是否同样成立尚未测试，暂按未知处理；非技能位置调用时的判定逻辑也尚未明确。当前记录统一采用字段名 `.requires_kill_target`。

## 真伤击杀容器的类型规避：仅为推测

由“声明了对应类型的真伤具有其类型性质”推测：如果把真伤声明为 `attack`，或声明为 `bleed`、`poisoned`、`burn` 三种 DOT 类型之一，可能可以避免真伤击杀容器导致的容器 Bug。该方案目前只是推测，不是已确认的安全方案；`captor` 真伤不能据此列入规避类型。

### 非 Size-0 怪物的保守设计建议

当前用户于 2026-10-10 补充设计建议：由于上述类型规避容器 Bug 的效果尚未实机确认，针对**非 Size-0 怪物**造成的真伤，在没有特殊设计要求时，通常建议声明：

```darkest
.damage_type attack
```

如果设计要求真伤无视护体格挡，则建议改用已知的三种 DOT 类型之一：

```darkest
.damage_type bleed
.damage_type poisoned
.damage_type burn
```

这是一条基于当前推测的创作建议，不是“写成这些类型就必定修复容器 Bug”的引擎确认。该建议不适用于 Size-0；Size-0 的真伤应按其生命反馈、死亡门、Trigger 和后续链条的具体设计单独判断。使用 DOT 类型还会引入对应的伤害性质，例如死亡变身条件、击杀 Trigger 排除和护体格挡无视等边界，不能只把它当作容器 Bug 的标签绕过字段。

## `.cure` 与 `.cure_*`
- `.cure 1` 在一定意义上可等同于同时写 `.cure_bleed 1` 与 `.cure_poison 1`。
- `.cure_bleed`、`.cure_poison`、`.cure_disease` 只有参数为 `1` 时有效；单独出现并写为 `0` 时一定无效。
- `.cure_bleed`、`.cure_poison`、`.cure_burn` 的治愈判定不受任何目标抗性影响。
- `cure_bleed_chance`、`cure_poison_chance`、`cure_burn_chance` 是施术者侧 Buff：持有者释放对应治愈 Effect 时，`amount` 与 Effect 自身的 `.chance` 直接加算；`amount: 1` 对应 100 个百分点。它们不是“持有者受到治愈”的概率修正，也不改变 DOT 本身的施加抗性。
- 当同一逻辑 Effect 中同时出现 `.cure_disease 1` 与 `.cure 1` 时，必须先写 `.cure_disease 1`，再写 `.cure 1`。
- `.cure_disease 1` 每次对一个目标执行时，从目标现有疾病中随机治愈一种，具体抽选权重未知。疾病定义中的扎营移除、城镇活动治疗和顶替限制均拦不住该 Effect，所以血病（猩红诅咒）也可被抽中并治愈。证据见迂回表第123条 P1882–P1883/X2415–X2416，以及知识库编写者于 2026-11-24 补充的随机选择和疾病定义限制。两条其他治疗路径见[扎营技能 `remove_disease`](49-扎营技能文件、通用专属分类与图标.md#治愈疾病-remove_disease)与[疗养院医疗室](46-怪癖描述显示与奇物手贱提示.md#疗养院医疗室一次治愈全部疾病的配置)。
- VS 插件的 Effect 语法诊断还明确检查同一行 `.cure` 与 `.cure_burn`：两者同时出现时，后写的关键字生效，较早的关键字被标为不生效。该插件规则只确认泛用 `.cure` 与 `.cure_burn` 的组合；不能据此推断 `.cure_bleed`、`.cure_poison` 与 `.cure_burn` 也互斥。来源：`For_the_Darkest_Dungeon/Error/EffectErrorTagger.cs` 的同名关键字诊断分支（本机 VS 插件源码，2026-11-04核对）。
- 专用治愈字段有一项原表例外：同一 Effect 行内 `.cure_bleed 1`／`.cure_poison 1` 与 `.cure_disease 1` 同时出现时，原表观察为不受上述泛用 `.cure 1` 的顺序限制，两个对应治愈均可生效。此观察只覆盖这两个专用字段与疾病治愈同行的组合；不扩展到 `.cure_burn`，也不代表专用字段与燃烧治愈的相互兼容性已实测。原表建议优先用专用字段替代泛用 `.cure 1`。证据：迂回表第115条 P1818–P1819/X2320–X2321；当前用户于2026-11-04确认按此边界补入，本轮未新增游戏测试。
- 尚未确认上述 `.cure_disease` 顺序要求是否同样适用于同名分行、同一 Header 内换行，或其他被视为同一逻辑 Effect 的写法。
- 尚未确认 `.cure` 或 `.cure_disease` 在组合中写为 `0` 时是否会产生区别；创作时不要依赖这种写法。

## `.guaranteed_town_event`
- 参数为字符布尔；`true` 的已知语义是将一个随机城镇事件加入队列。
- Fire’s Edge 表格对任务中的行为保留疑问；当前不要据此推断指定事件 ID、立即发生时机或全部任务内调用边界。

## `.dotBurn` 与燃烧

知识库编写者补充（2026-09-20）：燃烧没有对应的目标燃烧抗性。Effect 写 `.dotBurn` 时，不能为燃烧凭空添加一个“燃烧抗性”字段或抗性计算。

- 当燃烧 Effect 的基础 `.chance` 为 100% 或更高时，如果不写 `.dot_irresistible true`，技能/Effect 自动描述可能显示“燃烧[x]（100%基础概率）”。
- 写 `.dot_irresistible true` 后，该“100%基础概率”描述不会显示；对燃烧而言，这通常是清理自动描述，而不是为了绕过一个实际存在的燃烧抗性。
- 因此，概率大于等于 100% 的燃烧通常会写 `.dot_irresistible true`。这条建议针对描述和常规写法，不把 `dot_irresistible` 的一般 DOT 语义擅自扩展到其他未确认的 DOT 类型。
- 燃烧在持有者行动结束后结算，默认把燃烧层数减少 50%，剩余层数向下取整；带有燃烧的单位死亡时触发野火蔓延，随机把一半层数传给左侧或右侧目标，向下取整。死亡蔓延是否受燃烧衰减速率 Buff 影响尚未确认。

Effect 型燃烧的合并与强制 `duration: 10000`、Buff 型燃烧的不合并与低于 1 层行为，见[燃烧生命周期](17-Buff持续时间类型与实际清除.md#effect-型燃烧的持续时间与两类燃烧的结算)。

## `.cure_burn`
- 原表将参数标为整数，官方实例使用 `.cure_burn 1` 治愈燃烧。
- 治愈燃烧不判定任何抗性；施术者侧 `cure_burn_chance` 与 Effect 的 `.chance` 直接加算。这个“治愈不判定抗性”与上方“燃烧施加没有对应抗性”是两个独立结论。
- 参数 `0` 是否与未写完全等效尚未确认；创作时使用已确认的 `1`，不要依赖 `0` 的边界行为。

## `.requires_kill_target`
- `.requires_kill_target true` 使 Effect 仅在施术者击杀目标时有效。
- 击杀普通尸体不满足条件。
- 大型尸体以及其他种族/类型为 corpse 的非普通尸体怪物是否满足条件尚未确认。

## `.can_apply_on_corpse`
- 参数为字符布尔；英文原表未收录该字段，官方 Fire’s Edge DLC 存在 `.can_apply_on_corpse true` 写法。
- 当前只推测 `true` 允许 Effect 对尸体生效；官方实例只能确认字段存在，不能单独确认其完整目标判定边界。

## 瞬时效果组合的未确认边界
- 同一文件、同一来源且处于相同大时序的连续 Effect 可按书写顺序构成严格窗口；跨文件书写时能否保持相同顺序尚未确认。
- `clear_buffs_on_rule_active` 已通过 `16385` 项列表测试，但绝对数量上限尚未确认。
- 某些 Buff 无论使用何种源仍会显示；目前没有完整的此类 Buff 清单。
- 正负相抵会增加常驻 Buff 数量，但“累计多少 Buff 会导致不稳定或崩溃”没有统一阈值。

## 本轮仍未确认的组合边界
- 攻击暴击时，DOT 除 `.chance +20%` 外的额外变化尚未明确，也不确定该部分是否受 `.crit_doesnt_apply_to_roll` 控制。
- 友方技能双 false 当前观察为不触发，但该边界仍按避免使用处理。
- size-0 的 Spawn Effect 调用时序已有确认，见 [Spawn 执行链](28-spawn、生命反馈与size0执行链.md)。该结论限定于时序。
- `.can_apply_on_death true` 是否能让 `queue true` 真伤造成的击杀延续到尸体尚未确认；当前不要依赖。
- 真吸血的 AOE 治疗量是否按所有目标最终直伤合并计算尚未确认。
- 英雄升级文件名前缀是否允许不等于英雄 ID 尚未确认；创作时使用 `<hero_id>.upgrades.json`。

## 使用原则
- 这些条目是“已知部分 + 未知边界”，不是要求重新测试的任务清单。
- 生成代码时应避开依赖未确认边界的写法；若必须使用，应在推理中明确标记对应的不确定点。
- “同一条 Effect”应按逻辑 Effect 判断：同一 Header 内换行，以及不同 Header 的同名 `.name` 分行，均可能属于同一逻辑 Effect；跨 Mod 的同名 Effect 文件仍叠加。但各字段能否利用该机制突破限制，仍需查看对应词条。
