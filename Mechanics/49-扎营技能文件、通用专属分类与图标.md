扎营效果新增type: effect，sub_type为Effect ID；每效果has_description:false可隐藏提示。避免用扎营Effect杀英雄、移动英雄、召唤敌人、捕获或心控英雄。击杀警告不限于.kill；真伤也可能杀死处于死亡之门的英雄，不能因未使用.kill就视为安全。原chance.code规则仍须检查。

## 文件目录与命名

扎营技能定义位于：

```text
raid\camping\*.camping_skills.json
```

原版主文件使用：

```text
raid\camping\default.camping_skills.json
```

职业 Mod 通常建立：

```text
raid\camping\<hero_id>.camping_skills.json
```







可以确认文件名的识别格式是 `*.camping_skills.json`。星号前缀是否完全允许任意自定义、同前缀覆盖与不同前缀差分的详细规则尚未确认；创建新职业时，最安全的做法是使用对应英雄 ID 作为前缀。

文件的基础外层结构为：

```json
{
  "configuration": {
    "class_specific_number_of_classes_threshold": 4
  },
  "skills": []
}
```

## 英雄生成时的初始扎营技能数量与零值红字

知识库编写者确认（2026-09-20）：英雄 Info 的 `generation:` 中，`.number_of_class_specific_camping_skills` 控制初始随机解锁的专属扎营技能数量，`.number_of_shared_camping_skills` 控制初始随机解锁的通用扎营技能数量。它们不是本页 `class_specific_number_of_classes_threshold` 字段。

这两个数量分别写为 `0` 时，过周会出现对应的红字报错，但**不会阻止英雄正常刷新**。知识库编写者提供的 app.log 原文为：

```text
[2026-09-20 14:53:54] [ERROR] [General] HeroGeneration: Number of class specific camping skills is 0
[2026-09-20 14:53:54] [ERROR] [General] HeroGeneration: Number of shared camping skills is 0
```

游戏内显示从 `HeroGeneration:` 开始的部分，不带上述时间戳与日志前缀。两行分别对应两个字段，不能理解为只要某一项为 0 就必定同时报两行。

### 通用数量不等于额外提供技能

即使 `.number_of_shared_camping_skills` 大于 0，只要该英雄定义中没有通用扎营技能，就不会错误地出现通用技能。数量配置不能凭空创建或追加不属于该英雄技能池的通用技能。

知识库编写者以苦修为例：只有专属扎营技能，仍可配置通用数量为正。库内保留的官方代码实例 `DarkestDungeon\dlc\580100_crimson_court\features\flagellant\heroes\flagellant\flagellant.info.darkest:63` 确有 `.number_of_class_specific_camping_skills 2 .number_of_shared_camping_skills 1`，参见 [generation 字段与实例](../Info/headers/Info.generation.md)。代码实例证明配置写法；刷新表现依据知识库编写者的确认。

因此，只有专属扎营技能的英雄，不必为了“没有通用技能”而将通用数量设为 0；保留正数并让通用技能池为空可避免上述零值红字，同时不会凭空获得通用技能。若当前用户明确要求某字段为 0，应说明报错但不阻止刷新，不擅自改变初始技能设计。

尚未确认：负数、超出可用技能数量时的完整分配算法，以及这两个字段在事件直接赠送／监狱生成英雄时是否生效。不要由通用技能空池结论推导缺额会自动转成专属技能，或把马车过周结论外推到全部英雄生成入口。

## 专属扎营技能数量配置



- 当前正常职业结构通常是四个专属扎营技能；

- 该字段是否必须严格等于实际定义的专属技能数量，以及省略、写错或改为其他数字时会出现什么行为，均未知；
- 没有专项设计和实测证据时必须仿照原版填写 `4`，不得根据字段名自行扩展其机制。

## 通用与专属扎营技能

当前已知的通用扎营技能只有：

| 技能 ID | 常见中文称呼 |
|---|---|
| `encourage` | 鼓励 |
| `first_aid` | 急救 |
| `pep_talk` | 鼓舞／鼓舞演讲，具体译名按本地化处理 |

目前观察到的其他扎营技能大多应按职业专属扎营技能理解。这里的“专属”表示技能被分配给特定职业，并不保证其内容或 ID 在所有职业之间绝对唯一：例如盗墓贼与强盗存在内容完全相同的专属扎营技能。因此，不得仅凭两个职业的技能效果相同，就把它误判为上述三种通用扎营技能之一。



## 英雄溢出与技能定义总量

英雄溢出取决于不同英雄的战斗技能数量与不同 ID 的扎营技能数量之和，不能按固定英雄个数换算容量。提高资源入口文件的 `max_resource_entries` 不能提高这一上限；削减不同 ID 的专属扎营技能是原表记录的缓解方向。具体溢出阈值仍未知，不把英雄数量或资源入口参数作为安全保证。

## 技能等级 `level`

每条扎营技能定义通常包含：

```json
"level": 0
```

截至目前，没有发现任何能让扎营技能升级的游戏机制；已扫描到的原版、官方 DLC 与本地现有 Mod 扎营技能定义也均使用 `level: 0`。因此：

- 当前应把扎营技能视为没有可升级等级的技能，并固定填写 `0`；
- 不得仿照战斗技能为扎营技能擅自建立 1～4 级差分；
- 该字段更深层的引擎用途、能否省略，以及填写其他数字时的行为均未知；
- `upgrade_requirements` 的存在不能直接证明扎营技能本身具有等级成长，它还可能只负责技能的购买／解锁条件，两者必须分开理解。

## 扎营点消耗 `cost`

`cost` 表示每次使用该扎营技能需要消耗的扎营点数。例如：

```json
"cost": 2
```

表示使用该技能消耗 2 点扎营点数。

- 写 `0` 表示使用时不消耗扎营点数；
- 小数、负数以及省略 `cost` 时的行为均未知，不得依靠猜测使用；
- 没有专门实测依据时，应填写符合设计的非负整数。

## 单次扎营使用次数 `use_limit`

`use_limit` 表示该技能在一次扎营期间允许使用的最大次数。例如：

```json
"use_limit": 1
```

表示该技能在本次扎营中最多使用一次。

- 大于 `1` 的整数会允许该技能在同一次扎营中使用相应次数；
- 写 `0`、负数、小数或省略该字段时的行为均未知；
- 不得把未经验证的 `0` 或负数解释为无限使用。需要多次使用时，应明确填写对应的正整数。

## Effect 目标选择 `selection`

扎营技能的每条 `effects[]` 通过 `selection` 规定该条效果作用于谁。当前已知值包括：

| `selection` | 当前含义 |
|---|---|
| `self` | 技能使用者自己。 |
| `individual` | 由玩家选择的一名单体队友；当前观察认为它不能选择使用者自己，但尚未完成专项验证。 |
| `party_other` | 当前技能目标之外的所有英雄。它不是固定表示“使用者之外”：应先判断技能的目标是谁，再排除该目标。 |

例如原版扎营技能 `mockery` 先以 `individual` 选择一名队友并使其增加 20 压力，再以 `party_other` 使该目标之外的所有英雄减少 20 压力：

```json
{
  "selection": "individual",
  "type": "stress_damage_amount",
  "amount": 20
},
{
  "selection": "party_other",
  "type": "stress_heal_amount",
  "amount": 20
}
```

因此，Agent 不得机械地把 `party_other` 翻译成“除施术者外全队”；它排除的是当前技能目标。若技能以自身为目标，排除目标后的结果才会恰好等于使用者之外的其余队员。其他 `selection` 合法值及更复杂组合的目标继承规则仍需继续依据原版实例整理。

## Effect 目标条件 `requirements`

扎营技能每条 `effects[]` 内的 `requirements` 用于筛选该条效果的受术目标。例如原版可见：

```json
"requirements": []
"requirements": ["religious"]
"requirements": ["not_religious"]
"requirements": ["afflicted"]
"requirements": ["has_deaths_door_recovery_buffs"]
```

- 空数组 `[]` 表示该条效果没有额外的目标条件；
- 当前推测同一数组内填写多个条件时，目标必须全部满足，即按 AND 处理，但这一点尚未专项验证，不能当作完全确定的结论；
- 合法条件的完整列表目前未知，只能使用原版已有值或经过实际验证的扩展值；
- `requirements` 约束的是对应 `effects[]` 的受术目标，不应擅自解释成整条扎营技能的使用者条件或技能解锁条件。

## Effect `.name` 命名习惯

除非当前用户对 Effect 名称有专门要求，否则 `.name` 尽量不要包含空格，优先使用稳定的 ASCII 英文、数字与下划线，例如 `my_mod_damage_boost`。这样可减少解析、同名分行、引用和后续检索中的歧义；这是一项默认命名建议，不是把所有含空格的历史名称一律判为非法。

## Effect 随机组 `chance.code` 与抽取数值 `chance.amount`

扎营效果的 `chance` 结构包含 `code` 与 `amount`：

```json
"chance": {
  "code": "b",
  "amount": 0.65
}
```

当前已确认：

- 使用相同有效 `code` 的多个结果具有互斥性；同一随机组中不会把这些结果当成彼此独立、可同时成功的效果。
- 使用不同有效 `code` 的效果属于不同随机组，各组可以同时结算并生效。若设计希望多个扎营效果共存，应选择确认不互斥的不同有效 `code`；这不替代各自 `requirements`、目标和其他生效条件的检查。
- 当前用户补充（2026-09-28）：此前以 ASCII 为例观察到多字符 `code` 只看首字符，`a` 和 `aa` 视为同一组并互斥；不得将这里的“首字符”扩展成已确认按完整 Unicode 字符判定，最新首字节证据见下。先前的 `aa`、`E8`、`c9` 等写法可以被接受，但不能借尾部字符建立独立随机组。单个大小写字母及数字均可用；大小写字母是否相互折叠仍未确认。
- 已测试可用的其他单字符：`! @ # $ % ^ & * ( ) - _ = +`、反引号、`~ [ { ] } | ; ' : , < . > / ?` 以及空格（JSON 中写为 `" "`）。这是已测试集合，不是全部合法字符的穷举。原始反斜杠不能直接作为 JSON 字符串内容，原始双引号也不能直接写入；其转义写法见下。
- 当前用户确认可用的 JSON 转义写法包括 `\"`、`\r`、`\\`、`\/`、`\b`、`\n`、`\f`、`\t`。转义序列不因为源码都以反斜杠开头而按首字符互斥；`\/` 与 `/` 则被确认互斥。`\"` 预计不与其他转义符互斥，但该独立性仍属推测。空格与通过 Tab 输入的空白是否冲突，当前仅有疑似观察，未确认。其余字符和转义符未测试。
- 知识库编写者此前报告 `\u0000` 与 `\uffff` 可被接受、`\u0021` 与 `!` 互斥。这只能说明接受性或特定等价关系，不能证明不同 Unicode 字符是独立随机组。转义写法与对应字符相同会互斥，但不同字符也可能互斥，不能反推为“只有相同字符才互斥”。不直接写中文、优先转义的建议只涉及书写方式，不能消除解码后的冲突。
- **已撤回旧推测**：“不同 Unicode 字符即可独立共存”及“65536 个独立 code／效果”。本次存档对照已表明，JSON 可解析、解码后是单字符且互不重复，不足以保证 Buff 共存。不能再以这些条件作为共存验证通过的标准。

### 存档对照证据：GUID 12283 的 MEGA_pea

证据来源：知识库编写者在本会话提供的只读配置／存档对照报告（2026-09-28）。本次入库没有收到原始存档路径或完整配置快照，没有独立重做存档解析；以下是报告中的观察，不是引擎反编译结果。

| 技能 | 配置应有 | 存档存在 | 缺失 |
|---|---:|---:|---:|
| 呼吸作用 | 98 | 65 | 33 |
| 同素一体 | 160 | 65 | 95 |
| 合计 | 258 | 130 | 128 |

呼吸作用：文本 Buff、+10 精准、普通形态 48 个充能 Buff、初始 PF 与寒冰 PF 各 6 个均存在。新增 Unicode code 的 36 项只留下以下 3 项：

```text
MGP_Camp_RespChg_Flame_250_PF
MGP_Camp_RespChg_Ark_200_PF
MGP_Camp_RespChg_Star_200_PF
```

缺失 ID 格式为 `MGP_Camp_RespChg_<形态>_<充能>_PF`：Flame 缺 0/50/100/150/200（5）；Poison、Primitive、Triplets 各缺 0/50/100/150/200/250（各 6）；Ark、Star 各缺 0/50/100/150/250（各 5），共 33。

同素一体：配置前 62 项（含 6 个自定义文本 Buff）全部存在；新增 Unicode code 的 98 项只留下以下 3 项：

```text
MGP_Camp_Iso_DMGL_Triplets_200
MGP_Camp_Iso_DMGH_Triplets_0_PF
MGP_Camp_Iso_DMGH_Ark_300_PF
```

缺失汇总：Primitive 普通/PF 的 0～300 七档位移加成共 14；Triplets 普通/PF 的七档 DMGL/DMGH 除上述两项外缺 26；Ark 同类伤害加成除 PF300 的 DMGH 外缺 27；Star 同类伤害加成缺 28，共 95。

将新增 code 按 **JSON 解码后的字符串重新以 UTF-8 编码所得的首字节** 分组：

| 首字节（十六进制） | 呼吸作用：配置项数／存档存在数 | 同素一体：配置项数／存档存在数 |
|---|---:|---:|
| C2 | 28／1 | 28／1 |
| C3 | 2／1 | 2／1 |
| E2 | 6／1 | 68／1 |

两个技能都恰好每组只留下一个 Buff。观察总数分别为 28+2+6=36、28+2+68=98，与每个技能新增部分吻合。每个技能的 65 个存档 Buff 不是已证实的硬上限，而是本例已有 62 项加三个首字节组各一项的结果。

### 三阶段存档对照：完整重启后 code 生效与燃烧 Buff 重复

知识库编写者于 2026-09-28 提供了新的三阶段只读存档对照。测试前完全退出并重启游戏，并进入一个新的副本；对象为英雄 GUID `12283`、职业 `MEGA_pea`。这组条件必须与此前旧存档对照分开记录。

1. **扎营前**：英雄共有 4 个 Buff 实例；`source: 8`（`bsrc_campingskill`）的扎营 Buff 为 0；呼吸作用与同素一体的 Buff 均不存在，可视为本轮干净初始条件。
2. **第一次扎营后**：呼吸作用应有 98 个不同 Buff ID，实际 98，缺失 0；同素一体应有 160 个不同 Buff ID，实际 160，缺失 0；合计 258 个实例，全部 `source: 8`，无重复。
3. **再次扎营后**：呼吸作用仍为 98/98；同素一体仍为 160 个不同 ID，但实例总数为 174；合计 258 个新实例仍全部出现，同时第一次扎营产生的 14 个火焰燃烧修正 Buff 旧实例仍保留，因此这 14 个 ID 各出现两份。

这组测试支持：在“完全退出重开 + 新副本 + 干净扎营前存档”的条件下，当前 Unicode／控制字符 code 配置能够让两个技能的 258 个目标 Buff 全部出现；此前“code 未生效”的旧存档结果不能直接归因于字符不支持，仍需考虑旧配置未重新加载、测试副本或其他运行时条件差异。

14 个重复的 ID 是普通与 PF 火焰形态、0～300 充能的燃烧施加量修正 Buff。两份实例字段均为：

```text
stat_type: hp_dot_burn_amount_percent (存档编号 89)
source: bsrc_campingskill (存档编号 8)
rule_type: in_mode (本例存档 rule 27)
is_false_rule: false
amount: 0.2
duration_type: combat_end
duration: 4
remove_if_not_active: false
remove_on_battle_complete: false (存档值)
```

### 当前解释与 Agent 安全检查

- **强支持的推断，尚非底层实现确认**：引擎可能按解码后字符串的首个 UTF-8 字节区分 code，而非完整 Unicode 字符。不要误写为“按 JSON 源码的反斜杠或 u 分组”。这能解释普通 ASCII 多字符首字符相同会互斥，也能解释不同 Unicode 字符仍发生分组冲突。
- 需要多个效果共存时，除了 JSON 合法性与字符唯一性，还应按解码后 UTF-8 首字节检查潜在碰撞；相同首字节按高风险互斥处理。不同首字节只是排除了当前已识别的碰撞风险，不代替目标、条件、生命周期与实际施加后存档 Buff ID 的核对。
- 优先使用已有共存依据的单字节 code；不能靠大量不同 Unicode 转义扩大独立组数。发现缺失时检查首字节碰撞，不要仅归咎于 JSON 无法接受某个转义。
- 尚未知：所有字符的支持范围、空值及 NUL 等特殊处理、同组保留哪个候选的完整算法、真正的独立组数／效果数上限；不得改口宣称上限已确定为 65、256 或其他数值。该解释不验证 `chance.amount` 的权重／概率语义。

- 原版实例主要使用同组 `amount` 合计恰好为 `1` 的写法，因此 `amount` 究竟是归一化后的组内权重还是百分比／概率值，当前仍不能完全确定。安全表述是“同组候选的抽取数值”，不要在未知边界下断言两者之一。
- 同组 `amount` 总和不等于 `1` 时的归一化或剩余概率行为，仍未确认；多个效果都写 `1` 时是否按等权抽取、首项优先、允许超额或产生其他行为，也未确认。
- 因此，不要把原版“合计为 `1`”的用法当作引擎强制要求，也不要在未实测时依赖多个 `1` 的特殊行为。

### 战斗开始时的惊慌判定与 `.can_surprise`

`surprise` 在这里应理解为战斗开始时的**惊慌**。惊慌概率会综合全局规则、英雄持有的相关 Buff 等修正进行判断，而不是只由某一个独立字段决定。

怪物 `battle_modifier:` 中的 `.can_surprise` 控制怪物方是否允许令英雄方惊慌：

- `.can_surprise true`：该怪物不禁止怪物方令英雄方惊慌，但不代表单凭它就必定造成惊慌；
- `.always_surprise true`：怪物方必定令英雄方惊慌，不再依赖常规惊慌概率是否足够；`.always_surprise false` 不提供这种强制效果。

若同一初始怪物队伍同时出现 `.always_surprise true` 与 `.can_surprise false`，两者谁的优先级更高目前未知。不得擅自推断“必定惊慌”或“必定不惊慌”；创作时应避免配置这种冲突组合，审计既有 Mod 时则明确标记为需要专项验证。
- `.can_surprise false`：现有认识是，只要战斗开始时的怪物队伍中有任意一个怪物写有该值，英雄方就不会被惊慌。这个“任意一个即整体禁止”的队伍级行为尚带有一定不确定性，应视为当前高可信结论而非已经专项验证的绝对规则。

`.can_be_surprised` 控制怪物方是否允许在战斗开始时陷入惊慌：

- `.can_be_surprised true`：该怪物不禁止怪物方陷入惊慌，但不表示怪物方必定惊慌；
- `.always_be_surprised true`：怪物方在战斗开始时必定惊慌，不依赖常规惊慌概率；`.always_be_surprised false` 不提供这种强制效果。

若 `.always_be_surprised true` 与 `.can_be_surprised false` 同时存在，谁的优先级更高目前未知。应避免主动创建这种冲突配置；审计既有配置时不得擅自判断最终结果。
- `.can_be_surprised false`：当前高可信认识是，只要初始怪物队伍中任意一个怪物写有该值，整支怪物队伍便不会惊慌；该“任意一个即整体禁止”的队伍级行为同样尚未专项验证。

在无 Mod 的原版常规环境中，英雄方与怪物方似乎只会有一方陷入惊慌，不会在同一场战斗开始时双方同时惊慌；这一互斥关系目前也属于高可信观察，尚不能扩展成所有 Mod 环境下都绝对成立的引擎规则。

还需注意：

- 在没有怪物以 `.can_surprise false` 禁止惊慌的情况下，夜袭战斗开始时英雄方必定惊慌；
- 战斗中途才召唤出来的怪物恒定不参与本场战斗的惊慌判定，因为惊慌过程只发生在一场战斗开始时；
- 因此，不能用中途召唤一个 `.can_surprise false` 的怪物来追溯取消已经完成的惊慌，也不能认为中途召唤的 `.can_surprise true` 怪物会重新触发惊慌判定。

### 扎营后的双方惊慌概率 Buff

原版提供以下两类 Buff：

```json
{
  "id": "campingPartySurprise",
  "stat_type": "party_surprise_chance",
  "amount": 0.1,
  "duration_type": "combat_end",
  "duration": 4
}
```

```json
{
  "id": "campingMonstersSurprise",
  "stat_type": "monsters_surprise_chance",
  "amount": 0.1,
  "duration_type": "combat_end",
  "duration": 4
}
```

- `party_surprise_chance` 修正英雄队伍在战斗开始时被惊慌的概率；负数会降低英雄队伍被惊慌的概率。
- `monsters_surprise_chance` 修正怪物队伍在战斗开始时被惊慌的概率；正数会提高怪物队伍被惊慌的概率。

- 同类惊慌概率修正相互加算。
- `duration_type: "combat_end"` 配合 `duration: 4` 在这里表示 Buff 持续接下来的 **4 场战斗**，而不是只持续下一场战斗。每场战斗结束消耗一段持续次数。
- 扎营技能直接提供的正式 Buff，其 Buff 来源应为 `bsrc_campingskill`。
- 进一步推测 `party_surprise_chance`、`monsters_surprise_chance` 以及前述夜袭概率效果，本质上都会给目标施加相应的 `bsrc_campingskill` 来源 Buff；其中正式 `type: "buff"` 的来源可以据扎营技能来源确定，但其他简写效果的内部 Buff 化仍需专项验证。

## 可获得职业 `hero_classes`

扎营技能的 `hero_classes` 数组用于规定哪些职业能够获得该技能：







- 数组内可以填写多个职业 ID，列出的所有职业都可以获得该技能；
- 这里应填写职业的内部 ID，而不是本地化后的职业名称；
- 空数组、省略字段、填写不存在的职业 ID 或其他特殊写法会怎样，目前未知；
- 新职业技能应明确列入对应职业 ID，不得依靠空数组或省略字段推测其会自动成为通用技能。

## 生存大师购买要求 `upgrade_requirements`

扎营技能中的 `upgrade_requirements` 规定英雄在生存大师处购买／解锁该技能所需满足的要求；它不是扎营技能自身的等级成长机制。这也解释了为什么扎营技能始终写 `level: 0`，但仍然带有名为 `upgrade_requirements` 的结构。



```json
"upgrade_requirements": [
  {
    "code": "0",
    "currency_cost": [
      {
        "type": "gold",
        "amount": 1750
      }
    ],
    "prerequisite_requirements": []
  }
]
```

其中 `currency_cost` 是购买该扎营技能所需支付的货币：

- `type: "gold"` 表示货币类型为金币；
- `amount: 1750` 表示需要支付 1750 金币；
- 该结构负责购买／解锁，不得据此给扎营技能制作多个等级；
- 其他货币类型、多项 `currency_cost` 的结算关系、空数组、省略字段、负数或小数费用的行为，目前尚未确认；没有特殊设计时应仿照已验证实例填写单项非负整数金币费用。

### 购买节点 `code`

当前扫描到的原版、官方 DLC 与本地 Mod 扎营技能实例中，`upgrade_requirements[].code` 均写为字符串 `"0"`。其底层用途目前未知，不能确认它是否真的是购买节点编号，也不能据此扩展出其他编号。

在没有专项验证的情况下：

```json
"code": "0"
```

应作为固定仿写值保留。不得因为字段名为 `code` 就擅自改成技能 ID、职业 ID、数字类型 `0` 或其他字符串。

### 前置条件 `prerequisite_requirements`

当前扫描到的 258 条原版、官方 DLC 与本地 Mod 扎营技能实例中，`prerequisite_requirements` 全部写为空数组：

```json
"prerequisite_requirements": []
```

该字段理论上可能用于规定购买扎营技能的前置条件，但其实际功能、合法非空结构和结算规则均未知，当前没有可供验证的非空扎营技能实例。

因此：

- 制作普通扎营技能时应固定仿写空数组 `[]`；
- 不得因为字段名称相同，就直接套用英雄升级树中的前置升级结构；
- 若设计确实要求购买前置条件，必须先通过专项测试或找到可靠实例，不能让 Agent 自行猜测格式。

## 扎营技能图标

图标放置目录为：

```text
raid\camping\skill_icons\
```

已确认的命名对应关系为：

```text
camp_skill_<camping_skill_id>.png
```

例如：

```text
skills[].id = "mixology"
raid\camping\skill_icons\camp_skill_mixology.png
```



- 自定义扎营技能应提供与技能 ID 对应的 `camp_skill_<id>.png`；

- 图标文件名的 `<camping_skill_id>` 必须与技能定义中的 `id` 对应；大小写差异、非标准命名和缺图时的具体回退表现未知，制作时不得依赖。

## 本地化名称

扎营技能名称通常使用：

```text
camping_skill_name_<camping_skill_id>
```

例如：

```xml
<entry id="camping_skill_name_mixology"><![CDATA[调酒]]></entry>
```

其他自动描述、Effect 文本和台词本地化应分别按本地化文档与实际技能结构检查，不能仅创建名称词条便断言扎营技能的全部显示文本已经完整。

## 用 Loot 引用承载扎营技能自定义文本

扎营技能可以通过增加一个 `loot` 类型的效果来触发自定义文本。当前实测可用的做法是：

1. 在扎营技能的 `effects[]` 中增加一个 Loot 引用；
2. 将该 Loot 表设计为实际不产生物品，即只有 `nothing` 条目具有大于 `0` 的抽取权重；
3. 在本地化 XML 中为该 Loot ID 添加 `camping_skill_effect_loot_<loot_id>` 条目。

例如 Loot ID 为 `T_ANTIQ_CAMP` 时：

```xml
<entry id="camping_skill_effect_loot_T_ANTIQ_CAMP"><![CDATA[产生一件随机的饰品。]]></entry>
```

这样可以在扎营技能界面显示自定义文本而不实际给予掉落。如果技能本来就要产生掉落，则可以直接为那个有效 Loot 表使用同样的本地化键；原版古董商人的扎营技能“搜寻饰品”是已知参考案例。该方法只确认 Loot 文本的引用形式和空掉落用途，不应据此推导其他自动描述或奖励结算规则。

## Agent 检查清单

1. 文件是否位于 `raid\camping`，并使用 `*.camping_skills.json` 命名？
2. 新职业文件前缀是否安全地使用英雄 ID？
3. `class_specific_number_of_classes_threshold` 是否在没有专项需求时仿原版写为 `4`？
4. 是否只把 `encourage`、`first_aid`、`pep_talk` 当作当前已知通用技能？
5. 是否避免因两个职业拥有相同技能，就擅自把该技能归类为通用技能？
6. 扎营技能 `level` 是否固定写为 `0`，没有擅自创建升级差分？
7. `cost` 是否按设计填写为非负整数；若不消耗扎营点数，是否明确写为 `0`？
8. `use_limit` 是否按单次扎营的设计次数填写为正整数，没有擅自用 `0` 或负数表示无限使用？
9. `selection` 是否准确区分 `self`、`individual` 与 `party_other`；是否避免把 `party_other` 无条件解释为“使用者之外全队”？
10. `requirements` 是否只使用已有或已验证的目标条件；多个条件按 AND 的行为是否保持为待验证，而没有擅自写成定论？
11. 是否区分 code 接受性与共存性；是否检查 JSON 解码后 UTF-8 首字节碰撞，而非只查单字符唯一性；是否按实际有效 code 分析施加顺序、按数组排列描述；是否撤回 65536 个独立效果的旧推测；是否把多字节排序、真实上限与底层实现保持为未知；是否核对施加后实际存档 Buff ID，并保留 chance.amount 的未知边界？ 修改了含 Unicode 转义 code 的扎营技能后，是否建议大退（关闭游戏重开）再验证，而非仅小退（主界面重进存档）？
12. `type: "buff"` 时，`sub_type` 是否指向有效 Buff ID；是否以扎营技能 `effects[].amount` 为优先数值（高于引用 Buff 的 `amount`），并正确识别热诚演讲实际为 −15% 而非 −30%；没有误要求两处必须一致或外推到其他字段与施加来源？使用 `stress_heal_amount`／`stress_damage_amount` 时，是否将 `sub_type` 安全地留空并填写明确的非负整数压力变化量，是否考虑了相关压力 Buff，并将扎营减压来源识别为 `camping_relieve_stress`、同时保持扎营加压来源为未知？使用 `health_heal_max_health_percent` 时，是否按最大生命值比例填写数值，并根据单体／多体目标正确考虑 `camp_skill`／`camp_skill_multi_target` 治疗源？使用 `remove_bleeding`／`remove_poison` 时，是否分别理解为清除全部流血／全部腐蚀，并在无专项证据时仿写空 `sub_type` 与 `amount: 0`，且没有擅自断言其是否受对应治愈／受到 DoT Buff 影响？使用 `reduce_ambush_chance` 时，是否把基础值、扎营技能修正与 Buff 修正按加算关系合并检查，并以最终概率小于等于 0 作为必定不夜袭的条件？使用扎营 Buff 时，是否将来源识别为 `bsrc_campingskill`？使用双方惊慌概率 Buff 时，是否正确区分 `party_surprise_chance` 与 `monsters_surprise_chance`，并将 `combat_end`、`duration: 4` 理解为持续接下来 4 场战斗？
13. `hero_classes` 是否列出所有应获得该技能的职业 ID，没有依靠空数组、省略字段或不存在 ID 实现未验证的特殊分配？
14. `upgrade_requirements` 是否只用于生存大师处的购买／解锁，没有被误写成扎营技能等级？`currency_cost` 是否按设计填写购买所需货币？其中未知用途的 `code` 是否安全地仿写为字符串 `"0"`，`prerequisite_requirements` 是否在没有专项证据时保持空数组？
15. 自定义技能是否提供 `raid\camping\skill_icons\camp_skill_<id>.png`？
16. 新图标是否按已验证实例制作成 72×72 PNG？
17. 是否提供 `camping_skill_name_<id>` 名称本地化？
18. 若需显示自定义扎营技能文本，是否添加了 Loot 引用，并确认该 Loot 表只有 `nothing` 条目具有正抽取权重，或直接复用本来就会产生掉落的有效 Loot？
19. Loot 文本是否按 `camping_skill_effect_loot_<loot_id>` 形式写入 XML，并确认 XML 仍包含必需的 `english` 基准节点？
20. 若技能或英雄使用迂回、复杂 Effect 顺序或 Bug 规避结构，是否已先询问用户要保留自动描述、修正排版还是改用自定义文本，并确认可变数值、符号、展示顺序及不同界面的具体期待？
