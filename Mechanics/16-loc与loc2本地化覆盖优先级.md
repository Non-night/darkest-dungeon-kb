## 新版 Effect 自定义文本与辅助演出

`.description_tooltip_id "entry_id"` 用指定本地化替换Effect自动描述，即使Effect `.has_description false`仍生效。必须与Buff同名字段区分：不能直接继承Buff的amount占位符或堆叠。2026-11-17技能路径已确认Effect自定义单项保留255字节，独立于最终511及模式255；其他调用方仍未由该研究覆盖。

- **辅助Buff隐藏抵抗**：Effect `.suppress_resist_popup true` 隐藏抵抗Pop；配合Buff JSON `suppress_apply_poptext: true`，后者隐藏成功施加的增益／减益Pop但单独仍显示抵抗，可同时减少两分支演出。特别适合协助机制而不参与常规数值的Buff，例如二段式条件检测，不限于此用途；不改变判定本身。
- **隐藏0治疗**：Effect `.suppress_zero_heal_popup true` 只隐藏降为0的治疗Pop。知识库编写者推测可加快狗贼二段式，但**仅限机制中的治疗被压制到0并隐藏零治疗Pop；正常直接治疗与此加速推测无关**。加速未经验证，不能保证缩短逻辑执行时间，不改死亡门与生命反馈时序。
- **隐藏自动喊话**：Effect `.suppress_bark true` 隐藏推拉等自动喊话，不影响`.bark`主动喊话。尤其适合推拉模拟前进／后退；不保证跳过位移动画，不修复位移机制。

来源：文档B037–B044及当前用户2026-11-05的用途、可能加速与明确零治疗限定；证据见Sources/modding_update_20261105_effects.json。成功施加隐藏字段已在Buff/buff_schema.md及官方决斗Buff实例记录。显示控制、设计建议与加速推测分别使用，不混为实测机制。

## 资料层级


## XML 源文件与 `localization.exe`
XML 源文件通常使用：

```text
localization\<自定义前缀>.string_table.xml
```

单独运行 Red Hook 的 `localization.exe` 时，已验证可用的最小项目布局是：

```text
<项目根目录>\
├─ localization\
│  ├─ project_paths.txt
│  └─ <前缀>.string_table.xml
└─ colours\
   └─ <前缀>.colours.darkest
```

原版 `localization\project_paths.txt` 的内容为 `..`，即要求编译器回到上一级项目根目录扫描。编译器内置的扫描模式为 `localization/.*\.string_table.xml$`，输出名形式为 `<语言>.loc2`；经上传器处理时还可能添加 Workshop ID 前缀。无论使用真上传 `direct_upload` 还是只编译不提交的假上传 `dont_submit`，都要经过这套 XML 编译检查。

把 XML 孤立放在当前目录、而不形成上述项目布局时，编译器可能无法发现语言节点并报：

```text
Couldn't find english language?!?
```

编译器出现条目错误时，进程退出码仍可能是 `0`。自动化脚本不得只判断退出码，必须同时检查控制台输出是否含 `SUCCESS!`，并检查是否出现 `ERROR`、`Malformed input`、`Mismatch`、`Couldn't find` 等诊断。

## `english` 是必需的基准语言节点
每份参与编译的 XML 必须提供：

```xml
<language id="english">
</language>
```

黑箱结果：

- 完全缺少 `english` 节点会报 `Couldn't find english language?!?`；
- `english` 节点可以为空；
- 空 `english` 加非空 `schinese` 可以成功生成 `schinese.loc2`。

在真上传或假上传编译时，如果 XML 完全不包含 `english` 节点，编译结束后不会输出对应的 `loc2` 文件。不能因为上传器进程退出码正常，或控制台只出现非致命提示，就认为本地化已经编译成功；必须同时检查 `english` 节点、控制台诊断和预期的 `loc2` 输出文件。最小安全模板仍可写成：

```xml
<language id="english">
</language>
```



## `entry` 的基本形式

```xml
<entry id="some_entry_id"><![CDATA[显示文本]]></entry>
```

CDATA 可避免普通文本中的 `<`、`>`、`&` 等字符直接参与 XML 解析。`id` 是否可自由命名取决于消费方，不能把所有 Entry ID 一概视为自定义字符串键：

1. **引擎按固定规律拼出的 ID**：必须满足命名规律；
2. **JSON/Darkest/XML 其他字段显式引用的 ID**：可以自定义，但引用处与 Entry 必须逐字符一致；
3. **固定 UI 文本 ID**：由硬编码界面消费，通常应沿用原版 ID；
4. **台词候选 ID**：允许同 ID 多条 Entry 作为候选池的情况，不能按普通键值覆盖理解。

## 具名格式参数 `{?name}`
Red Hook 编译器支持 `printf` 风格参数，并允许在参数前添加编译期名称：

```xml
{?hero_name}%s
{?amount}%d
{?percent1}%d%%
```

`{?name}` 的作用是帮助编译器在不同语言中重新排列参数，不是最终显示文字。例：

```xml
<!-- English -->
{?hero_name}%s has consumed {?amount}%d apples

<!-- 目标语言可重排 -->
{?amount}%d 个苹果被 {?hero_name}%s 吃掉了
```

已验证性质：

- 具名标记会从普通显示文本中剥除；
- 参数名不是固定枚举，编译器接受自定义名称；
- 名称本身不强制数据类型，但英语与目标语言应使用相同名称和相容格式；
- `{?name}` 后没有合法格式参数会报 `Malformed input`；
- 未具名参数若在目标语言中改变顺序，会报参数顺序/类型不匹配；
- 编译器对“目标语言少参数、多参数或错名”的校验并不完整，出现 `SUCCESS!` 不能证明游戏运行时调用安全。

当前二进制中的格式扫描表达式支持的转换字符至少包括：

```text
d f u i s c
```

常见含义为整数、浮点数、无符号整数、整数、字符串和字符。原版常见具名参数包括 `string1`、`decimal1`、`percent1`、`hero_name`、`amount`、`building_name`、`dungeon_name`、`quirk_name` 等；这些是原版使用习惯，不是编译器合法值白名单。

### 百分号与紧邻英文字符的转义冲突

当前用户于 2026-10-06 补充：在 XML 本地化中，单个字面 `%` 后面不能直接紧邻某些英文字符；目前已确认 `%` 后紧邻 `{` 或 `/` 时会被错误识别为转义符，导致 `%` 的显示被吞掉。若排版上必须让 `%` 与 `{` 或 `/` 看起来紧邻，应在两者之间插入一个零宽空格（U+200B）；源码中不再是直接相邻，但游戏显示时可保持视觉上的紧邻。

- 已确认的冲突字符：`{`、`/`。
- 直接相邻的 `%{` 或 `%/` 不应作为安全 XML 本地化写法。
- 这条规则针对单个字面 `%` 与紧邻字符；`%%`、`%d%%` 等格式字符串需继续按其自身格式语法分析，不要混用。
- 其他 `%` 后紧邻字符是否也会触发同类转义冲突，目前未确认；不要把已确认的 `{`、`/` 自动扩展成完整禁用字符表。

知识库编写者于2026-11-11明确补充：**即使某类文本本来就允许单个字面 `%`，仍不能据此认为 `%{` 安全。** 怪癖风味文本、Buff新版自定义文本等单 `%` 可正常工作的场景，直接写 `%{` 仍会被莫名识别为转义，导致 `%` 不显示。若不想影响排版且长度预算有余量，推荐在 `%` 与 `{` 之间插入**一个单独的 U+200B ZERO WIDTH SPACE**，不需要任何颜色标签。对既有 `%/` 冲突也保留上述间隔处理。不要把此方法理解为可以修复下节“本应写 `%%` 却漏写”的错误；两类问题必须分开。

### 百分号
需要先区分本地化 Entry 的消费方式：

- 对由 `description_tooltip_id` 直接引用的自定义文本，文本中的字面百分号只需写**一个** `%`。例如需要显示“造成 30% 伤害”时，直接在 XML 文本中写 `30%`；不要把 `description_tooltip_id` 的文本套用打折 Buff 的 `%%` 写法。
- 对打折 Buff（`upgrade_discount`）等会作为格式字符串、并由数值参数参与替换的自定义文本，字面百分号仍按格式字符串规则写成 `%%`；例如 `%d%%`。

因此，不能把打折 Buff 的字面百分号规则直接套用于新写法的固定文本；同时，新写法也支持 `%d` 等数值占位符，不得据此断言它只读取原样字符串。含占位符文本的字面百分号转义细节尚未确认。

知识库编写者于2026-11-11补充：**在本应使用 `%%` 表示字面百分号的位置只写一个 `%`，且没有紧邻其他英文符号时，该描述显示会导致游戏崩溃闪退。** 若紧邻其他符号，则可能因转义符的错误识别／拼接而没有闪退，同时也不显示 `%`；“没有闪退”不代表正确或安全，不把“可能”写成所有相邻符号组合均已验证。该结论限定于本应转义的消费路径，不将怪癖风味文本、新版Buff固定自定义文本等单 `%` 合法场景一律改成 `%%`。本次未给出全部相邻字符测试矩阵，不推断具体底层实现。

本次补充来源：`Sources/localization_percent_escape_20261111.json`；知识库编写者报告，Agent未自行执行游戏测试。

## 由 Buff 定义推导的固定 Tooltip ID
### Rule Tooltip
Buff rule 的自动描述通常按以下规律查找：

```text
buff_rule_tooltip_<rule_type>
buff_rule_tooltip_<rule_type>_false
```



```xml
<entry id="buff_rule_tooltip_target_hpabove"><![CDATA[{?string1}%s 对生命高于{?percent1}%d%%]]></entry>
<entry id="buff_rule_tooltip_target_hpabove_false"><![CDATA[{?string1}%s 对生命不高于{?percent1}%d%%]]></entry>
```

可解析为：

- `{?string1}%s`：被 rule 修饰的 Buff 基础描述；
- `{?percent1}%d%%`：rule 的百分比阈值；
- `target_hpabove`：Buff 的 `rule_type`；
- `_false`：该 rule 被取反。

原版/DLC 的 `buff_rule_tooltip_hpabove`、`buff_rule_tooltip_in_rank`、`buff_rule_tooltip_target_in_rank`、`buff_rule_tooltip_is_target_corpse` 等都支持这一规律。因此新增 rule 后若希望自动 tooltip 正常显示，应检查相应 Entry 是否存在；不能把它当作任意自定义 ID。

### Buff 型愈合与 Rule Tooltip 参数冲突

历史观察（2026-11-01，迂回聊天）：Buff型愈合hp_dot_heal在字符串Rule成立并生成描述时崩溃。新版文档明确已修复此崩溃，并修复条件未满足时仍显示施加pop。其他Buff型DOT同类修复仅为知识库编写者推测，不能当成已确认。

若 Rule 具有实际 `rule_data.float` 含义且没有有意义的 `rule_data.string`，同一聊天记录报告：Buff 型愈合描述中的 Rule `%d` 会显示愈合的持续回合数，而非 Rule 的 float 参数。例如 `in_rank` 所配置的站位条件，无论分别写 `0`、`1`、`2`、`3`，当愈合持续 8 回合时，描述仍可能显示成“5点8回合愈合【如果在8号位】”，其中时长的 `8` 被 Rule 描述再次取用；该显示现象不表示 Rule 实际按 8 站位判定。具体格式、数值顺序和其他 Rule/stat 组合未穷举验证。

旧版规避历史：自定义描述不能绕过上述崩溃，曾考虑覆盖Rule本地化或用带Rule清理Buff控制DOT存在；新版已修复hp_dot_heal字符串Rule崩溃，不再要求为此采用这些迂回。非静态条件DOT在不生效时需移除的其他生命周期要求仍独立核对。

聊天中关于“多个 `%d` 是否只导致描述错误而不崩溃”的提问没有得到明确确认；该表现保持未知。也不要把 float Rule 的回合数错显现象推广成所有多个 `%d` 的通则。

## 附魔描述：没有自动生成文本

所有附魔均无自带描述，不会自动生成可见描述。若设计要求在界面中显示附魔效果，必须为附魔提供自定义文本，并核对该文本实际挂载的 Buff、`has_description` 以及本地化 Entry。通常优先使用 Buff 的 `description_tooltip_id`，它也支持引用 `amount` 的数值占位符。若要在副本中持有者的 Buff 栏详情里合并显示，另须遵守下文的附魔与文本合并边界；若希望逐条显示，则可直接给承载附魔的 Buff 写自定义文本。

若不希望附魔显示描述，应明确隐藏描述；对于预计长期存在、且不需要图标表现的附魔 Buff，也可以使用合适的无图标 Buff 源。无图标源只解决图标/来源表现，不替代 `has_description`、`duration_type`、Rule 生命周期或清理设计；来源仍须按具体语义选择，不能仅凭无图标就任意替换。

不能因为附魔内部引用了普通 stat、Effect 或 Buff，就假设游戏会像普通 Buff 一样自动拼接并显示附魔说明。

## 新写法数值占位与堆叠显示（2026-10-28修正）

知识库编写者2026-10-28修正：新写法 `description_tooltip_id` 的本地化文本支持 `%d` 之类的数值占位符，取值使用对应 Buff 的 `amount`，且可像打折／进化写法一样堆叠显示。此前否认可引用或堆叠 Buff 数值的结论已撤回，不再作为当前规则。本条是知识库编写者明确修正，非本轮新增实机测试。

尚未确认完整占位符集合、多占位符取值顺序、数值缩放与取整及全部合并条件；不能由本条推定所有 stat_type 或不同 Entry ID 均会合并。2026-11-17补充确认了副本中 Buff 栏详情内的纯文本／计数文本及附魔影响，见下节；不由此推断其他界面是否合并。含数值占位符时字面百分号的转义细节仍需核验，不把既有固定文本单个 `%` 的规则泛化。

## 副本 Buff 栏详情的自定义文本合并与附魔边界

本节仅讨论副本中英雄／怪物身上 Buff 栏的详情显示，不对其他界面或调用位置能否合并作结论。这里的“折叠”即合并显示：原本会重复列出“受击时：XXX”等多条描述的地方，合为一条；计数文本可汇总显示数值。文本合并不等于 Buff 实例、附魔执行次数、Rule、持续时间或清理条件合并。

**先满足 Buff 原本就可合并的前提，再讨论下表。** 不能简单以来源是否相同、原本图标是否相同来代替这一判断：暴击源与技能源可以合并，虽然原本图标不同，合并后暴击源图标会覆盖普通技能源图标而显示为同一个图标；事件源与技能源不会合并。特殊源内部仍按自身的特殊合并规则处理，本次未测试，不能用下表覆盖这些特殊规则或扩展跨源合并范围。源类型与图标的既有规则见 [Buff 源与真驱散](15-Buff源与真驱散.md)。

在上述范围与前提下，**承载自定义文本的 Buff 本身不携带附魔**时：

| 自定义文本方案 | 纯文本，不含数值占位符 | `%d`、`%d%%` 等计数文本 |
|---|---|---|
| Buff `description_tooltip_id` 官方新写法 | 不合并 | 可以合并显示 |
| `upgrade_discount` 折扣型 | 可以合并显示 | 可以合并显示 |
| `quirk_tag_evolution_duration` 怪癖进化型 | 可以合并显示 | 可以合并显示 |

**承载该文本的 Buff 本身携带附魔时，三种方案均不合并显示**，无论纯文本还是计数文本，携带一个或多个附魔均按此处理。当前用户要求暂按所有附魔类型适用处理；社区报告未给出实际逐类测试清单，因此“所有类型”是当前采用口径，不冒称逐类实测，遇到特例再修订。这里限定的是该文本 Buff 自身携带附魔，不是说持有者身上存在其他附魔就会阻止独立文本 Buff 合并。

需要合并显示时，应让承载文本的 Buff 不携带附魔，并选择适合纯文本／计数文本的方案；需要合并的纯文本使用折扣型或怪癖进化型。若本就希望不合并、逐条显示，可以直接在承载附魔的 Buff 上写自定义文本，不要求为此拆分。此为显示需求下的方案选择，不是所有附魔一律拆分的创作要求，也不保证拆分能跨越来源等原有不可合并条件。

证据：九封2026-11-17 12:27:23–12:31:03的社区实测报告，由知识库编写者提供；不带附魔的折扣型／怪癖进化型合并能力由知识库编写者长期使用经验补足，当前用户明确按实测有效收录。当前用户同日补充显示位置、仅限制文本 Buff 本身、所有附魔类型的暂行口径，以及“原本能合并”的前提和暴击源／技能源／事件源的例子；最后修正取代了“源类型使用相同图标才可合并”的中间说法。原话与证据分级见 `Sources/buff_tooltip_merge_20261117.json`。具体游戏构建、测试代码、逐类附魔列表未提供；无 Agent 新增游戏实测。

## 新自定义文本的单条长度上限（2026-10-28）

2026-11-17技能消费者专项研究已将历史“256／128字符”的笼统说法按处理阶段修正。以下均为**实际保留的UTF-8字节，不含结尾NUL**：技能中Effect自身自定义项255；现代Buff自定义应用项255；`upgrade_discount`及`quirk_tag_evolution_duration`的具名技能正文先保留127，再追加SPACE；一个模式差分汇总255；公共正文511；公共与模式部分最终拼接后再截到511；面板一个模式名63。缓冲分配64／256／512不能等同于可保留正文64／256／512。

旧的2026-10-28“新写法256、打折128”及11-04建议255／127，作为知识库编写者历史报告保留，**不再作为所有消费者的统一硬边界**。新测技能127+尾SPACE与旧报告128可能有口径或消费者差异，当前饰品、状态栏Buff详情、怪癖等未由这次研究重测。怪癖总显示建议仍不超过255，确切255／256边界继续未知。

局部255不能直接当作可自由填写255字节正文：目标头、Rule、概率、持续时间、颜色、数值展开、连接符等可能另占各阶段额度。Effect自定义`P[:255]`与同类别现代instant Buff的`(P[:255]+SPACE)[:255]`已分离；这一差1不等同前后多一个换行。完整流水线、具名定义、量化表和边界见[技能描述专题](100-技能描述容量拼接排版与面板战斗可见性.md)第1—8节及附录。证据见`Sources/skill_tooltip_research_20261117.json`；本次为既有研究入库，未重新进行游戏测试。

## 完全空白 Bark 与不可跳过的延迟

在官方预设台词及自制 Bark 中，本地化台词内容完全为空、连空格也没有时，实际调用喊话不会显示对话框，但仍正常产生喊话的对话框延迟（原表称“系统不应期”）；这段延迟不能像普通对话框那样通过鼠标点击等方式跳过。这里“完全空白”指本地化条目的文本内容，不是省略本地化 ID 或引用不存在的条目。

仅含颜色代码的台词不同：会显示没有文字内容的对话框，而且可以跳过。不能将颜色代码或空格当成完全空白文本。

空白 Bark 是通用的延迟手段，可以用于一切需要拖延动画或回合结束的情形，不限于 buffFX。连续调用完全空白 Bark 可用于人为延长这段延迟；本节不规定未经记录的精确时长或调用数量，也不将原表“无明显副作用”的经验扩大为任何流程均无副作用的保证。它提供延迟，不据此宣称已修复某个具体崩溃，亦不恢复 buffFX 专题删除线中的可靠修复保证。

证据：迂回表第41条 P1056/X1228–P1058/X1230；当前用户于2026-11-03补充，空白 Bark 可用于一切需要拖延动画／回合结束的情形。非本轮新增实机测试。`.bark` 字段的英雄目标及本地化 ID 规则见 [Effect.bark](../Effect/keyword/Effect.bark.md)；此处不改写其对象边界。

## 英雄刀甲名称：Entry ID 直接取 Info 的 .name

知识库编写者2026-10-28明确：英雄武器／护甲名称的本地化Entry ID直接取Info中对应weapon:／armour:的.name字符串，必须完全一致，不固定拼接职业ID。weapon: .name "SF_Ele_weapon_0" 对应Entry ID就是SF_Ele_weapon_0；SF_Ele在该例不是职业ID，不得替换为真实职业ID_weapon_0。原版<hero_id>_weapon_<level>或<hero_id>_armour_<level>只是.name常用命名，不是引擎强制拼接规则。通用格式应写<weapon.name>／<armour.name>；不改变图标路径或升级等级规则。

本条来自知识库编写者明确说明，不冒称本轮新增实机测试。对应示例：

```darkest
weapon: .name "SF_Ele_weapon_0"
```

```xml
<entry id="SF_Ele_weapon_0"><![CDATA[自定义武器名]]></entry>
```

以上仅为名称引用关系示例，不是完整武器定义。护甲同理，以 armour: 的实际 .name 作为Entry ID。它也不等于技能名 combat_skill_name_<hero_id>_<skill_id> 的拼接规则。

### 武器与护甲的升级树名称

`upgrade_tree_name_` 接完整升级树 `id`。原版 `localization\heroes.string_table.xml` 的简中段提供 `upgrade_tree_name_crusader.weapon`（剑）和 `upgrade_tree_name_crusader.armour`（盔甲）。`upgrades\heroes\crusader.upgrades.json` 中相应树的 ID 为 `crusader.weapon`、`crusader.armour`。各档装备名另按 Info 中各档的 `.name` 取键，如 `crusader_weapon_0` 与 `crusader_armour_0`。建议自定义 XML 把整棵树的名称和各档装备名归在同一组。原版文件确认键及其关联，精确显示位置本轮未实测。

### 蓝字定位本地化查找失败

蓝色的内部键给出了界面正在查找的 `entry id`。例如饰品名 `str_inventory_title_trinket<trinket_id>`、单档装备的实际 `.name`、或装备升级树的 `upgrade_tree_name_` 加树 ID。拿到完整键后，先核对当前语言的对应条目，再检查编译产物是否包含新版本、是否加载了正确文件、清单和文件名有无冲突。原版文字也大面积受影响时优先排查 `0_schinese.loc2`、`schinese.loc2` 等重名产物，见[Mod 识别专题](24-Mod识别与职业Mod目录结构.md)。

## 文本自动居中、首空格与不可见非零宽字符（2026-10-31）

2026-10-31“绝大多数文本自动居中、忽略条目首空格”保留为知识库编写者的历史经验，不能继续套用到全部技能描述。2026-11-17收录的具名技能消费者对照中，首12个SPACE使可见文本右偏，尾12个左偏，前后配平约居中；Tab／NBSP也有对应偏移，CR有advance而非零宽。前置空格参与计宽，且始终占字节预算。

排版应看**解码后整条可见行两端的合计advance**，包括Buff包装尾SPACE、残片吞掉的SPACE及拼到同一行的后段。当前活动字体下SPACE／CR advance5、W22、i6、汉字采样23；前后L／R个SPACE且其余对称时，可条件估算中心偏移`(L-R)×5/2`。这些数值不保证其他字体、缩放、GUI。U+200B等在该活动路径缺字被跳过，不等于所有字体均零宽。

居中异常不能只凭肉眼把原因归为不可见字符；还须核对实际文本、颜色包装、截断接缝及布局。见[技能描述专题](100-技能描述容量拼接排版与面板战斗可见性.md)第9、13节及冻结的spaceflow14／whitespace14证据。

## 三种常见自定义描述方案

由于许多技能、饰品和其他界面的自动生成描述会受到迂回实现或已知 Bug 影响，制作时常需要改用自定义文本。当前应区分三种方案：

| 方案 | 主要做法 | 可变数值 | 当前取舍 |
|---|---|---|---|
| `upgrade_discount`（打折 Buff） | 利用 `buff_stat_tooltip_upgrade_discount_<stat_sub_type>`；实际本地化对象是 Buff 的 `stat_sub_type`。社区习惯上常让自定义 ID 与副类型后缀相同，但这只是命名约定。 | 不是绝对不能用于可叠加数值；使用 `%d` 等参数时数值前可能自动带负号。本来需要负号时可直接利用，也可人工额外写两个负号构造破折号；具体细节待补充。 | 方案成熟、通用；文本长度上限相对较短。 |
| `quirk_tag_evolution_duration`（进化 Buff） | 利用进化 Buff 在同一状态图标中的数值显示与叠加。 | 可以借助 Buff 叠加显示可变数值。 | 适合需要叠加数值的文本；具名技能消费者与打折同为正文127后加SPACE；其他消费者仍按各自证据。 |
| `description_tooltip_id` | 在 Buff 定义中直接引用自定义 Tooltip 本地化 ID，例如 `buff_tooltip_<自定义后缀>`；2026-08-19 更新后可用。 | 本地化支持 `%d` 等数值占位符，取 Buff 的 `amount`，可像打折／进化写法一样堆叠显示。 | 自定义文本默认优先方案，不限于固定文本；技能应用项保留255字节；旧打折／进化正文127后加SPACE。其他消费者不直接外推。 |

知识库编写者既有选择偏好是自定义文本默认优先 `description_tooltip_id`。经2026-10-28修正，数值占位及堆叠显示同样可用新写法；不能再仅因需要动态数值就排除新写法、强制改用打折或进化方案。2026-11-17明确的例外：副本中 Buff 栏详情需要合并纯文本时，应使用不携带附魔的折扣型／进化型 Buff，且须满足 Buff 原本能合并的前提。需要逐条显示时可直接在附魔 Buff 上写自定义文本。其他界面是否合并不作结论；不推定三者全部行为完全相同。

百分号书写也必须随方案区分：`description_tooltip_id` 引用的固定自定义文本写单个 `%`；`upgrade_discount` 的格式字符串写字面百分号时使用 `%%`。不要因为两者都属于本地化文本，就把后者的转义规则误用于前者。

三种方案的全部行为并未确认完全等价，但数值堆叠不再是排除 `description_tooltip_id` 的理由。技能应用项：新写法255字节，打折与进化正文127后加SPACE；历史256／128口径及其他消费者另见长度节。无论采用哪种方案，都必须检查实际本地化 ID、参数格式、`has_description`、Buff Rule、目标和生效时机。附魔没有自动生成描述，另需确认自定义文本实际挂载。

## Buff 型 `tag` 不适合作为隐形自定义文本或常驻逻辑载体

当前用户明确补充（2026-09-24）：不要把自定义文本（`description_tooltip_id`）挂载在 Buff 型 `tag`（`stat_type: tag` 或 `.buff_type tag`）上，因为这会使 Buff 栏强制渲染一个标记图标及其内容。常驻驱散 Buff 等不需要标记出现的场合也不要使用 Buff 型 `tag`；即使 `amount` 为 0，也不能用来规避该表现。

因此，凡是设计上不需要标记出现在 Buff 栏的场合，都不要使用 Buff 型标记。这里记录的是显示与设计安全边界，不是说 `tag` 的语法本身非法；不要把它推广到 Info/怪物标签或其他非 Buff 型 Tag 系统。

## Rule 与自定义文本显示的边界

知识库编写者确认（2026-09-20）：Rule 不可能直接控制自定义文本是否显示。`description_tooltip_id`、`upgrade_discount` 的本地化 Entry 以及其他固定自定义文本，本身没有一个“当 Rule 成立才显示／当 Rule 失效就隐藏”的条件接口。

Rule 能控制的是 Buff 或 Effect 的实际生效、条件状态、暂时停用、移除和后续调用；不能把 Rule 结果直接传给本地化文本渲染器。因而不能把“带 Rule 的 Buff”写成“Rule 不成立时自定义文本自动消失”，也不能用 `is_false_rule`、`remove_if_not_active` 或 `has_description` 推导出条件文本开关：`has_description` 是静态描述配置，`remove_if_not_active` 是 Buff 生命周期行为，不是本地化条件表达式。

如果确实需要条件化显示，应通过不同 Buff/Effect 的施加与清除、不同技能/模式的本地化路径或其他已确认的对象切换来间接实现；必须分别核对这些对象何时存在、何时移除以及文本 Entry 的实际消费方。不要把 Rule 本身当作自定义文本的显示门。

## 自定义文本建议长度与怪癖总显示长度

旧的2026-10-28“新写法256、打折128”及11-04建议255／127，作为知识库编写者历史报告保留，**不再作为所有消费者的统一硬边界**。新测技能127+尾SPACE与旧报告128可能有口径或消费者差异，当前饰品、状态栏Buff详情、怪癖等未由这次研究重测。怪癖总显示建议仍不超过255，确切255／256边界继续未知。

技能使用本次实际保留字节与逐层预算，不将历史建议值再称为尚有1字节余量。完整范围见本篇长度节及技能描述专题。

## 所有本地化文本的字符位计数与打折 Buff 上限

按实际消费者**保留的UTF-8字节**计数，不能按可见汉字数或XML源字符串`len()`计。2026-11-04历史通用计数经验，经技能路径研究细分如下：

- ASCII字母、数字、普通半角SPACE各1；本次普通汉字与U+200B／C／D、U+2060／FEFF各3。不是所有Unicode字符都3字节。
- 源Entry内CRLF为2；引擎拼接LF为1，不能把所有换行固定算2。LF被残片解码吞掉仍占已写入字节。
- 编译后的颜色头9、尾4，一对13；不是XML花括号标签原文的长度。
- 数值按实际格式化结果计；`%%`只在实际格式器将其变成单个百分号时计1。纯文本与不同载体不能统一折半，其他printf格式不因此获得支持。
- 分别核算单项、标题、Rule包装、模式汇总、公共正文与最终拼接；上限依消费者，详见本篇“新自定义文本的单条长度上限”及[技能描述专题](100-技能描述容量拼接排版与面板战斗可见性.md)。旧128／256不再作跨消费者硬上限。

## 迂回技能／英雄的描述期待必须先确认

使用迂回、清理后重施加、复杂 Effect 顺序或已知 Bug 规避结构的技能和英雄，自动生成的技能描述很可能无法准确反映实际效果。此类任务不能默认沿用引擎自动描述，也不能默认替作者选择某一种自定义文本方案。

在生成或修改代码前，必须询问用户的具体期待，至少确认：

- 是保留自动描述、修正排版，还是完全改为自定义文本；
- 是否需要显示可变数值、叠加后的合计值、正负号或特殊标点；
- 描述应按设计意图排序，还是按实际生效顺序逐项展示；
- 技能、英雄、饰品等不同界面是否需要分别提供文本。

若用户尚未明确，必须把描述方案标为待确认，不得仅凭迂回代码结构推断其希望的显示文本。

## 怪物名称本地化：使用小类 ID

知识库编写者确认（2026-09-20）：怪物名称的本地化 Entry ID 是 `str_monstername_<怪物小类ID>`，必须使用完整小类 ID，不能替换为大类 ID 或 enemy_type。怪物名称未本地化会产生红字报错，size0 也不例外。







空名称条目与缺少条目不是同一种情况；不能因为 size0 不显示名称就省略 Entry。每个 `_A`、`_B`、`_1` 等小类均需自己的名称 ID。普通可见怪物应填写实际名称，不把 size0 的空名称方案推广为默认。

该条目应放入 Mod 的 `localization/*.string_table.xml`，提供编译要求的 `english` 基准语言节点，并覆盖设计支持的显示语言。XML 源还需经本地化编译形成可加载产物，单纯存在未编译 XML 不等于游戏已经读到名称。

## 技能名本地化 ID 的长度边界

当前用户于 2026-10-21 提供并实测：`combat_skill_name_<hero_id>_<skill_id>` 类型的技能名本地化 Entry ID **不能超过 63 个字符**。示例 `combat_skill_name_Electors_of_the_Ancients_SF_Ele_eldritch_blast` 长度为 64 个 ASCII 字符；该条目完成编译后，游戏内未能正常识别，表现为蓝字。

因此，技能名本地化 ID 应在源 XML 中控制为不超过 63 个字符；超长时应优先缩短英雄 ID 或技能 ID，而不是只修改 CDATA 文本。这里记录的是技能名 Entry ID 的已观测边界，不应泛化为所有本地化 Entry ID、所有超长 ID 或所有蓝字问题都遵循同一规则。

以下细节仍未知：具体游戏版本；编译器是否必然报错还是主要在游戏运行时识别失败；非 ASCII 字符的计数方式；该边界是否适用于扎营技能、饰品、事件、Buff 或其他本地化 ID 类型。

### 职业专属台词与基础回退

英雄台词可以使用两级查询键：

```text
<hero_id>+<bark_id>
<bark_id>
```

其中加号 `+` 是完整 Entry ID 的组成部分，并非本文用于说明字符串拼接的占位符。凡是 `<hero_id>+<bark_id>` 形式的台词，发言者都是该职业英雄；即使基础台词 ID 中带有 `monster`、怪物技能名或剧情敌人语义，也不能据此把说话主体解释为怪物或旁白。引擎在某个英雄进入对应台词情境时，优先查询该职业的专属键 `<hero_id>+<bark_id>`；若未定义专属键，则回退到无职业前缀的基础键 `<bark_id>`。

例如，`str_bark_first_aid` 是使用通用扎营技能“急救”时的基础台词 ID。若本地化中存在：

```text
a+str_bark_first_aid = xxx
str_bark_first_aid   = yyy
```

则英雄 `a` 使用急救时说 `xxx`；没有定义专属差分的英雄 `b` 使用急救时说 `yyy`。若再增加：

```text
b+str_bark_first_aid = zzz
```

重进存档使本地化刷新后，英雄 `b` 使用急救时改说 `zzz`。

#### 黑暗之心“点名”台词实例

固定基础台词 ID：

```text
str_monster_user_selected_targets_kill_pill
```

它用于极暗地牢第四关面对黑暗之心（先祖最终阶段）时的技能“到吾造物主身边来”，社区俗称“点名”。该技能让玩家自行选择一名英雄：鼠标悬停到候选英雄时，被悬停的英雄说出该台词；玩家按下鼠标确认并使技能释放后，该英雄受到 `.kill` 的瞬间死亡效果。

职业专属形式为：

```text
<hero_id>+str_monster_user_selected_targets_kill_pill
```

这里的发言者仍是 `<hero_id>` 对应的英雄，不是黑暗之心、先祖或旁白。`monster_user_selected_targets` 描述的是“怪物技能由玩家选择目标”这一交互情境；台词触发点是鼠标悬停选择阶段，而非 `.kill` 已经结算之后。

台词 ID 末尾的差分编号没有统一的纯文本判定规则：

- 有些 `_0`、`_1` 是同一情境下的多条差分；
- 有些 `_0`、`_1` 实际对应不同情境；
- 有些差分编号写作 `0`、`1`，不带下划线。

因此不得仅凭 `_0`、`_1` 或 `0`、`1` 后缀，断言它们一定是随机台词池或一定是不同事件。必须结合原版/Mod XML 注释、同前缀条目以及实际消费情境逐项判断。另需注意：这套“职业专属键优先、基础键回退”机制不等于任意 Entry ID 都能在同一个 XML 中安全重复；普通同 ID 重复仍应按后文的闪烁风险处理。



```text
<hero_id>+str_roster_list_low_stress_bark
<hero_id>+str_bark_shuffled
<hero_id>+egg_increment_bark_1
```

它们分别可用于城镇名册低压力闲置、战斗中被乱位、女伯爵寄生蛋 ActorDot 进入第一阶段等英雄发言情境；同一 ID 下的多条文本均作为候选台词多抽一。

该规律的安全边界是“由英雄发言的 Bark 类消费项通常支持”，而不是“所有重复本地化 ID 都支持”。普通 UI 文本、描述、自动 Tooltip 格式以及其他非 Bark Entry 仍不得无意重复；遇到陌生台词 ID 时也应结合原版/Mod 注释和实际消费方判断。

### Effect 自动描述的全局格式 Entry
以下固定 Entry ID 会影响所有由游戏自动生成的 Effect 描述，不只影响定义它们的英雄、饰品或 Mod：

```text
effect_tooltip_dot_format
```

- 用于自动生成 DOT 数值与持续时间的格式；
- 第一个整数参数表示每次触发的数值，第二个整数参数表示持续回合数；

- 重新本地化该固定 ID 会全局改变其他自动生成描述的显示格式。

```text
effect_chance_format
```

- 用于自动生成 Effect 概率相关的显示格式；
- 不能把其出现条件简化成“.chance 低于 100%时显示”；
- 任何需要自动显示概率的场合都可能调用它，包括 Effect 自身概率，以及流血、腐蚀、眩晕、跨侧 Buff 等还需经过对应抗性判定的效果；以上只是常见例子，不是完整消费清单；
- 某些 100% 概率会显示，某些 100% 概率好像不会显示，具体抑制条件目前尚未明确；
- 重新本地化该固定 ID 同样会全局影响所有调用自动生成描述的内容。

上述全局影响仅指由引擎使用这些固定格式 Entry 自动拼接的描述；完全由作者手写且不调用这些模板的自定义描述不会仅因这两个 Entry 改变。

## 相同 Entry ID：跨文件覆盖与同文件闪烁
相同 Entry ID 的行为必须区分“位于不同本地化文件”与“在同一个 XML 内重复定义”。

### 不同文件中的相同 Entry ID
大多数相同 Entry ID 位于不同文件时会发生覆盖，这正是汉化 Mod 覆盖原文本地化的基础。覆盖时还必须先比较文件格式：

- `loc` 的覆盖优先级高于 `loc2`，不受双方 Mod 加载优先级影响；
- 双方同为 `loc` 或同为 `loc2` 时，再按 Mod 加载优先级决定最终覆盖者。

### 同一个 XML 内重复定义同一 Entry ID
编译器允许在同一个 XML 的同一语言节点中多次定义同一 Entry ID，生成的 LOC2 也会保留这些文本。该 LOC2 被游戏读取后，大多数此类词条会在多份本地化内容之间快速闪烁，而不是稳定采用第一条或最后一条。因此：

- 普通 Entry ID 禁止在同一个 XML 内无意重复；
- 编译成功不代表重复定义安全；
- 遇到游戏内文字闪烁，应优先检查同一 XML 内是否重复定义了该 Entry ID。

只有少数特殊 Entry ID 在同文件重复时不会闪烁，而会被游戏作为正常差分或候选内容处理；目前尚不能完整列出这些特殊 ID。未取得该消费方的明确实例或测试前，不得假定任意 bark、UI 文本或描述 ID 属于例外，也不得把“重复 ID”笼统解释为随机候选池。

## 尚未明确：哪些条目必须本地化

当前知识库还没有一份完整、经过逐项验证的“所有需要本地化的 Entry ID 清单”。已确认或有较强规律的只是部分类别，例如技能名称、扎营技能名称、饰品名称与稀有度、Buff 的 rule/stat Tooltip、部分 Effect/饰品 Trigger 前缀、明确写出的 `description_tooltip_id`，以及特定 Loot 或台词键。自动生成描述、技能/饰品附加效果、Loot 文本、条件分支、不同调用方的显示字段，是否必然使用某个固定 Entry ID，当前不能仅凭字段名或最终界面表现推断。

因此暂列为未知边界：

- 哪些技能、饰品、扎营技能、Loot、Buff、Effect 或其他配置会自动产生描述；
- 自动描述缺失时，究竟应补固定 Entry、使用自定义 Buff 描述方案，还是填写 `description_tooltip_id`；
- 同一配置在不同界面、语言、调用方或游戏版本中是否消费不同 Entry ID；
- 已知 Entry ID 之外是否存在尚未整理的固定前缀、条件后缀或版本新增键；
- 仅提供名称词条是否足以覆盖该对象的全部显示文本。

制作时必须先按实际调用方和已有原版/DLC/实测证据逐项确认需要的本地化键；不能因为某个对象“看起来会显示文字”，就把一个猜测的 Entry ID 当作通用必需项，也不能把当前已列举的示例误当成完整清单。

## XML `entry` 的 `arena_priority`


```xml
<entry id="..." arena_priority="1"><![CDATA[...]]></entry>
```

当前官方 `localization.exe` 的黑箱结果：

- 精确字面值 `arena_priority="1"` 会改变 LOC2 中该 Entry 的 1 字节元数据；
- 省略属性以及 `0`、`2`、`true`、`false`、`True`、`01`、`-1`、`1.0`、`abc`、空字符串等值，均与未写属性生成相同结果；
- 因此它不是普通整数优先级，也不是布尔字段；编译器只专门识别精确字符串 `"1"`；
- 它不改变可见文本，但确实进入了 LOC2 Entry 元数据，所以不是注释。

仍未知的是游戏运行时如何消费这一个标志位：可能与竞技场文本选择、通用覆盖或来源区分有关，但尚无证据证明哪一种。因此：

- 原条目带 `arena_priority="1"` 时应原样保留；
- 不得改写为 `true` 或更高数字；
- 不得将其解释成“数值越大优先级越高”；
- 对普通新 Entry 不应无依据地批量添加。

## `colours\*.colours.darkest` 与本地化颜色
颜色定义文件位于：

```text
colours\<自定义前缀>.colours.darkest
```

每条定义固定使用 `colour:` Header：

```darkest
colour: .id "example_hex"   .rgba #58C3E0
colour: .id "example_short" .rgba #fff
colour: .id "example_rgba"  .rgba 255 255 255 255
```

- 颜色定义常用于 XML 的 `{colour_start|颜色ID}` 与 `{colour_end}`；
- 饰品稀有度也应存在同名颜色 ID；缺失时会报红字，并且好像会渲染为 Shader 报错紫色；
- 原版存在 `#RRGGBB`、`#RGB` 和四个十进制分量的写法，十六进制字母大小写无区别；
- 透明度在一般颜色文本中的通用效果仍不能外推；但辅助模式名隐藏有一个知识库编写者确认的专用例外，见下方“零宽辅助模式名”。
- 重复颜色 ID 据作者推测为后写覆盖先写，尚未专门验证；
- 非法颜色值或缺失字段的后果仍未知。

### 本地化颜色嵌套与外层恢复

知识库编写者实测确认（2026-11-08）：本地化文本允许嵌套颜色标签，以下写法合法可用：

```text
{colour_start|aaa}{colour_start|bbb}xxx{colour_end}yyy{colour_end}
```

`xxx` 使用内层 `bbb` 颜色；第一个 `{colour_end}` 结束内层颜色后，`yyy` 恢复使用外层 `aaa` 颜色；第二个 `{colour_end}` 才结束外层颜色。`aaa`、`bbb` 是示意颜色 ID，实际使用时须有相应颜色定义。

不得将颜色嵌套判为非法，也不得声称内层结束后不能恢复外层颜色。按嵌套层级配对开始与结束标签即可；这不改变已有本地化字符位计数规则，每一对颜色标签仍各计 13 个字符位。最大嵌套深度、未配对标签及无效颜色 ID 的行为不由本次实测确定。

证据：`Sources/localization_colour_nesting_20261108.json`；社区实测，Agent 未自行执行游戏测试。

### 零宽辅助模式名

> 以下为原条件下的历史方案，不是任意长度／字体保证；当前可计算的无色方案与接缝规则见技能描述专题第9—12节。

知识库编写者确认（2026-09-20）：辅助用模式名（例如充能、计数或其他不希望挤占技能描述的内部模式）通常会占据技能描述空间。可为每个模式提供 `str_skill_mode_info_<模式id>` 条目，用 `U200BZWS` 颜色把一串零宽字符隐藏：

```xml
<entry id="str_skill_mode_info_模式id"><![CDATA[{colour_start|U200BZWS} ​​​​​​​​ {colour_end}]]></entry>
```

示例中的零宽字符串左右各有一个普通空格；这两个普通空格必须保留。实际制作时将中间连续的 `​`（U+200B ZERO WIDTH SPACE）重复到足以覆盖该模式名的长度。代码块中的两个可见空格不是排版装饰：

- 模式数量为 1 时，通常不会出现额外空白行；
- 模式数量大于等于 2 时，普通空格使结果收敛为一个空白行；
- 如果删除零宽字符串两侧的普通空格，可能出现大量空行。

配套颜色定义：

```darkest
colour: .id "U200BZWS" .rgba 0 0 0 0
```

`U200BZWS` 只应作为这个辅助模式名隐藏方案的透明颜色 ID；不要把它当成所有本地化文本都能使用的通用半透明颜色。每个模式都要使用自己的 `str_skill_mode_info_<模式id>` Entry；模式 ID 必须与实际定义逐字符一致。该方案隐藏的是模式名本地化显示，不会移除模式本身、`valid_modes`、模式 Effect 或模式切换逻辑。

### 技能名称后的零宽等级数字隐藏

知识库编写者补充（2026-09-21）：不可升级技能可以在技能名称 Entry `combat_skill_name_<英雄ID>_<技能ID>` 的技能名后，紧接着放置 `U200BZWS` 透明颜色包裹的连续 U+200B `ZERO WIDTH SPACE`，把技能名称后自动渲染的等级数字挤出可见排版区域。例如：

```xml
<entry id="combat_skill_name_MEGA_pea_Trans_to_Initial"><![CDATA[还原{colour_start|U200BZWS}​​​​​​​​​​​​ {colour_end}]]></entry>
```

上例中的零宽字符数量只是示意；具体需要多少个尚未确认，但不能太少，应按实际自动等级数字和界面排版检查。**技能名与 `{colour_start|U200BZWS}` 之间不能加普通空格，零宽序列与 `{colour_end}` 之间也不能加普通空格**：普通空格会真实显示，使技能名称不再居中。

该方案只隐藏技能名称后的自动等级数字显示，不改变技能的实际等级、升级定义、技能 ID 或技能是否可升级；通常用于本来就不可升级、但界面仍会自动附加等级数字的技能。不要把本方案与辅助模式名隐藏混用：辅助模式名方案为了控制多模式空白行，另有“两侧必须保留普通空格”的规则。

配套颜色定义仍为：

```darkest

```

### 编译器扫描边界
单独运行 `localization.exe` 时，已验证它会扫描项目根目录中的：

```text
colours\*.colours.darkest
```

测试中 `colours\base.colours.darkest` 可被读取，而裸名 `colours\colours.darkest` 未被读取。孤立运行 `localization.bat` 不能自动取得游戏本体以外的项目颜色环境；应把本次 XML 实际引用的颜色定义放进可扫描的项目 `colours` 目录，或使用上传器提供的完整编译环境。



## loc 与 loc2 的覆盖优先级
发生同一本地化条目冲突时，先比较文件格式，再比较 Mod 优先级。

| 冲突双方 | 结果 |
|---|---|
| `loc` 与 `loc2` | `loc` 覆盖 `loc2`，无视双方 Mod 优先级 |
| `loc` 与 `loc` | 按 Mod 优先级决定 |
| `loc2` 与 `loc2` | 按 Mod 优先级决定 |

因此，高优先级 Mod 的 `loc2` 通常不能覆盖低优先级 Mod 或原版的同条目 `loc`。只有冲突双方均为 `loc` 或均为 `loc2` 时，才依照 Mod 加载优先级。

## 编译文件的 Workshop ID 前缀
XML 编译为 `loc2` 后，上传器生成文件通常使用 `project.xml` 的 `PublishedFileId` 作为文件名前缀。只经过 `dont_submit` 假上传、从未真正发布的 Mod 可能生成 `0_<语言名>.loc2`；无前缀的 `<语言名>.loc2` 同样属于高风险通用命名。

`0_schinese.loc2`、`schinese.loc2` 可能与其他 Mod 或原版文件同名并触发覆盖，严重时令对应语言的大量本地化消失，游戏内显示蓝色 Entry ID。尚无真实 Workshop ID 时，应为编译产物改用唯一、非 `0` 的文件名前缀；不要靠伪造 `PublishedFileId` 解决。

## Agent 检查顺序
1. 检查 XML 是否位于 `localization\*.string_table.xml`，项目扫描路径是否正确。
2. 检查是否存在 `english` 基准节点，即使它为空。
3. 检查每个 Entry ID 是固定拼接、显式引用、固定 UI ID 还是台词候选池。
4. 检查 `%s`、`%d` 等参数在各语言中的数量、类型和顺序；需要重排时使用一致的 `{?name}`。
5. 检查字面百分号是否写为 `%%`。
10. 单个字面 `%` 后是否避免直接紧邻已知冲突字符 `{`、`/`？若需要视觉紧邻，是否在中间插入 U+200B 零宽空格？
6. 检查颜色 ID 是否在本次编译器可扫描的 `colours\*.colours.darkest` 中定义。
8. 原条目若带 `arena_priority="1"，原样保留；不得擅自推广。
9. 同 ID 冲突时先比较 `loc`/`loc2` 格式，再比较 Mod 优先级。
10. 自动编译时检查控制台诊断和生成物，不得只看退出码或 `SUCCESS!`。

## ESC 术语表的编号检索（str_glossary_term_X）

按《迂回表》第143条 P2139–P2167/X2773–X2806 的历史观察，游戏在已加载的本地化文本中从 `str_glossary_term_0` 开始逐号查找。命中就将连续空号数清零；连续遇到 10 个空号就跳到下一个整千编号。从整千编号起，若最初 10 次查找全部落空，便记一次空区间；区间内有命中则清零连续空区间数。连续三个整千区间都这样落空，整个检索结束。

原表环境中已有 1–62、1001–1006、2001–2010。在没有其他 Mod 填补空号时，新增首条放在 72 仍可显示，放在 73 则因 63–72 全空而被跳过。若 3000、4000、5000 开头的十个编号均无命中，则不会查到 6000。条目能否显示取决于整套已加载文本中有哪些编号。

原表 P2173–P2194/X2814–X2844 的历史编号示例包括猩红学院 63–99、雪山 1007–1009、Voivode 101–105、堕落英雄 230–247、浊心斯卡蒂 4001–4005、拔刀剑 4009–4017、阿比盖尔威廉姆斯 5001–5030。这些编号仅反映原表记录时的占用。
