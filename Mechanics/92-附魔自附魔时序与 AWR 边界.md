本页中的“附魔 Buff”指带有 `attack_additional_effect_ids` 等攻击追加 Effect 的 Buff；“自附魔 Effect”指当前单位通过 Effect 让自己获得这类 Buff。附魔内的 Effect 仍按普通 Effect 读取 AWR、`queue false`、`queue true`，但获得附魔的时点决定本回合是否能被带出。

## 回合结束附魔与小回合 Buff 到期

知识库编写者于2026-11-11明确补充：回合结束附魔（`turn_end_additional_effect_ids`）在所讨论的技能、移动、跳过和撤退失败这些结束方式中，仅在尝试撤退且撤退失败时不触发；移动技能或跳过回合不属于该附魔的禁止触发项。与之不同，饰品回合结束 Trigger（`turn_end_additional_effects`）在移动技能、跳过回合、撤退失败时均不触发；即使先用了不结束回合的友方／进攻技能，再以跳过或移动结束回合，也不会保留前面的技能来使该Trigger触发。“与AD类似”指最终操作决定结算的这一性质，不表示所有AD边界都能套给Trigger，也不表示跳过／移动没有结束回合。来源：`Sources/turn_end_trigger_and_ad_last_operation_20261111.json`；不混同撤退失败与成功撤退。

知识库编写者于 2026-11-27 补充，战斗中仅在英雄处于可操作的行动阶段（可放技能、用道具、跳过回合或移动）时，才能尝试撤退。撤退失败会结束当前英雄的行动，失败本身不造成加压，也不会触发上述回合结束附魔或饰品 Trigger。

知识库编写者实测确认（2026-11-08）：`turn_end_additional_effect_ids` 先触发，随后才扣减小回合型 `round`／`after_turn` Buff 的持续时间。技能 `queue false` 自身获得的1回合回合结束附魔 Buff，本回合仍能触发；同时序获得的1回合抑制 Buff 也仍能制约该次附魔内容，不会先到期再放行。

同一时序内严格先后及持续时间类型组合均已测试；时序分离的施加方式未测试，“不影响结论”为知识库编写者判断。两组完整测试见[Buff持续时间专题](17-Buff持续时间类型与实际清除.md)，来源：`Sources/turn_end_additional_before_duration_20261108.json`。本条不确定附魔与其他回合结束事件的排序。

## 战斗撤退成功后的加压顺序

知识库编写者于 2026-11-27 补充，战斗撤退成功后，全队英雄按当时站位从 1 号位到 4 号位逐个结算撤退加压。如果 2 号位英雄因这次加压触发美德，美德带来的队伍减压可以插在 2 号位加压之后、3 和 4 号位加压之前。

撤退加压与美德减压均正常受到各自适用的所有修正。后续站位的英雄能否因此避免爆压，取决于其原有压力及修正后的实际加压量和减压量。

## 战斗开始附魔切模式：依赖临时通路

知识库编写者补充确认：模式的战斗开始时效果早于战斗开始附魔的战斗开始时效果。若同一模式战斗开始流程先给自身施加战斗开始附魔、再给自身施加或执行战斗开始驱散，后续模式驱散会在战斗开始附魔触发前移除该Buff，因此本次战斗开始附魔的内容不会被触发。若设计目标是驱散该 Buff，应让附魔内部自行带出针对自身的战斗开始驱散，而不要依赖模式战斗开始时效果中的后续驱散。该结论仅覆盖这两个战斗开始调用层级的相对时序，不推广到其他附魔来源或其他驱散时序。

### 模式战斗开始自附魔可扩展本次调用链

知识库编写者2026-11-09确认：模式的 `.battle_start_effect_ids` 给自身施加带有 `combat_start_additional_effect_ids` 的Buff时，这个本次新获得的战斗开始附魔内的Effect能够在**本次战斗开始流程**中触发，不必等到下一场战斗。模式战斗开始列表8个Effect引用不够用时，可以通过该附魔扩展调用链。

这不是增加原列表的8个ID上限，也不是重复同ID `mode:` 分行追加；Buff的Rule仍须生效。知识库编写者随后明确确认：**战斗开始附魔A所引出的新战斗开始附魔B，不能在本次战斗开始流程中连带触发，不能依靠新附魔在本次连带触发来无限递推。** 必须区分“模式战斗开始效果→附魔A（本次可触发）”与“附魔A→附魔B（B本次不连带触发）”。这不否定借A扩展模式8条引用不足的方案；不推断B在下一场战斗是否触发，也不补造底层原因。若内部Effect要切模式，仍须满足下述临时通路及召唤／自加动／生命反馈的特殊要求；普通附魔扩展本身不能绕过切模式要求。来源：`Sources/spawn_sharing_and_mode_start_enchantment_20261109.json` / `MODE-START-ENCHANT-01`、`MODE-START-ENCHANT-02`；非本轮Agent游戏测试。

知识库编写者实测补充（2026-11-08）：先在模式战斗开始效果中完成“召唤 size-0 → 该 size-0 在自身 Spawn 按既有要求自加行动点 → 触发自身生命反馈并引出 Effect”的流程，打通底层原因未知的通路。生命反馈输出什么无所谓，不必执行切模式。通路已打通时，战斗开始附魔 `combat_start_additional_effect_ids` 可以直接引出切模式；未打通时，战斗开始附魔中无论如何迂回都会在战斗开始崩溃。

通路持续到存档重启，不是以游戏程序重启为界；存档重启后必须重新打通。所有可能在战斗开始切模式的模式，都必须配置前置流程。不能把此前成功切模式当作该状态可稳定留存的证明。

自加行动点的既有限制不变，尤其不能使用 `.bonus_action_next_turn true` 或天然回合／召唤参数替代。推荐直接在模式战斗开始的既有流程里完成切模式，把条件控制交给其他地方；附魔不能简化这项前置需求。完整限制见[英雄战斗开始切模式](28-spawn、生命反馈与size0执行链.md)，来源：`Sources/combat_start_mode_switch_path_20261108.json`。不据此推定其他调用来源均可直接切模式。

## 模式战斗开始 Effect 按列表序号跨英雄执行

Yuri 于 2026-11-27 的实测经 Cathelia 转述。四名英雄 A、B、C、D 各自在一个模式下配置 `.battle_start_effect_ids`，列表各有 `x`、`y`、`z` 三个引用。观察到先执行四名英雄的 `x`，再执行四名英雄的 `y`，最后执行四名英雄的 `z`。

`A.x → B.x → C.x → D.x → A.y → B.y → C.y → D.y → A.z → B.z → C.z → D.z`

测试把 `target_enemy_random` 标记放在 `x`，把用于防止战斗开始切模式崩溃的 size-0 召唤放在 `y`，多次测试均未出现标记落空。调换两者后会出现落空，最初也曾观察到标记落到这个 size-0 上。`.can_apply_on_death false .can_apply_on_corpse false` 只会在最终目标处于死而不僵时拦住 Effect 实际生效。Effect 仍可进入调用流程，随机选取仍可抽到这个单位，所以双 `false` 无法用来避免标记落空。若这里需要避开同一开场流程召出的 size-0，可把随机标记安排在更早的列表序号，并检查其他英雄的召唤序号。

执行顺序可用类似 AOE 的逐序号交错来理解。英雄之间的遍历顺序由什么决定、不同长度列表如何处理、引擎为何采用这种调度仍未确认。

## 同一 Buff 承载多种附魔（判断，尚未实测）

知识库编写者判断（2026-11-08，非实测确认）：同一个 Buff 理应可以同时带有不同类型的附魔，例如同时填写 `attack_additional_effect_ids`（攻击附魔）与 `friendly_additional_effect_ids`（友方技能附魔）。不应默认把它们视为互斥字段，或仅因类型不同就强制拆成两个 Buff。

各类型仍分别遵循各自的触发条件、时序和目标语义；共用一个 Buff 不会使友方技能附魔拥有独立 AWR 时序。此判断不能扩展为任意组合已实测兼容；跨类型同时触发时的调用顺序、去重及概率共享均不由本条确定。

来源：`Sources/buff_multiple_additional_effect_types_20261108.json`；证据等级为知识库编写者判断／待验证，Agent 未自行执行游戏测试。

## `.buff_ids` 先检查最终参数数量

每条实际 Effect 的 `.buff_ids` 最终解析参数最多 `8` 个。引号内含空格的一个 Buff ID 仍算一个参数；计数按解析后的参数数量，不按视觉行数。

- 超过 `8` 个时，必须使用合法分行拆分，或直接拆成两个不同 Effect；每个实际 `.buff_ids` 参数串都重新检查并保持不超过 `8` 个。
- 使用同名 Effect 分行时，必须核对该字段的逻辑合并方式；无法确认拆分后仍是独立实际调用时，优先使用两个不同 Effect ID。
- 不要把超过 `8` 个 Buff ID 继续塞在同一个实际 `.buff_ids` 调用中，不能依赖截断后的结果。

## 友方技能附魔没有独立 AWR 时序

知识库编写者2026-11-06明确补充：友方技能附魔（`friendly_additional_effect_ids`）与友方技能、友方技能饰品 Trigger 一样，不存在独立 AWR 时序；写成 AWR（`.apply_with_result true .queue false`）时，视同普通 `queue false`，不是 Effect 不执行。因此不能用下文攻击自附魔的 AWR 前置规则推导友方技能附魔能够提前结算。来源：`Sources/friendly_enchantment_no_awr_20261106.json`；Agent未自行运行游戏测试。

## 自附魔要到下一回合才生效

如果设计不要求获得附魔的这一回合就让附魔内容生效，而是从下一回合开始生效，则给自己施加附魔的 Effect 必须位于普通 `queue false` 或 `queue true`，不能位于 AWR。

这条限制针对“附魔获得时点”。附魔 Buff 的 `attack_additional_effect_ids` 在之后的攻击调用中仍须按攻击命中/未命中、来源层和附魔 Effect 自身时序单独核对。

## 自附魔要在当前回合生效

知识库编写者实测确认，并于 2026-11-05 明确纠正：**AWR 自附魔一定能正常引出附魔内的 `queue false` / `queue true` 时序，前提是附魔 Buff 的 Rule 生效。** 自附魔在 AWR 时序获得附魔，使 Buff 在 AWR 结束前已经存在，即可参与本次攻击后续的 queue 调用；这不是“能否加入已形成队列尚未确认”的情况。

这里确认的是 AWR 获得附魔后引出后续 queue 时序，不是要求新附魔内的 AWR Effect 再赶上本次 AWR。不得擅自添加后一种需求，也不得用下方队列冻结推测把已确认的 queue 调用降级为可能不可用。正常引出仍须区别于 Effect 最终通过概率、抗性、目标等检查并产生结果。

存在一个 size-0 例外路径：如果 AWR 召唤 size-0，再由该 size-0 定向给英雄施加附魔，要求召唤 Effect 位于 AWR；给英雄上附魔的 Effect 本身不必再写 AWR，只要它在 AWR 结束前完成即可。其他类似“前置 Effect 在 AWR 内带出实际附魔”的调用也按“获得附魔必须早于 AWR 结束”核对，不能只看最后一条施加附魔的 Effect 是否写了 AWR。

## 同阶段自附魔的调用边界与队列冻结推测

知识库编写者于 2026-11-05 明确说明以下调用边界：

- 在普通 `queue false` 或 `queue true` 时序自附魔，不能在本次攻击中引出新附魔内的 queue 时序 Effect；不能靠在 `queue false` 安装附魔来赶上本次 `queue true`。
- 在 AWR 时序自附魔，不能引出新附魔内的本次 AWR 时序 Effect。
- 在 AWR 时序自附魔，可以正常引出新附魔内本次攻击后续的 `queue false` / `queue true` Effect，前提是附魔 Buff 的 Rule 生效。

下述“冻结”是用于解释前两条同阶段无法追加调用的内部模型推测；不能用它否定第三条。调用边界与解释模型的证据等级须分开记录。

知识库编写者补充（2026-09-22，明确标为个人推测，未通过反编译确认）：同一个发起者可能在技能开始时先形成 AWR Effect 队列；在本次 AWR 时序结束前，该队列不再增加或减少。直伤结算后再形成包含 `queue false` 和 `queue true` 的后续队列；在 `queue true` 时序结束前，该队列同样不再增加或减少。

该模型可以解释以下现象，但不能当作绝对引擎事实：

- 同一个发起者在 `queue false` 或 `queue true` 驱散附魔，不一定阻止附魔内排在后面的 Effect **发生**；AWR 内也应按同一模型保留这个可能性；
- 该模型中的后续 queue 队列在直伤结算后形成；AWR 自附魔已在此前完成。因此该推测不妨碍 AWR 自附魔引出附魔内的 queue 时序，不能用于质疑这一已确认行为；
- 召唤出的 size0 形成新的 Effect 发起者，因此它拥有自己的队列；新发起者的 Effect 可以执行，不与“同一发起者队列不增不减”的推测冲突。

必须区分“发生”和“生效”：

- **发生**：该 Effect 是否被带出、进入并出现在对应时序队列中；
- **生效**：该 Effect 在实时结算时是否通过概率、抗性、目标、死亡状态等检查并产生实际结果。

驱散附魔可能无法阻止已经进入队列的 Effect 发生，但仍可能影响某些 Effect 的生效。例如腐蚀的实际施加仍会在结算时重新经过腐蚀概率与腐蚀抗性检查，因此“Effect 发生”不等于“腐蚀一定成功”。

该队列模型目前是知识库编写者的逻辑推测，不是反编译确认的绝对结果；不得把它外推到不同发起者、不同调用来源或未核对的特殊时序。

## 附魔施加新附魔时的同次触发边界

知识库编写者于 2026-11-27 提出高把握推测：附魔 A 可以施加附魔 B，但 B 不会补入已经触发的同类附魔结算。B 最早可在下一次符合条件的触发机会结算，前提是其 Buff 仍在且 Rule 生效。例如，回合结束附魔 A 施加新的回合结束附魔 B，推测 B 最早在其持有者的下一次有效回合结束时触发。轮次结束等其他附魔的同次连带触发边界也暂按此推测理解。

- **攻击附魔与回合开始附魔有实测依据。** 攻击附魔按上节的阶段边界处理。AWR 阶段施加的新攻击附魔仍可参与本次攻击后续的 `queue false`／`queue true` 结算。回合开始附魔引出的新回合开始附魔可跨回合递推，见下文。
- **战斗开始附魔已有同次不连带触发的历史确认。** 2026-11-27 的证据分级只把攻击和回合开始列为有实测的类型，因此战斗开始保留为既有确认记录，实测状态待核对。模式 `battle_start_effect_ids` 的先行施加路径仍按本篇对应章节处理。

## 回合开始附魔结束后的表现与 Update 推测

知识库编写者于2026-11-13补充以下表现：在回合开始附魔（`turn_start_additional_effect_ids`）内对自身切换模式，`combat` 动画可以正常变为切换后模式的动画；该回合开始附魔内召唤的 size0 也不会卡鼠标。

知识库编写者据此推测：**回合开始附魔结束时疑似有一次 Update。** 两项表现与其解释分开记录；Update 的发生、精确插入点及次数尚未独立确认，不能把“疑似有一次”改成已确定发生一次。这里的 Update 沿用[统一的游戏状态更新机制](01-effect执行模型.md#update-的统一含义)，不另造独立机制；本次没有补充其对其他 Buff 清除或其他事件的结果。

范围限于上述回合开始附魔调用，战斗开始附魔、攻击附魔等调用的 Update 情况须按各自记录核对。该观察不撤回[size0在其他调用中的鼠标遮挡记录](60-size0实际位置与定身遮挡.md)，也不意味着本次新获得的回合开始附魔能在当前回合连带触发；后者仍按下一节的跨回合递推边界处理。与愈合及 `act_out` 的相对时序仍按[Buff持续时间专题](17-Buff持续时间类型与实际清除.md)分别核对，不由本条补定。

## 回合开始附魔的跨回合递推与修正后的无限式

知识库编写者于2026-11-10紧急更正：**回合开始附魔A引出的新回合开始附魔B，不能在当前回合触发。** 2026-11-06所记“新附魔同回合连带触发、A/B互引造成同回合死循环”的结论及据此建立的旧Kaze无限式基础已撤回，不能再作为可用机制或风险依据；不补造底层引擎原因。

仍可进行跨回合递推：第一回合A触发并引出B，第二回合B触发并引出下一阶段，以此类推；须保证相应Buff存续且Rule生效。若不希望旧阶段重复执行，可按设计用ID定向驱散清理。这里不是让新获得的B在A触发的同一回合立即执行。

若要在同一个回合内实现条件性递推／递归式效果，应在附魔内部预先展开大量分支，以 `effect_chance` 控制特定分支是否开启；这是预写Effect链的条件推进，不是新回合开始附魔同回合递归触发，内部列表可能较臃肿，不代表真实无限调用或没有容量限制。逐项核对Effect时序、概率门作用对象及必要的清理。

## 阻止附魔内容发生时的驱散顺序与大时序

知识库编写者补充（2026-09-22）：如果 AWR 自附魔的设计目标是在特定条件下阻止附魔内容发生，那么用于阻止附魔的驱散必须满足两层要求：

1. **严格时序**：驱散必须写在自附魔之后；
2. **大时序**：驱散必须属于 AWR 范围。

这里的“大时序属于 AWR”不等于驱散 Effect 的定义行必须固定写某个 `.awr` 字段。该 Effect 到底是否需要声明 AWR，取决于它在哪里被调用以及调用方如何把它放入 AWR；必须按实际调用位置核对，不能把调用时序和 Effect 定义字段混为一谈。

按上一节的队列冻结推测，顺序正确也只能说明它在同一发起者的 AWR 阶段中位于自附魔之后；是否能阻止某条附魔 Effect **发生**，仍取决于该 Effect 是否已经进入本次 AWR 队列。即使 Effect 已经发生，驱散仍可能影响它的实时**生效**，例如概率、抗性、目标或死亡检查；不得把“驱散在后”直接写成“后续所有附魔 Effect 都不会发生”。

## 一次性 AWR 自附魔的清理时序

如果 AWR 自附魔只是为了在特定条件下触发一次，类似饰品攻击 Trigger，而不是让附魔长期存在：

- 清理该附魔的 Effect 仍应放在 `queue true`；
- 但按上述“同一发起者队列冻结”推测，清理在 AWR 或 `queue false` 不应被写成“必定阻止后续附魔 Effect 发生”；后续 Effect 可能已经进入队列。它们是否实际生效，还要按各自的实时概率、抗性、目标与死亡检查判断；
- 清理写在 `queue false` 时，AOE 技能中仍会出现已知问题，不能作为常规清理位置；
- 因此，`queue true` 是一次性清理的推荐时序，但不等于可以绝对保证此前已入队的附魔内容不发生。

这里的清理时序是一次性附魔的组成部分，不能只按“获得 Buff 后尽快清除”的直觉移动到 AWR 或 `queue false`。发生/生效的区分和队列冻结目前仍属于推测边界。

## 当前回合生效且附魔内需要 AWR 的替代写法

如果既要求当前回合生效，又要求附魔内部的 AWR Effect 执行，使用：

- `skill_instant` 引出该 Buff；
- 为该 Buff 显式定义一个非 `bsrc_instantSkill` 的 Buff 源；
- 该写法只在技能调用中有效，不能直接推广到饰品、spawn、hp_reaction 或其他调用方；
- 必须使用前置驱散，先清除旧的附魔和/或自身，防止同一次技能或重复点击导致残留与重复；
- 由于非 `bsrc_instantSkill` Buff 有残留风险，其他所有技能也必须加入 `skill_instant` 引出的清理逻辑来驱散该附魔。推荐清理 Effect 同时驱散附魔 Buff 和清理器自身。

这条方案仍须遵守 `skill_instant` 的目标、两次施加、点击重复、AOE 重复和生命周期限制；它不是把普通长效附魔安全地改成任意调用方都可用的即时机制。

## 审查顺序

1. 先数 `.buff_ids` 的最终解析参数，确认没有超过 `8`；
2. 确定附魔需要本回合生效还是下回合生效；
3. 若下回合生效，自附魔只能放普通 `queue false` / `queue true`；
4. 若本回合生效，检查附魔获得是否在 AWR 结束前完成；
5. 区分三个调用边界：queue 自附魔不能引出本次附魔内 queue；AWR 自附魔不能引出本次附魔内 AWR，但 Rule 生效时一定能引出后续 queue。队列冻结只是对同阶段不能追加调用的解释模型；
6. 若设计目标是阻止附魔内容发生，检查驱散严格位于自附魔之后，且从调用方大时序看属于 AWR；不要据此要求定义行固定写 `.awr`；
7. 一次性 AWR 附魔按 `queue true` 清理，降低 AOE 清理问题，但不要声称它绝对阻止已入队附魔 Effect 的发生；
8. 只有技能内“当前回合 + 附魔内 AWR”需求才考虑 `skill_instant + 非 skill_instant Buff 源`，并补齐前置驱散和其他技能的清理。
