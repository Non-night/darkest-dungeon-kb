## 1. 四种“长度”必须分开

技能文本至少有四个不同量：

1. **源文本长度**：XML／JSON 中写下的字符，包括 `{colour_start|…}`、`%d`、`%%` 等语法。
2. **消费者保留的 UTF-8 字节**：本地化编译、数值替换、包装、局部裁切和拼接后的数据。这才是本文各上限的单位，不含结尾 NUL。
3. **解码后的字符序列**：截在多字节字符内部时，可能与源字符完全不同。
4. **字形宽度及行数**：由实际字体、advance、换行及布局决定。字节数相同不保证同宽，同宽不保证等字节。

|内容|本研究路径中的费用|限定|
|---|---:|---|
|ASCII字母、数字、符号、半角SPACE|每个1字节|不是全角空格|
|普通汉字|本次样本每个3字节|Unicode并非所有码点都3字节|
|U+200B／U+200C／U+200D／U+2060／U+FEFF|每个3字节|相同字节长度不代表相同解码接缝／字形|
|DEL U+007F|1字节|当前活动字体路径跳过，非跨字体保证|
|源Entry内CRLF|2字节|`\r\n`，与原生LF分开|
|原生拼接LF|1字节|即使后续被残片解码吞掉，仍已占字节|
|编译后的颜色头／尾|9／4字节|完整一对13；不是源花括号标签的字符串长度|
|`%d`|替换后的带符号整数长度|不按源占位符2字节固定计费|
|`%%`|取决于具体格式化消费者|经过本次整数格式器时输出一个`%`；不能对所有Entry统一折半|

例如“自身：”是三个三字节字符，9字节。若后面再接一个原生LF，则共10。带一对颜色的“增益目标：”为 `5×3+13=28`，再加LF为29。可见字符只有五个，存储费用却远多于五。

本篇中“字节”“字符位”“slots”均按上述保留字节理解。历史记录中的“字数”如未明确单位，不能直接代入公式。证据：F01—F05、F09—F13；附录证据账本。

## 2. 容量不是单一上限，而是一条截断流水线

|阶段／消费者|最大保留字节，不含NUL|已确认的含义|
|---|---:|---|
|技能面板的一个模式名|63|先独立裁切，再与其他段拼接|
|Effect自身`.description_tooltip_id`正文|255|公共和差分中的单项都先受此限|
|现代Buff自定义应用描述项|255|具名路径为 `(P[:255]+SPACE)[:255]`；P是格式化后的自定义正文|
|旧`upgrade_discount`技能正文|127，然后追加SPACE|该127阶段先于外层包装；不等同现代255|
|旧`quirk_tag_evolution_duration`技能正文|127，然后追加SPACE|仅本次具名技能消费者，不是所有“进化类”功能统一127|
|一个模式差分的聚合正文|255|Effect列表内部先构造，再复制／裁切到255|
|公共正文|511|包括进入此块的原生统计／效果／目标头／连接符|
|最终拼接正文|511|公共块与模式部分合并后**再裁一次**|

静态结构中部分缓冲大小为64／256／512，含结尾NUL；因此不能将“256缓冲”写成“256字节可见正文”。对旧载体，实机确认的是保留127，不据此凭空推断未绑定分支的分配大小。

可用下面的概念模型理解，实际分类重排、空段和标题条件还要按后文计算：

```text
本地化Entry → 数值／引用名称格式化 → 单项裁切
           → Effect列表分类、连接、标题 → 公共块裁到511
                                       → 模式差分块裁到255
模式名独立裁到63

英雄面板：公共块 + 按本次有效顺序生成的模式名／差分 → 最终裁到511
战斗提示：公共块 + 当前实际模式差分                   → 最终裁到511
```

模式的显示顺序必须以当前实际加载结果核对，不能只凭源码排列推断所有 Info 合并情况。单模式、多模式以及复用旧模式的加载异常另见第16节；不能借偶发缺段隐藏文字。

**“差分比公共少一半”只能作为现象描述。**确认的是差分255、公共511及其各自的包装，不是任何中文描述都严格少一半。公共单个Effect仍有255局部限制；公共聚合则还可以包含多个项目。其他人所说“公共eff先顶满，变成子模式后减半”，与这条流水线相容，但不能取代逐层计数。

仅从输出末尾消失，不能判断截在哪层。一个自定义Effect本身超过255时，即使技能总共只有300字节，它也会先丢字。多个Effect合计超过模式255时，每个单项未满也可能在模式阶段丢失。证据：F01、F03—F04、F43、F54、F58、F62—F63。

## 3. 扩大上限与在上限内省字节

在已读、已复现的当前技能正文调用链中，最终正文最多511字节。没有发现通过增加`.valid_modes`、增加虚假模式、改Effect／Buff载体、condense、吞换行、不可见字形或透明颜色扩大此阶段的办法。

以下方法有实际用途，但应记录为**节省包装或绕过更早的局部瓶颈**：

- 将一个过长自定义Effect拆成多个，能绕过单项255；若仍在同一个模式内，模式聚合255照旧。
- 用Effect自身自定义代替已测现代instant Buff自定义，短文本通常少一个尾SPACE；不是多出一套正文容量。
- condense可能省掉专用增益／减益头，也可能因` / `比LF更长而增加费用，需计算净变化。
- 删除确实不需要的自动说明、减少重复文字或把固定说明移到面板专属假模式，可以重新分配预算。
- 自定义字体将一个码点画成图标，改变的是字形的信息量／宽度；本研究未修改字体，也没有证明引擎容量增长。

若战斗内必须显示实际模式差分，则公共块不能先填满511。以完全相同的拼接条件为前提，至少应留出 `1个LF + 最长实际差分` 的空间；若某消费者另加前缀或分隔，应计入实际值。不能用公共无色零宽“全部遮掉”，再宣称战斗差分可恢复。

## 4. 自定义文本载体：写法、包装与选择

### 4.1 Effect自身自定义

技能 Effect 描述未开启 `condense`（N=0）时，纯文本说明可用普通 `.target target` Effect 加 `.description_tooltip_id`，省掉独立目标标题。开启 `condense` 后的标题及排列待确认。

已验证的字段是Effect对象的`.description_tooltip_id "Entry_ID"`。它与Buff JSON的同名字段是不同消费者。参考摘录：

```text
effect: .name "TXT_Line" .target "performer" .chance 100% .description_tooltip_id "effect_tooltip_TXT_Line"
```

```xml
<entry id="effect_tooltip_TXT_Line"><![CDATA[自定义说明]]></entry>
```

这是**字段／Entry摘录**，不声称仅这两行构成完整可运行Mod。应放入已有合法Effect资源和本地化语言节点，保留原技能与实际效果所需定义。不要为了显示文本随意改变施加目标、时序或机械效果。

当前路径直接使用此自定义正文，项目局部255。其提前返回和`.has_description`关系与Buff载体不同：已有知识库记录Effect自身自定义即使`.has_description false`仍可显示，不能将Buff载体“必须保留描述”的规则机械移植到它。因此，**需要隐藏此文本时，不能只检查`.has_description false`是否写上**，还要确认实际消费者。

本研究没有建立Effect自身自定义与现代Buff完全相同的`%d`数值契约；纯文本可以复用，Buff的amount、缩放与堆叠规则不能直接搬到Effect Entry。

知识库编写者实测，技能引用的 Effect 使用自身的 `.description_tooltip_id` 时，即使该 Effect 以 `.target target` 施加减益，自定义描述也不会并入技能描述的“减益目标”标题下。



`.tag 1 .target target` 的原生标记行也是省略独立目标标题的例子。公共标记行和模式差分说明的相对位置按各自的拼接位置核对。

### 4.2 现代Buff自定义

具名试验使用：`stat_type=combat_stat_add`、`stat_sub_type=attack_rating`，`rule_type=always`、`is_false_rule=false`、`rule_data.float=0`、`rule_data.string=""`，Buff的`description_tooltip_id`指向独立Entry；引用Effect为`performer`、`skill_instant=true`、`chance=100%`。

```json
{
  "id": "TXT_Buff",
  "stat_type": "combat_stat_add",
  "stat_sub_type": "attack_rating",
  "amount": 0.05,
  "has_description": true,
  "rule_type": "always",
  "is_false_rule": false,
  "rule_data": {"float": 0, "string": ""},
  "description_tooltip_id": "buff_tooltip_TXT_Buff"
}
```

此为**描述字段摘录**，省略持续时间、来源、清理等字段；不能作为长期Buff的完整模板。精确完整测试定义见附录。`skill_instant`有真实施加／重复／生命周期影响，不是无副作用的排版开关。尤其不要把只读描述试验等同于相关instant目标组合安全可施放；既有知识库的危险目标限制继续有效。

在上述相同类别的纯文本路径，Effect自定义P和现代Buff自定义P的区别为：

```text
Effect项 = P[:255]
Buff项   = (P[:255] + SPACE)[:255]
```

`effect_tooltip_format`的包装包含正文与持续／附加说明之间的空格。即使后一个字段为空，前面这个SPACE仍可留下。

|格式化P长度|Effect项|现代Buff项|差额|
|---:|---:|---:|---:|
|10|10|11|1个尾SPACE|
|254|254|255|1个尾SPACE|
|255|255|255|SPACE已被裁掉，0|
|256|255|255|正文均先受局部裁切|

差额**不来自Effect前后各多一个换行**。同类别外部连接由同一追加器产生。改变目标、概率、Rule、持续或instant状态，会另加包装，不能继续只比较1字节。普通非instant Buff还可能进入带色专用目标桶。

### 4.3 旧打折与进化写法

本次技能路径分别测试`upgrade_discount`与`quirk_tag_evolution_duration`，不能合写为“旧Buff”。两者在数值替换后各保留127，再追加Buff尾SPACE；外层Rule等还有自己的阶段。

两个具名旧入口均通过`stat_sub_type`构造本地化键：打折为`buff_stat_tooltip_upgrade_discount_<子类型>`，进化为`buff_stat_tooltip_quirk_tag_evolution_duration_<子类型>`。例如本次`DLC_T8`使用后一个前缀。两个完整具名测试定义与引用见附录B的carrier14／carcond14；这些键是属性正文入口，不是Rule名称入口。

知识库编写者报告旧版本饰品曾测得“单Buff128”，此处只能作为历史来源。技能127保留+SPACE与该报告有可能口径不同，也可能消费者不同；**当前饰品还没有开始验证**。

## 5. 数值、Rule和引用名称的格式化

### 5.1 数字费用与取值来源

现代Buff的具名`combat_stat_add.attack_rating`自定义使用一个`%d`和正确转义的`%%`时：

|载体／属性|本次显示规律|例子|
|---|---|---|
|现代Buff自定义，attack_rating|约为`roundf(100×amount)`后整数显示|0.126→13，-0.125→-13|
|upgrade_discount，私有子类型|本次为反号缩放`round(-100×amount)`|0.126→-13，-0.125→13|
|quirk_tag_evolution_duration，私有子类型|本次非半值样本符合`round(amount)`|1.9→2，-1.9→-2，0.51→1|

现代数值格式器静态确认查找字面`%d`，按属性缩放／符号处理后`roundf`转整数；没有`%d`走有界复制。不能由此宣称支持任意printf参数、多参数、`%f`或位置参数。进化精确半值没有单独隔离，不能仅靠近似样本宣称所有浮点边界已验证。

本次技能`.buff_ids`应用描述按ID读**全局Buff定义的amount**，不读取角色已持有该Buff的合计值。实际叠层使精准0→9→18→0，但两个观察技能的文本始终`APP_9|`；静态路径也与此一致。不要用“状态栏会合并显示”推断技能描述会显示当前叠层。角色状态栏、命中预览、饰品应另论。

数值改变后的符号和位数照实占字节。`9`→`10`增1，`100`→`-100`增1。局部容量在数值展开后施加：现代路径源253字节可展开到254并保留尾SPACE；展开到255时SPACE就可能被裁掉。旧载体展开到128仍只保留127，之后再加SPACE。

证据：F02、F04、F34、F42、F52—F53；numformat14／numround14／numedge14。

### 5.2 常规Rule不是固定“条件税”

普通Buff先生成属性正文，再按确切Rule模板插入属性、数值／名称与字面内容。费用要按**最终展开的模板**计算，不能把`%s`源占位符当成固定2字节。

本研究清单中的55种Rule，均有具名正向和`is_false_rule=true`面板样本；这不等于任意rule_data、数值、名称、玩法激活、战斗状态都完成。附录A按`rule_type / rule_data.float / rule_data.string / is_false_rule`逐项记录，避免“测过buff的rule”这种无法复用的描述。

|例子|应如何记录|
|---|---|
|`hpabove`／`hpbelow`|百分数格式化后的位数；本次5%、50%、100%每多一位消耗1|
|`meleeonly`／`rangedonly`|固定文字及其颜色对；不能只数“近战”二字|
|`skill`取反|本次呈“非技能甲: +5精准”，是模板结构变化，不是普通尾缀；有两层颜色共26字节|
|`torch_setting`|取原生属性正文和所引用名称共同进入格式化结果；名称可承载自定义内容，但全局模板覆盖影响其他内容|
|`monsterType`|本次多出“对”等字面包装，名称可用预算比同长度torch样本少3；不是独立固定名称容量|

三个取反模板缺失样本需特别保留：`ondeathsdoorenter_false`、`torch_setting_false`、`walking_backwards_false`显示整个缺失模板的带色fallback，部分连原属性行也不显示。**缺本地化不证明Rule的玩法判定不支持**；fallback长度也不是正常说明费用。

### 5.3 可自定义的Rule入口和局部限制

`torch_setting`与`monsterType`具名路径已把格式化结果254／255／256隔离为保留254／255／255。它们的属性正文、字面包装和名称**共享255**：

|具名组合|名称可保留上限|计算口径|
|---|---:|---|
|torch，原生属性正文8|246|255-8-SPACE1|
|monsterType，同原生正文8|243|再减“对”3|
|torch，自定义旧载体正文5|249|255-5-SPACE1|

因此不能称“torch名称固定246”。旧载体127还会先截一次，再与Rule名称共用255。现代Buff自定义覆盖在指定样本里绕过了原生属性／Rule的可见包装，不能同时把两套正文累加。

`attacking_monster_type`、`monster_type_count_min`、`has_buff`另有新旧键对照：旧键本地覆盖未反映，新私有键300字节能进入255格式器，证明原现象不是简单“名称太长被截没”。它们分别有“受到／处于”15字节或“当场上”18字节前缀，名称余量不同；活动覆盖赢家尚未追到最终来源。

这些入口可用于兼容性设计，但会带条件语义、模板包装、全局本地化冲突和玩法成本，不能把它们当成无副作用的第二份技能正文。仅为了纯文本，在可用的版本中优先比较Effect自身自定义和现代Buff自定义。

## 6. 不同目标如何影响描述

必须区分技能Info的`.target`与Effect的`.target`。前者包含敌我、打点及`~`等旗标；后者决定Effect选取／分类目标。二者可能共同影响措辞、概率和目标标题，不能混记为“target”。

静态枚举21种Effect.target，其中20种有具名技能面板样本；`this_trinket`的真实饰品发起路径按知识库编写者边界延后。技能里显示`other_trinket`的目标头，不代表饰品触发已经实测。

目标费用来自最终生成的**标题+颜色+冒号／标点+连接符**；不存在统一固定字节税。标题有时只出现一次，有时成为逐行前缀；condense路径又可能跳过。参考：

|描述组成|本次费用|说明|
|---|---:|---|
|普通自身头`自身：`后接LF|10|9+1|
|普通队伍／其他队友等头|按真实Entry|标题长度、翻译和颜色各异|
|带色`增益目标：`后接LF|29|15+13+1|
|普通`target`桶|本次可无标题|不代表普通非折叠上Buff也无标题|
|缺Entry标题|fallback字面键+色标+LF|不是固定目标费，补充Entry后会改变|

目标头本地化控制显示了严格按输出长度变化：`K`费用2、`KK`3、`中`4、` 中`5、`中 `5、`H CRLF H`5。它们包括一个外接LF。空Entry样本无目标头行、费用0；一个SPACE样本费用2并留空行。故“空字符串”和“一个空格”不能互换。

局部标题样本可以超过255，证明目标头不必与单Effect文本共用那一项255。但“标题另有511限制”与“只受最终511”在该组未分离，不能声称目标标题可以任意长。

普通Buff的有益／有害分类不是只看amount正负；应按属性含义及引擎分类核对。N=0时可能分入“增益自身／减益自身／增益目标／减益目标”等带色桶；N非零改用普通目标桶。完整21类枚举、缺失键与本地化控制见附录A。

技能打点串中的`~`还有两个已绑定的描述作用。公共Effect列表读取其`0x100`旗标：无`~`时输出独立类别标题，有`~`时可改为每桶首项／新行的行内标题加SPACE；斜杠续接可跳过该前缀。模式差分的对应调用参数固定false，不沿用公共的`~`。所以相同Effect从公共移进模式后，标题和连接费用不保证不变。

`dotHpHeal 3 / duration 2`有单变量对照：公共`~`会选party措辞，比单体项多17字节（单体30、party47，含该项颜色和尾SPACE）；Effect.target performer本身不是party选择源，它另加自身头。模式差分即使所属技能有`~`也回到单体措辞。敌向100%概率后缀另31，友向100%在该族省略；50%后缀30。不能从技能阵营推断所有效果的概率规则相同。证据：F09、F60；nativegapD10。

## 8. condense：哪些字段控制什么

### 8.1 参数的实际写入规则

|字段|当前字段应用函数的动作|
|---|---|
|`.condensed_tooltip_effects true`|把内部每行项数N写为8|
|`.condensed_tooltip_effects false`|此分支不写N；**不是清零**|
|省略上述字段|此分支同样不写N|
|`.condensed_tooltip_effects_per_line N`|后应用；若存在，覆盖前面的N，包括true写入的8|
|`.condensed_tooltip_type`|独立布尔字段|
|`.condensed_tooltip_stats`|另一个独立布尔字段|

需要N=0时，应明确核对最终对象中N是否为0；在相关Info路径可显式给`.condensed_tooltip_effects_per_line 0`。不能只写effects false，就断言此前值已消失。负数能被字段函数写入不代表安全或推荐。Info／Art、重复行及模式声明的整体加载顺序不能只由这个函数推出。

N=1和N=0在单桶相邻项目都可能用LF，但**Buff分类仍不同**：判断专用Buff桶的是N是否为0。只凭画面“还是一项一行”不能判断condense没开。

### 8.2 项目展开、39桶、共享计数器

Effect列表按源顺序展开，每生成一个描述项调用追加器。一个Effect含多个可见Buff时，可能生成多项；一条自定义正文内部有多行，不因此变成多项。随后进入39个分类桶，最后按分类优先级重排输出。

所有桶共用一个计数器，初始0。追加到已有非空文本的桶时才计数+1；首项不计数、不先放分隔。N=0用LF；N非零时，通常计数是N的倍数用LF，否则用` / `。新行／首项路径还可能写标题前缀，斜杠路径可跳过它。

因此N不是最终物理行硬上限。例如源顺序`S1,O1,S2,O2,S3,O3`、N=2，S2／S3对应计数1／3而用斜杠，O2／O3对应2／4而换行；重排后自身三项可同一行，另一桶逐行。对调源顺序会改变哪组折叠。

### 8.3 行数少不保证更省字节

同一个桶有m项、无其他桶干扰／额外前缀时：

```text
N=0：分隔开销 = m-1
N>0：LF数=floor((m-1)/N)
      分隔开销 = 3*(m-1) - 2*floor((m-1)/N)
```

六项时N=0的分隔共5字节；N=2为11；N=8为15。每个LF1换成` / `3，多2。多桶交错要模拟共享计数，不能各自独立套公式。

但普通Buff在N非零时又可能省掉有益／有害专用头。例如morefamily14七组具名配对各净省54：去掉两组`28+LF1`省58，两处LF改斜杠多4，净省54。**54是这组结构的净值，不是condense常数**。

Effect自定义、普通Buff自定义、instant Buff、打折、进化、原生DOT／治疗等已分开取样。原生DOT含内部CRLF、概率或不同目标措辞；不能只数顶层Effect数。项目255、模式255、最终511均不因折叠改变。完整样本与原生分隔记录见附录B。

## 9. 零宽“吞换行”和末尾`!`的实际机制

### 9.1 截断是按字节，不保护UTF-8码点

当前解码器不校验后续字节是否为合法UTF-8续字节，因而局部裁切留下的残片能把下一段的LF或文字吞进同一次解码：

|拼接后的原始字节|解码结果|影响|
|---|---|---|
|`E2 80 0A`|U+200A|原本LF被消费，不再作为换行|
|`E2 0A 20`|U+22A0|LF和下一SPACE都被消费；当前字体可能有可见图形|
|`EF 0A 20`|U+F2A0|与上一种字节同长但码点不同，可能变成图标|
|最终末尾只剩三字节字符的1／2字节|字面`!`|后面不再有足够输入补完|

U+200B源字节为`E2 80 8B`。模式名63或Effect255恰裁掉最后的8B，留下`E2 80`，再接原生LF，就产生第一种接缝。“1+2分裂”要记录为具体截点及剩余字节，不能只说“零宽被截断”。

这解释了下一行文字可以接到上一行、也解释了为何FEFF不能随意替换U200B。若截掉的不止LF，下一字符的开头也可能参与解码，必须用最终字节重放。

### 9.2 吞掉换行没有减少总量

`E2 80 LF`三个字节已经写入缓冲，后续解码把它当成一个码点，**不会退回一个LF的容量**。少一行是渲染结果，不是511变512。

要分别检查：模式名63、单Effect255、模式聚合255、公共511和最终511。中间层的残片后面还有输入时，可能变成别的字符；最终残片没有足够输入时才可能变`!`。只算最后一个Entry的剩余字节模3，无法覆盖最终点落在模式名／桥接LF上的情况。

### 9.3 灰色不是感叹号的充分原因

锁定与解锁配对已观察到：同样末端残片，两状态都可出`!`；完整尾部，两状态都可干净。活动字体配对也显示字体对象与采样glyph表相同，默认色不同。原Angler锁定时才出符号的历史现象不能直接归因“灰色会加感叹号”。

强制着色确实会破坏依靠原颜色隐藏可见字形的方案。零宽填充的合格条件应是**不用颜色包住填充，也没有杂符、空行及可见偏移**；当前具名配方已经实现这点，但仍受实际字体前提约束。

颜色头恰损两个字符是否崩溃仍未知，未进行这项实验。知识库编写者报告应双`%%`处单`%`会崩溃，记录为经验来源；不要为验证这一经验故意生成损坏格式。本文所有例子避免在颜色／百分号格式内部做危险截断。

## 10. 面板隐藏、战斗可见：可用的结构

### 10.1 面板与战斗为什么能分离

面板会列出本次有效模式的名字与差分；战斗提示只显示当前实际模式的差分，模式名不以面板方式列出。把**不会实际进入的虚假模式放在面板实际模式之前**，可让虚假分支填充至最终511，挡住后续实际模式名／差分；战斗当前处于真实模式，虚假填充不被拼入，真实差分可恢复。

这要求同时满足：

1. 实际模式差分保持描述开启，不能为了面板隐藏而统一`.has_description false`。
2. 公共段保留战斗差分空间；填满动作发生在虚假模式分支。
3. 虚假模式在实际玩法中不可进入；不能靠名称“虚假”就假定不会被切换。
4. 每个局部段及最终511的接缝都干净，相关字体下填充无advance／无字形。
5. 所有需支持的等级、数值位数、统计与可用性状态都纳入长度集合。

只有“无任何需要战斗显示的模式差分”时，公共段饱和可以作为独立简化路线；该路线不得作为存在战斗差分的通用解。

### 10.2 设计需求与对应方法

|设计需求|构造|代价和边界|
|---|---|---|
|末行风味台词，模式名隐藏|虚假模式名承载可见台词并用无色填充接缝；其差分继续填充|模式名局部63；长台词需拆分载体|
|不添加风味文字，面板／战斗保持原最后一行|将最后公共Effect移到所有真实模式的首个可见差分；虚假模式名复制该文字|所有实际模式都要补引用，增加Info量；不扩大文本容量|
|多行风味、面板专属说明|可见假模式名+假模式Effect；必要时多个假模式|每段63／255，最终511；内部换行要另算|
|多个面板专属章节|两个或更多有描述的虚假模式组合|已测双可见假模式；任意数量与任意排列未穷尽|
|不同等级长度不一|逐级归一化，或共享DEL尾部覆盖有限长度集合|只测满级不足以证明低级正常|
|较长战斗说明|尽可能减少公共包装，保留真实差分预算|真实单模式聚合仍255，公共+差分最终511|

“移最后公共行”的例子：原公共为`A、B、C`，真实模式另有`R_A／R_B`。改为公共`A、B`；假模式名显示`C`并填充；所有真实模式的可见差分以`C`开头，再接各自`R`。面板仍像`A、B、C`；战斗显示`A、B、C、R_当前`。不得漏掉任一可进入真实模式，也要保证每个差分的255容纳得下C+R。

该方法已有COPY真实施放和多行例证，不只是纸面推导。若C本身具有机械作用，移动的应是明确的显示载体／引用方案，不能未经核对把功能也从公共移走，改变哪些模式实际执行它。

## 11. 无色DEL配方：可复用计算步骤

这是**当前字体和已绑定消费者下的条件配方**。DEL U+007F与生成的U+200A在当前活动路径不产生可见字形／advance。其他字体、GUI或消费者必须先核对这两点。

定义：C为完整公共块实际保留字节；V为最后要显示的普通可见行，UTF-8长1—61，以下不含颜色；R为最长真实差分所需字节。现有某个公共文本载体需有明确余量用于补DEL，不能暗自新加一条Effect而引入新行。

```python
# 仅构造本地化源字符串；不写游戏文件、不加载游戏。
DEL = chr(0x7F)
ZWS = chr(0x200B)
V = "LAST|"
v = len(V.encode("utf-8"))
assert 1 <= v <= 61

first_name = V + DEL * (61 - v) + ZWS  # 源64，模式名保留63，尾为E2 80
second_name = DEL * 61 + ZWS          # 源64，保留63
bridge = DEL * 253 + ZWS             # 源256，Effect保留255，尾为E2 80
pad = DEL * 300                      # 源300，Effect保留255
```

双假模式模板的概念拼接为：

```text
common(C)
LF + first_name[:63] + LF + bridge[:255]
LF + second_name[:63] + LF + pad[:255]
LF + 实际模式后续内容
→ 最终[:511] → 使用实际解码器验证
```

单假模式模板用first_name+pad。上例中模式差分只有一个自定义项且无额外头，局部Effect255与聚合255恰好一致；换成普通Buff或其他目标时必须重新加入其包装，不能照搬255填充数量。

已测四公共长度7／126／190／501：前三使用双假模式，501使用单假模式，面板只显示预期LAST、战斗只显示真实差分。501样本战斗为 `501+LF1+REAL9=511`，A／B切换实际施放后仍完整无杂符。

**这不是所有C都自动成功。**同一具体模板在C447、448最终截为残片，出现`!`；446、449干净。锁定样本C127、128、447、448也失败；在现有公共行内加2个无色DEL后，变129、130、449、450并干净。补2对这四个点成立，不应写成“所有问题加两个DEL”。

可复用离线规划器：

```powershell
python -B -X utf8 Sources/evidence/skill_tooltip_20261117/raw/.alex_del_padding_planner.py --common 127 128 447 448 --visible "LAST|" --real-bytes 9 --spare 4
```

这只是本地条件计算，不是新实机验收。输入必须包括**整个实际长度集合**。例如125—129或445—449区间在该模板下共同补4才全部通过模型；仅看两端会漏掉内部失败点。501—505且必须再留9字节差分时，在所给余量与配方族内无解，不能升级为“所有引擎方案都无解”。

实际Info模式差分字段的参考形式为`.MODE_ID_effects "Effect_A" "Effect_B"`，模式名Entry为`str_skill_mode_info_MODE_ID`。完整实际配方及旧模式／Effect定义闭包见delmix4／layout4／sharedlevels5的原manifest；这里不复制实验技能的回血、切换、加动或伤害助手，避免把研究控制逻辑误用成文字模板。

## 12. 等级与数值变长：两条已测路线

### 12.1 每级独立文本，公共长度归一化

若允许每个等级用独立Entry，先求其全部格式化后长度C_i，再选共同目标T，并在**同一文本行内**插入前后配平SPACE与完整U+200B：

```text
T - C_i = 2a + 3b，a∈{0,1,2}，b≥0
```

2a来自a对前后SPACE，3b来自b个完整零宽。任何差值d≥2都有解：按`2a ≡ d (mod 3)`选a，再算b。T还需满足具体尾部接缝相位条件，不是随便选max+2就保证全部排版。

现代Buff尾部自带SPACE时，应先给源文本加对应前SPACE配平，再计入C_i；不能把引擎尾SPACE漏算。归一化不会自动适配同Entry运行时任意数值变化。

norm14具名7数值5／10／100／-5／-10／1000／0，公共统一20字节，已学／未学各一次共14项均两行无杂符约居中。后来levels5进一步实际购买同一技能代码level0→4，数值1／9／10／99／100，每级独立Entry补为20，四次工会比较、购买后tooltip及英雄面板端点均通过。中间级英雄面板未另看；不冒称五个英雄决心等级。

### 12.2 同Entry自然变长，共用尾部

sharedlevels5使用同一个现代Buff Entry `VALUE|%d|END`，五级值9／10／99／100／1000，对应公共12／13／13／14／15字节（含尾SPACE）。始终同一DRY_0／DRY_1／BRIDGE／PAD，未逐级补长。实际0→4升级的工会比较、购买后提示和英雄面板端点均两行无空行杂符约居中；两端活动原文均511并与模型相同。

这证明**有限数值集可以共享**，不证明任意数值区间、实时amount、所有统计／目标变化都能共享。新设计应列出实际位数集合、所有等级原生字段和最长真实差分，再交规划器检查。已有失败接缝仍然有效。

## 13. 居中、空格与最大单行宽度

### 13.1 半角空格不能一概当作排版中性

实机spaceflow14：首12SPACE右偏，尾12左偏，前后配平约对齐；颜色边界、CRLF／LF、原生LF、U200B没有普遍消除偏移。whitespace14：Tab／NBSP首8右偏、尾8左偏、各4配平；U+3000／U+202F在该字体没观察到偏移；U+00AD能显示横线。

在当前活动字体，SPACE和CR的advance为5，W22、i6、汉字采样23；height29、scale1、kerning为空。若某行确实保留L个首空格和R个尾空格、其余字符对称且未被解码吞并，可条件估算可见中心偏移为`(L-R)×5/2`。这里只用于解释，不用于按截图框边逐像素验收。

“起竿收线公共Effect前面有空格却看起来居中”与此不矛盾：应计算**解码后这条可见行两端合计advance**，包括包装尾SPACE、被接缝消耗的SPACE、后续拼到同一行的内容。源Entry开头有几个空格不足以单独决定偏移。

CR不是零宽替代品：前／后／中间12个CR分别造成右偏／左偏／文字中间间隙，虽没多一行。DEL在同路径未见此偏移，后续活动字形证据支持缺字被跳过。

### 13.2 当前字体的“不可见”怎样定域

已学Healing活动tooltip队列的标题与正文同一字体对象；锁定配对同指针及采样glyph表，只默认色不同。DEL、U+200A／B／C／D／U+2060在此消费者缺字且被跳过。历史未绑定候选字体表的记录不能替代活动证据，也不能把缺字记录中的未定义字节当advance。

字体源文件合并、fallback及具体Mod赢家未追到最终所有权。其他图标字体可能恰好给U+22A0／U+F2A0等提供可见图标；这正是不能把不同零宽互换的原因。

### 13.3 单行宽度与屏幕越界

当前英雄面板构造器开启auto-width，内容宽取各项最长行测量宽的最大值+10；视口调整位置，但该计算未见固定单行字数限制或视口钳宽。历史width14有W120超屏；活动采样字形离线推导W120／i120／汉120分别2640／720／2760宽，各仍一行。

因此最大单行“字数”没有一个跨字体常数。它受字节容量、实际glyph宽、UI布局共同影响。**屏外端点、截图没截全边框、底层文字透出，不是正文截断证据**。本项目验收按预期文字、大概行数、相同参照标签与相对居中；不使用截图框边像素计算结论。

## 15. 可直接采用的预算与排版工作流

1. **明确显示目标**：公共／面板专属／当前真实模式专属；是否有风味、多行、锁定状态、等级与运行时数字。
2. **建立实际字节账**：原生类型／统计／限制，目标头，单项正文，颜色，数值和引用名称，Buff尾SPACE，CRLF和原生LF／斜杠逐项计入。
3. **先过局部容量**：模式名63、各载体127／255、模式聚合255。单项已经被截掉的文字，后面空余总量救不回来。
4. **保留战斗空间**：公共+真实最长差分及其实际连接不得超过最终511；面板隐藏填充留在假模式。
5. **选择布局族**：短末行、COPY无风味、多行说明、多个可见假模式、逐级归一化或共享DEL有限集合。
6. **按层裁切后重放解码**：标出每个残片接缝，不以标准UTF-8解码器自动替换错误来模拟游戏。
7. **检查排版**：解码后的实际行、首尾advance、缺字是否被跳过，预期文字是否完整；不把画框越界或底层透字当成正文内容。
8. **使用已有实机证据的同构范围**：若目标／消费者／字体／边界实质不同，再做最小差异验证。静态计算、机器码隔离与实际施放分别记录。

这套流程用于有限已知设计。本文没有提供“任意Info自动重写并保证任意字体排版”的转换器；现有规划器针对已证配方、显式余量和有限长度集合。

## 16. 常见故障的准确诊断

|现象|先核对|不能直接下的结论|
|---|---|---|
|末尾`!`|最终残1／2字节；更早残片与后段合成；本级实际公共长度|“一定是灰色bug”|
|末尾出现陌生图标|FEFF／U200B残片的实际解码码点及字体映射|“所有零宽都一样”|
|多一个空行|实际空Entry、SPACE、标题、Buff尾SPACE、原生LF及接缝|“只要加一个零宽就行”|
|已学正常、未学异常|两状态最终原文／模板／默认色／字体是否真的相同|“灰色会额外加字符”|
|低级坏、满级好|数值位数／原生行有无／公共长度集合内部边界|“只验满级即可”|
|开condense后截得更早|斜杠增加、项目展开数、共享计数、头是否真省掉|“折叠必省字节”|
|差分明显比公共短|单项255、模式聚合255、公共511各层|“正文严格减半”|
|名称覆盖没反映|本地化键、模板、名称登记、活动赢家、加载入口|“这是名称长度上限”|
|改源码后仍出现旧模式文本|首次创建位置、重复字段、分行合并、Info／Art实际消费者|“模式太多导致固定截断”|
|长行端点看不到|屏幕越界、框裁切、原始字符串和标尺尾部|“达到单行字数上限”|

本次已观察：同一行重复`.effect`后者在指定样本覆盖前者；同level分行`.effect`在另一组保留BEGIN／NEXT两项。不能把两种语法位置混为“都追加”或“都覆盖”。Info／Art描述冲突样本按Info呈现，Art可能不消费这些字段，不等同所有Art字段优先级已证明。

另有模式引用行位置改变导致旧内容迁移、某些已存在模式名／差分缺段的具名现象，完整loader原因未知。不要把偶发缺段、旧缓存或单／多模式差异当稳定隐藏方法。`refreshes_skill_uses`固定Entry覆盖编译正确但旧文本仍显示，也不能因此测出该入口的长文本容量。
