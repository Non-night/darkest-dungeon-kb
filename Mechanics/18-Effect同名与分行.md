## 分行必须显式填写.target（2026-11-05）

知识库编写者2026-11-05明确补充：使用同名Effect分行迂回时，各分行不得省略.target；省略会黑屏报错，按Esc可继续正常游戏，但对应Effect是否正常生效尚未确认。不能依赖其他分行提供.target来省略本行字段。此要求针对Effect分行，不推广为技能Info中.target的默认规则。

来源：Sources/effect_split_target_required_20261105.json。

## `.buff_ids` 列表、同名分行与跨 Mod 施加顺序（2026-10-27社区实测）

证据来源：知识库编写者于2026-10-27提供的截图及聊天转录；外部来源作者无夜、Cathelia。不是本次Agent实机复测，不是反编译结论。截图标题为“由clear_buffs_on_rule_active参数反推buff_ids在同一行施加多个buff的顺序”。

### A/B测试与同文件分行
A具有 `clear_buffs_on_rule_active`，生效时清除A自身和B；B为常规Buff。截图所录无夜测试：

| `.buff_ids`参数顺序 | 观测结果 | 对顺序的解释 |
|---|---|---|
| A → B | B留存，A未清除随后施加的B | 先A后B |
| B → A | B不留存，被A清除 | 先B后A |

无夜于10-27 11:42:31、11:42:47、11:42:52补充：同名Effect分行也满足该顺序，观测与书写／阅读顺序一致；当时跨文件顺序未知。此处按同文件多Header的同名Effect分行记录，不是两个不同名称Effect的普遍时序。11:43:19提出跨文件可能按加载顺序，仅为当时推测。

### 跨Mod双向测试
Cathelia于10-27 11:45:54提出用两个Mod验证，18:03:36报告结果：两个Mod分别用同名Effect引出A/B；A为0防御的定向清理Buff，清除自身和B；B为+50%防御Buff，均有可见描述。

| 高优先级Mod | 低优先级Mod | 观测结果 | 支持的施加顺序 |
|---|---|---|---|
| A | B | 看不到B防御Buff，定向清除成功 | 低优先级B → 高优先级A |
| B | A | 能看到B防御Buff，A未清除后来施加的B | 低优先级A → 高优先级B |

已测结论：两份定义均实际保留、参与同名Effect分行时，`.buff_ids`的跨Mod施加顺序为**低优先级Mod先、高优先级Mod后**。这里的高低指聊天所述Mod优先级，不自行换算成未记录的数值或文件名字母顺序。报告作者据此解释为加载顺序；双向结果直接支持的是该同名分行Buff链的实际先后，不能据此证明所有游戏文件的内部加载算法。

### 同一Mod跨文件A/B双向测试补充（2026-10-27）
知识库编写者随后提供测试转述及截图 `codex-clipboard-51efe327-3e43-4641-bffb-54beb466dc4d.png`；本条按该次会话补充记录，不把上一轮无夜／Cathelia的署名自动套用于这次未署名的报告。截图中红框文件为 `AbigailWilliams.effects.darkest`（文件A）与 `BbigailWilliams.effects.darkest`（文件B），同目录另可见若干AbigailWilliams前缀文件；截图只用于辨认文件名，不证明其他文件参与测试或全部文件遍历顺序。

沿用同名Effect分行、定向清除与待清除Buff的测试语境，交换两份文件内的职责，得到：

| 文件A：AbigailWilliams.effects.darkest | 文件B：BbigailWilliams.effects.darkest | 观测结果 | 支持顺序 |
|---|---|---|---|
| 定向清除Buff | 待清除Buff | 待清除Buff留存，未被前者清除 | 先文件A、后文件B |
| 待清除Buff | 定向清除Buff | 待清除Buff不留存，被清除 | 先文件A、后文件B |

此处A/B是**文件标签**，不是上一轮固定指清理者A与普通Buff B；本次通过交换内容确认结果随文件先后变化，而不是清理Buff总在某个固定时点。

知识库编写者修正并补充（2026-11-04）：知识库编写者强调（2026-11-04）：文件名大小的排序规则仅适用于同一Mod／DLC内部；同目录下文件名小的先加载、大的后加载，按首字母排序理解，具体比较规则不明。不同Mod／DLC之间应按对应Mod／DLC优先级判断，不能跨来源比较文件名决定先后；低优先级先加载、高优先级后加载。同名Effect分行的重复单参数后加载覆盖先加载，buff_ids等多参数按实际加载顺序补充。跨子目录的内部顺序仍未确认。 在同一Mod／DLC、同目录、两定义均保留参与同名Effect分行时，文件名小的靠前、先加载，文件名大的靠后、后加载；这里的大小按首字母排序理解，具体采用哪种比较规则不明。原A/B双向测试支持A开头文件先于B开头文件。同名Effect分行的单参数覆盖也遵循相同加载顺序：后加载的覆盖先加载的，因此文件名大的文件中的重复单参数覆盖文件名小的文件中的值。这不同于.buff_ids等多参数内容按加载顺序补充。本次没有覆盖大小写、数字、标点、中文、共同前缀后的比较、子目录以及其他文件类型；不能升级成所有文件的通用加载或覆盖规则。原先“同一Mod跨文件未测”的空白已由此补充为“已测本组A/B先后，完整排序规则未知”。

### 适用边界
- 同列表按参数书写顺序，同文件同名Effect分行按定义书写顺序；跨Mod按上述低优先级到高优先级。不能再把同文件分行写成未知；无夜较早的跨文件未知被Cathelia后续跨Mod测试在该范围内补充，而非通用撤销。
- 同一Mod跨文件已由后续A/B双向测试补充：文件名小的先加载、文件名大的后加载（按首字母排序）；重复单参数后加载覆盖先加载；完整文件名比较规则、其他字符与子目录顺序仍未确认，见上节。
- **分行合并后的施加先后不等于整条或整文件覆盖**：跨 Mod 的同名 Effect 文件仍参与叠加，不能假定低优先级定义已整体丢失。多参数内容继续补充；重复单参数后加载覆盖前者的规则见下节。
- 聊天中“从低到高读、后读覆盖先读”的解释不升级为所有字段和所有文件类型的通则；来源作者也提示特殊文件例外。
- 不跨越AWR、普通queue false、queue true及调用来源层级推导任意Effect顺序；其他字段合并、8个最终Buff参数限制、定向清除条件仍分别按既有规则核对。


## 逻辑 Effect 身份
- 同一 `effect:` Header 内换行继续书写的内容，属于同一条物理 Effect 定义。
- 不同 Header 只要 `.name` 参数相同，会在一定意义上被视为同一个逻辑 Effect；跨 Mod 的同名 Effect 文件仍参与叠加。
- 不同 Header 的同名写法称为“分行”。
- 迂回表第88条 P1424–P1427/X1718–X1721 经当前用户于2026-11-04确认：Effect 文件不按普通同名文件的高优先级完全覆盖规则处理；制作补丁不能假定旧 Effect 定义已被同名文件替换。本轮未新增实机测试，不推广到其他文件类型。

## 分行的多参数补充与单参数覆盖
当前用户于2026-11-04结合迂回表第88条 P1419–P1420/X1712–X1713 澄清：Effect 同名分行的本质是多参数关键字相互补充，单参数关键字相互覆盖，后写／后加载的值生效。因此，分行中重复填写不同的 `.target` 时，最终只使用后面的 `.target`，不会让各分行分别保留不同目标。

原表“需要 target 相同”应理解为：通常采用分行是为了补充多参数内容，应保持 `.target` 等不希望改变的单参数字段一致，避免它们被后续分行改写；不是说不同 `.target` 会使同名分行失去逻辑身份。未填写某字段时的默认值与继承行为，仍须按具体字段核对，不由这项重复赋值规则推断。

当前用户随后明确确认：单参数覆盖与 `.buff_ids` 分行使用相同加载顺序。同文件后写的值生效；沿用上文已测范围，跨 Mod 为低优先级先、高优先级后，故后者的重复单参数值生效；同一 Mod 两文件 A/B 测试中 B 后加载，故 B 的重复单参数值生效。完整文件名比较规则、其他字符与子目录仍未确认，不据本次确认扩充为所有文件的通用规则。多参数内容的保留与单参数字段覆盖可以同时发生，不等于整个 Effect 或整个文件被替换。本轮为当前用户确认补录，没有新增实机测试。

## 相同内容重复分行不会自动去重
迂回表第88条 P1421–P1422/X1714–X1715 经当前用户于2026-11-04确认：相同多参数内容重复分行仍会继续追加，不能当作自动去重；重复的单参数字段仍按后写／后加载覆盖，不是任意相同 Effect 字段的数值都会翻倍。技能的真吸血代码重复填写会导致翻倍吸血，次数须按每个技能等级最终合并后的定义检查。各等级分别写一次是正常用法；若采用正确的无等级共用分行，则共用部分整体只写一次，不要又在各等级中重复写入同一内容。技能等级合并边界见[专题37](37-技能同ID分行与无等级共用分行.md)，真吸血见[专题27](27-治疗源与真吸血.md)。本轮未新增实机测试。

## `.buff_ids` 的最终参数数量

知识库编写者确认（2026-09-22）：`.buff_ids` 必须按引号外空白解析出最终参数数量；单条实际 Effect 调用最多 `8` 个 Buff ID。超过 `8` 个时，不能继续把它们写在同一条 `.buff_ids` 中，必须采用合法分行拆分，或直接拆成两个不同 Effect；每个实际 `.buff_ids` 参数串都必须重新计数并保持不超过 `8`。

这里的“分行”不能只按视觉排版理解：如果使用同名 Effect 分行，必须核对该字段的逻辑合并方式；无法确认拆分后仍是独立实际调用时，直接使用两个不同 Effect ID 更安全。引号内含空格的 Buff ID 仍只算一个参数，计数按解析结果而不是空格数量或代码行长度。

## 推理边界
- 同名视为同一逻辑 Effect，不等于所有关键字都已确认会无条件合并；具体字段必须查对应词条。
- 已知该机制可能突破某些按单条 Effect 计算的限制，例如 `.buff_ids` 的有效引用数量。
- 判断某关键字的“同一条 Effect”时，应按逻辑 Effect（`.name`）判断，而不只按物理行判断。

## 与 `.can_crit_heal` 的关系
`.can_crit_heal` 判断的是同一逻辑 Effect 中的 `.heal`：同一 Header 内换行，或不同 Header 的同名 Effect 分行，均属于其作用范围；不能因跨 Mod 的 Effect 文件同名就假定其中定义已被覆盖。只有该逻辑 Effect 中存在参数大于 `0` 的 `.heal` 时，`.can_crit_heal` 才有实际意义。

## 最小示意
```darkest
effect: .name "Heal Split" .target "performer" .heal 10
effect: .name "Heal Split" .target "performer" .can_crit_heal true .on_hit true .on_miss true
```

上例仅说明“同名分行”的逻辑关系；具体字段合并规则仍以对应关键字资料为准。
