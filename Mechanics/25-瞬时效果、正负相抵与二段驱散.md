## “瞬时效果”的含义
“瞬时效果”是社区口语，指为了完成当前 Effect 结算而临时施加 Buff，并希望该 Buff 只存在于一段严格、极短的结算窗口中，不干扰后续行为。

典型需求：技能仅在施术者生命值大于等于 `50%` 时，额外造成一次流血。如果使用 `.skill_instant true`、`.keyStatus` 或 `.monsterType` 引出的条件简写 Buff，该 Buff 默认属于 `bsrc_instantSkill` 源，并可能在后续游戏 Update 前持续存在，期间可能错误影响反击、同技能其他 Effect、饰品 Trigger，以及由 `attack_additional_effect_ids` 引出 Effect 的“附魔 Buff”等内容。

`.skill_instant true` 与 `.keyStatus` 均有两次施加：第一次从点击技能图标开始，到直伤面板第一次结算为止；第二次从对应 Effect 实际被引用的具体时序开始。第二次施加不固定在 AWR，而是与常规 Effect 一样服从 AWR、`queue false`、`queue true` 等实际时序。`bsrc_instantSkill` 源 Buff 会在游戏 Update 时消失，例如其他单位回合开始或玩家切换当前选择的技能。若在同一条 Effect 中通过 `.buff_ids` 引出 Buff，`.keyStatus` 和 `.monsterType` 会被按等同于 `.skill_instant true` 的机制处理。

因此这类简写通常只适合覆盖当前技能处理期间的效果，**高度不建议用于瞬时效果**。瞬时需求应使用准确指向实际目标的普通 Effect/Buff，并在使用后立即通过已确认的方案善后。需要注意：下次 Update／点击其他技能时消失的根本原因是 `bsrc_instantSkill` Buff 源类型，而不是 `.skill_instant true` 这个布尔字段本身。`.skill_instant true` 默认会带出该源，但可以用专门的 `.buff_source_type` 覆盖；例如在技能中使用 `.skill_instant true .buff_source_type bsrc_skill`，可以保留点击技能时的即时获得窗口，同时使所引出的 Buff 不再因 `bsrc_instantSkill` 的 Update 清除而消失。但这种写法可能触发一个原因尚不明确的首次点击双重施加问题，使 Buff 错误堆叠；这只是必须注意的风险，不是绝对禁用规则。

## 严格时序前提
以下三个方案都依赖同一技能中多个 Effect 按引用顺序依次结算。

- 参与操作的 Effect 必须处于同一个“大时序”，例如全部为 AWR，或全部为普通 `queue false`。
- 在同一文件、同一来源的连续引用中，可利用书写顺序形成“临时增益 → 使用增益 → 善后”的不可插入窗口。
- 跨文件书写时能否保持相同严格顺序尚未确认，不要依赖跨文件顺序实现该类迂回。
- AWR、`queue false`、`queue true` 的整体层级见：[queue 与 AWR](04-queue与AWR.md)。

## 方案一：瞬间真驱散
以下保留旧式方案的工作原理与风险，供解读既有代码；不是当前选型建议。当前用户于 2026-11-02 要求：在支持 `clear_buffs_on_rule_active` 的目标版本，瞬时 Buff 善后不应使用按源瞬间真驱散，应改用 Buff ID 定向驱散。若需兼容不支持该字段的旧版本，应另行说明，不把旧方案当作默认选择。

以“生命值大于等于 `50%` 时额外造成一次流血”为例：

1. 条件成立时，给自身施加 `+4000%` 流血施加概率 Buff，并声明为 `bsrc_last_hero` 源。
2. 使用 `-3900%` 基础概率施加流血；条件 Buff 存在时，最终概率为 `100%`。
3. 对自身的 `bsrc_last_hero` 源执行 `.steal_buff_source_type` 真驱散。

这组连续 Effect 不会被其他 Effect 插入，可使临时概率 Buff 在完成本次流血判定后立即消失。

### 风险
- 旧式偷取／真驱散一次处理的 Buff 数量大于 `1024` 时必定崩溃；实际起崩点不确定。`1000` 是安全极限参考，大于 `1000` 有较高崩溃概率，小于 `1000` 也不保证不崩溃，只是概率更低；不得把该参考理解为安全保证。恰好 `1000` 或 `1024` 的必现性未单独确认。 证据与历史测试差异见 [Buff源与真驱散](15-Buff源与真驱散.md)。
- Buff 源不能真正自定义；非法源都会归入同一个 `combat_end` 源。按源清除可能误伤同源的其他 Buff。
- 合法源数量有限。即使社区约定将 `bsrc_last_hero`、`bsrc_flashback_start` 留给瞬间真驱散，也不能消除来源冲突和数量风险。

因此瞬间真驱散虽然无 Buff 残留、演出干净，但在上述可使用 ID 定向驱散的目标版本中不作为当前方案。

## 方案二：正负相抵 / AX-A 迂回
正负相抵也称**正负互抵**；国外资料中也称 **AX-A 迂回**。流程为：

1. 条件成立时，给自身施加 `+4000%` 流血施加概率 Buff。
2. 使用 `-3900%` 基础概率施加流血。
3. 给自身施加 `-4000%` 流血施加概率 Buff。

正 Buff 与负 Buff 必须满足以下条件：

- 数值绝对值相同、符号相反。
- rule 相同。
- 持续时间和持续时间类型相同。
- `remove_if_not_active` 等一切会影响 Buff 是否存在及何时消失的属性相同。

只有两者同时出现、同时失效或同时消失，净修正才会稳定归零。

适用边界（迂回表第 2 条 P355/X366、P358/X372，经当前用户于 2026-11-02 复查确认）：AX-A 只能用于能精确抵消的瞬时流程，不能代替持久 Buff 的实际移除。A 与 -A 必须作用于相同目标，且生成数量、数值与生效条件应能一一对应；不能只保证单个 Buff 的参数相同。

例如，A 按敌人数生成，X 尝试用真伤杀死敌人，再按当前敌人数生成 -A：若 X 已改变敌人数，-A 的数量可能与 A 不同，无法完整抵消。环境或条件在 A→X→-A 之间变化时，应先确认抵消仍然精确；无法保证时应改用 Buff ID 定向驱散（目标版本须支持 `clear_buffs_on_rule_active`），不沿用原表“只能真驱散”的旧选型。这是适用条件与清理方案的确认，不是新增实机测试。

### 风险
- 两个 Buff 仍会留在单位身上；它们只是数值相抵，不是被清除。
- 旧式 AX-A 的临时 Buff 若短期叠加无害，可用无图标的 `bsrc_notspecified`；若累积会干扰 buffFX 等表现，可考虑在 Any Update 时自动清除的 `bsrc_battle_modifier`。这是迂回表第 2 条 P360/X376 的用源经验，经当前用户于 2026-11-02 确认为基本成立，并补充：真光环源需要图标且必定有图标，不是无图标替代源。自动清除也不等于在 X 完成后立即清理；本段不撤销当前采用 Buff ID 定向驱散的要求。
- 若要求无图标表现，应选择适用的无图标源并确认实际 Buff 类型；不得为了利用真光环源的自动清除就宣称没有图标。
- 某些 Buff 无论使用何种源都可能显示，例如“无法被守护”类 Buff，因此仍可能产生演出瑕疵。
- 瞬间施加过多 Buff 可能导致游戏闪退；其原因有可能是内存溢出，但目前尚未确认，不能写成定论。
- “过多”的具体界限尚未确定；当前只能明确确认一次瞬间获得 **80 个 Buff 是安全的**，超过 80 个的安全范围和崩溃阈值均未知。
- 因此，80 个应作为当前已确认的安全参考点，而不是引擎的硬上限；超过该数量时必须保留风险，不得断言必定安全或必定闪退。
- 长期累积大量 Buff 也会增加老旧引擎的不稳定风险；具体安全数量没有统一结论。

正负相抵避免了按源真驱散及其数量溢出，但代价是 Buff 残留。

## `clear_buffs_on_rule_active` 的关键性质
`clear_buffs_on_rule_active` 是 Buff 的 ID 定向驱散列表。当前实测结论如下：

1. **仅作用于持有者自身**：它只扫描清理 Buff 持有者身上的 Buff；即使场上其他单位持有相同 ID，也不会被清除。ID 定向驱散不能直接跨单位驱散。
2. **Rule 通用**：任意 rule 只要成立，就会执行列表清除。
3. **检测极快**：rule 成立后几乎立即清除。使用 `attacking_monster_type` 测试时，清除甚至早于伤害结算，可按“条件满足即执行”处理。
4. **先执行自身清除，再被其他 Buff 清除**：若一个 Buff 即将被清除，但自身也具有 ID 定向驱散，它会先清除自己的列表目标，然后才被清除。
5. **允许清除自身**：列表包含当前 Buff 自身 ID 时，它会先处理列表，再将自身清除；该行为与列表内 ID 的书写顺序无关。
6. **空 ID 会命中全部 Effect 简写 Buff**：所有 Effect 简写形式生成的 Buff ID 均为 `""`。列表中只要出现一项 `""`，就会清除持有者身上的所有简写 Buff，无法按简写类型区分；这可能误伤技能、饰品、反击或其他机制产生的简写 Buff，通常不建议使用。

链式例：A 清除 B、B 清除 C，三者 rule 均为 `always`。按 `C → B → A → C → B` 成功施加后，最终只留下 A；最后一个 B 会先清除 C，再被 A 清除。

## 瞬间大量施加 Buff 的数量边界

一次瞬间流程中不要无条件堆叠大量 Buff。当前只能确认 80 个 Buff 的瞬间施加是安全的；超过 80 个的安全边界未知，闪退原因可能与内存溢出有关但尚未确认。该数量是安全参考点，不是硬性上限。

## `.buff_ids` 的列表内部顺序与刷新写法
同一个 Effect 的 `.buff_ids` 列表存在已确认的内部施加顺序：先书写的 Buff 先施加，后书写的 Buff 后施加。若 Buff A 的清理逻辑会清除自身和 Buff B，则：

```darkest
.buff_ids "A" "B"
```

可在能够引用 Effect 的场景中实现“不可叠加、重复施加只刷新持续时间”的 Buff。重复施加时，A 先清理旧的 A/B，随后 B 再按列表顺序施加；其结果是旧状态被移除后重新建立，而不是多个同类实例叠加。

该写法有明确前提：A 必须确实能清除自身和 B，清理后 B 必须仍能成功施加，且 Effect 与 Buff 的持续时间及持续时间类型覆盖关系不能造成冲突。这里的顺序只确认于同一 `.buff_ids` 数组内部，不得外推为不同 Effect、不同调用来源或 AWR、`queue false`、`queue true` 之间的通用时序规则。

同名 Effect 的分行写法也有效；跨 Mod 的同名 Effect 文件仍参与叠加。以下以当前目标为受术者展示结构，每个分行均保留 `.target`；A/B 的定义、命中门、概率与持续时间仍须在实际调用中补齐：

```darkest
effect: .name "aaa" .target "target" .buff_ids "A"
effect: .name "aaa" .target "target" .buff_ids "B"
```

两行属于同一个逻辑 Effect，仍可按 A 后 B 的顺序实现相同的清理—重新施加效果。不要把这条结论扩展为两个不同名称的 Effect；还必须保留同名逻辑 Effect 的实际引用顺序，并核对其他字段的合并规则。

官方 Fire’s Edge DLC 实例：`DarkestDungeon\dlc\4964110_fires_edge\features\runaway\shared\buffs\runaway.buffs.json:327`

```json
{
  "id": "rw_in_rank_1_clear_run_and_hide",
  "stat_type": "tag_blocked",
  "stat_sub_type": "",
  "amount": 0,
  "remove_if_not_active": false,
  "rule_type": "in_rank",
  "is_false_rule": false,
  "rule_data": { "float": 0, "string": "" },
  "is_clear_debuff_valid": false,
  "has_description": false,
  "description_tooltip_id": "buff_tooltip_rw_in_rank_1_clear_run_and_hide",
  "clear_buffs_on_rule_active": [
    "rw_run_conditional_stealth"
  ]
}
```

持有者位于一号位时，该 Buff 清除 `rw_run_conditional_stealth`。

## 方案三：二段驱散 / 驱散二段式
本文的“二段驱散”专指利用 `clear_buffs_on_rule_active` 的自清除方案，不指“先把 Buff 偷到另一个单位，再从该单位偷走”的旧式两阶段真驱散。

仍以条件流血为例：

1. 条件成立时，给自身施加临时的 `+4000%` 流血施加概率 Buff。
2. 使用 `-3900%` 基础概率施加流血。
3. 给自身施加一个 rule 为 `always` 的清理 Buff；其 `clear_buffs_on_rule_active` 同时填写第一步临时 Buff 的 ID 和清理 Buff 自身的 ID。

清理 Buff 出现后会先定向清除临时 Buff，再清除自身。最终没有 Buff 残留，也不依赖 Buff 源批量偷取，不经过旧式按源偷取的数量溢出路径，并且与瞬间真驱散一样没有图标或演出残留。




























该 Buff 会清除四个指定的临时 Buff 及自身，最终无 Buff 残留。

## 方案选择
| 方案 | 是否残留 Buff | 主要优点 | 主要风险 |
|---|---|---|---|
| 瞬间真驱散 | 否 | 演出干净，旧版本也可使用 | 按源误伤；超过1000有较高崩溃概率，超过1024必崩；更少也不保证安全 |
| 正负相抵 / AX-A | 是，保留两个互抵 Buff | 不使用真驱散；避免驱散溢出 | 图标或演出瑕疵；Buff 累积 |
| 二段驱散 | 否 | 按 ID 精确清除；无演出残留；已测规模远高于旧式真驱散 | 依赖支持 Fire’s Edge 新字段的游戏版本；绝对数量上限尚未确认 |

在可以使用 `clear_buffs_on_rule_active` 时，二段驱散是当前应采用的瞬时 Buff 善后方案；它按 ID 精确清除、干扰更小。此选型不把 ID 定向驱散的已测规模误说成无限容量。

## 容量边界
- 旧式偷取／真驱散一次处理的 Buff 数量大于 `1024` 时必定崩溃；实际起崩点不确定。`1000` 是安全极限参考，大于 `1000` 有较高崩溃概率，小于 `1000` 也不保证不崩溃，只是概率更低；不得把该参考理解为安全保证。恰好 `1000` 或 `1024` 的必现性未单独确认。 这是当前用户2026-11-03确认的数量风险边界，不是本轮实机复测。
- ID 定向驱散已通过列表含 `16385` 个 Buff ID 的测试：目标 Buff 均被清除，游戏仅轻微卡顿。
- 该测试只能证明可处理至少 `16385` 项，不能证明绝对无上限；上万项列表不属于常规创作用量。
