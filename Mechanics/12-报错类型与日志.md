这些名称是社区用于区分报错表现形式的简称，不表示固定的严重程度。

## 红字报错
- 报错信息会写入游戏主程序同目录的 `app.log`。
- 在游戏设置中开启报错显示后，信息也可显示在游戏右下角，文字为红色，因此俗称“红字报错”。
- “出现红字”只说明记录和显示形式；是否会造成代码失效、存档问题或后续崩溃，必须按具体机制单独判断。

### `Could not find effect "<ID>"`：Effect 引用查找失败

知识库编写者确认（2026-09-24）：`app.log` 中类似：

```text
Could not find effect "MG"
```

这一诊断必定表示：游戏引擎在该调用点把 `MG` 当作 Effect ID 查找，但没有找到／识别到对应的 Effect 定义。它说明的是**引擎的查找结果**，不等同于已经证明磁盘上真的完全不存在该定义。可能原因包括但不限于：

- 该 ID 的 Effect 定义确实不存在，或调用 ID 与定义中的 `.name` 不完全一致；
- Effect 所在 `*.effects.darkest` 文件未被正常识别，例如文件带 UTF-8 BOM，导致首个定义／Header 未被读取；
- Info 中引用 Effect 的位置发生溢出或截断，导致引擎实际读取到的引用与预期不同。知识库编写者更正（2026-11-01）：Info 中非注释内容单行保留前 `511` 个字符，仅超出部分被截断，恰好 `511` 字符可保留；空格、引号及其他已知参与该行的原始字符均计入长度，不能只计算可见的非空白内容；换行符、制表符和中文字符是否以及如何参与底层计数，当前尚未确认。因此长技能行也可能让调用字段/引用被截断。技能 `.effect` 引用数量另有 Info 溢出风险，见 size0 资源最小化说明；
- 其他使该定义或引用未能进入引擎实际查找数据的加载／解析问题。上述情况是排查方向，不是穷尽列表，也不能仅凭这条报错断定是哪一个根因。

该错误不是由本地化 XML、`.loc2` 或其他无关本地化内容导致的。看到这一条时，应优先检查 Effect ID 的精确拼写、定义是否被游戏识别，以及调用方文件是否被正确解析；不要把本地化缺项当成它的原因。即使名称相同的本地化 Entry 缺失，也不会把 Effect 定义变成“找不到 Effect”。

## app.log 中的部分回合流程

`app.log` 不只用于查看错误；部分回合流程也可以根据其中的记录得出。当前用户于2026-11-03明确补充此用途，并确认将迂回表第56条P1168–P1170/X1368–X1370的debug观察保留为历史流程记录，见[Buff持续时间类型与实际清除](17-Buff持续时间类型与实际清除.md)的回合顺序专节。

只有实际日志中可对应的事件才可作为该次运行的流程证据；不能把“部分流程可得出”写成日志必定覆盖完整流程，也不能将原表debug观察冒充为本轮已经核验的app.log。本轮未读取对应运行日志，不补造日志内容、开关或工具参数。原表问号、版本与调用边界保持不变。

## 黑屏报错
- 指游戏进入黑屏错误或警告界面的报错表现。
- 是否能退出、是否会崩溃、是否影响当前存档或仅在本次运行中出现，取决于具体错误；不得只根据“黑屏报错”四字推断后果。

## 与其他故障的区分
- **闪退/崩溃**：游戏进程异常退出或无法继续运行。
- **卡死/软锁**：进程可能仍在运行，但流程无法继续。
- 红字、黑屏、闪退与卡死是不同维度的表现，记录知识时应分别说明。

## Agent 记录规则
描述报错时至少分开记录：
1. 显示形式：红字、黑屏或无可见提示。
2. 功能结果：该项是否生效、是否留下无效状态。
3. 稳定性结果：是否闪退、卡死或损坏流程。
4. 恢复方式：能否退出提示、重启恢复或需要修复存档。

没有明确测试结论的后果必须写“当前资料未确认”。
