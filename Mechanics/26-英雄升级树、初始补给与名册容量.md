## 自定义 Heirloom 的副本掉落与回城结算

在未修复环境中，真正自定义新增的 `heirloom` 型祖产货币若在副本内掉落并被获得，回城时必定崩溃。本项指纹章、地契等祖产货币类型，不包括血酿等俗称“祖产”的 `estate` 型道具。原表将原因解释为回城祖产结算 HUD 没有支持自定义祖产的框架；该原因保留为原表解释，不冒称已核验引擎内部实现。

原表的替代获取渠道是任务本身的奖励、城镇事件或区域建筑每周产出，而非副本内掉落；其举例分别为 Exaelus 图鉴的水晶与朝日群岛的印章。这些是原表案例，不据此补造对应 Mod 的当前完整实现。原表指出黑圣物的四种“新增祖产”属于原版祖产换皮，因此不能用它们证明真正新增 `heirloom` 可安全在副本内掉落；这一例子仅用于区分换皮与新增类型，不引入黑圣物专门适配要求。

原表另记旧局师傅主程序已修复此回城崩溃，允许自定义 Heirloom 在副本产出并正常回城。该修复只作为旧环境历史记录；当前版本及经 AI 更新版本是否沿用未知，不能直接认定当前已修复，也不能沿用“任何环境均无解”的绝对说法。设计获取渠道时须按实际程序环境区分上述边界。

证据：迂回表第49条 P1104/X1284–P1106/X1286，当前用户于2026-11-03确认按上述类型、获取渠道、原因层级与版本边界补入；非本轮新增实机测试。

## 英雄历练值升级阈值

`campaign/roster/roster.variables.json:4` 的 `resolve_level_thresholds` 是英雄等级的累计历练值表。数组从等级 0 开始索引，第 `n` 项对应升到 `n` 级需要的累计 `resolve_xp`。明耀模式的同名字段定义在 `modes/radiant/campaign/roster/roster.variables.json:4`。两套阈值见[原版副本数据速查表](../Reference/vanilla_raid_tables.md#英雄历练值升级阈值)，单次任务奖励的配置入口见[原版副本探索、扎营夜袭与出本结算](101-原版副本探索、扎营夜袭与出本结算.md#地区随机本的任务完成奖励配置)。

累计历练值达到对应阈值（`>=`）即升到该等级。还有下一级时，英雄面板显示「从 0 级起的当前累计历练值 / 下一级所需的累计历练值」。例如在极暗、血月或狱火难度下，累计历练值刚好达到 14 点时英雄已是 3 级，面板显示 `14/24`。24 是升到 4 级的累计阈值，还差 10 点。

阈值表依据 2026-11-25 本地原版 JSON 静态核对。升级边界与面板示例据同日知识库编写者确认，本轮未新增实机验证。

## 英雄升级树
原版英雄升级定义位于：

```text
DarkestDungeon\upgrades\heroes\<hero_id>.upgrades.json
```

原版例子：`DarkestDungeon\upgrades\heroes\abomination.upgrades.json`。

- 文件名通常为 `<英雄ID>.upgrades.json`。
- 是否允许使用其他前缀尚未确认；为保证可识别性，Agent 必须使用对应英雄 ID 作为文件名前缀。
- 英雄有三类可升级内容：武器、护甲、战斗技能。升级树的 `tags` 通常分别必须包含 `weapon`、`armour` 或 `combat_skill`，大概用于向引擎声明该树的所属类别；当前倾向将其视为对应类型的必写标签。它们是否还直接决定建筑、升级界面或其他处理方式，以及省略、写错、混用或添加自定义标签时的具体后果，均未知，不得自行试写。

- 完全仿照原版时，武器、护甲和每个技能都具有 `0～4` 共五个等级。
- 武器与护甲树通常带有 `first_level_not_upgrade`。当前理解是：该标签表示第一个实际等级属于初始自带内容，不作为一次付费升级购买，因此武器与护甲升级树只需提供后续四次升级要求；这一解释尚未经过严格专项验证。省略该标签的具体后果未知，新职业应仿照原版保留。
- 每个战斗技能树通常提供 `code 0～4` 五组取得/升级要求。
- `requirements` 中每档的 `code` 可能是升级节点标识符，供后续 `prerequisite_requirements[].requirement_code` 配合 `tree_id` 引用，但这一语义尚未确认。它是否还决定实际升级等级或先后顺序、能否使用非数字自定义字符串，均未知；制作时必须仿照原版使用连续的数字字符串，不得自行扩展。
- `currency_cost` 表示购买该档升级所需消耗的货币；其中 `type` 是货币类型，`amount` 是消耗数量。数组同时包含多项时是全部支付还是任选其一，以及省略字段或填写空数组时的行为，均未知；没有专项需求时应仿照原版填写单项金币费用。
- `prerequisite_requirements` 数组内的条件必须**全部满足**，按 AND 关系处理。其中 `tree_id` 指向作为前置条件的升级树，`requirement_code` 指定该树中必须已经满足的节点；因此它既可引用当前职业自身的前一档升级，也可引用铁匠铺、工会等外部升级树。此解释较可信但尚未严格专项验证。将数组置空、字段省略或使用其他空值写法时的行为未知，制作时应仿照原版保留字段与数组结构。
- `prerequisite_resolve_level` 的具体语义和边界尚未完全确认。当前仅能记录：用户推测写 `0` 表示无需决心等级，省略后的行为未知；不要把它未经验证地写成“最低决心等级”规则。制作时应仿照原版对应升级档位填写，并把非零值的实际门槛视为待验证。
- 升级 JSON 的严格最小字段集合和容错范围尚未完全确认；看不懂的结构、标签、建筑要求和费用结构按对应原版英雄原样仿写，不删减未知字段。

最小关系：

```text
<hero_id>.weapon              -> weapon/armour 定义中的 upgradeRequirementCode
<hero_id>.armour              -> weapon/armour 定义中的 upgradeRequirementCode
<hero_id>.<combat_skill_id>   -> combat_skill 的 level 0～4
```

## 初始补给
职业初始补给定义通常位于：

```text
campaign\provision\<hero_id>.provision.json
```

当队伍中存在对应英雄时，在进入副本前的补给购买阶段，配置中的物品会自动出现在背包中，并且不可卖出。

```json
{
  "raid_starting_hero_class_item_lists": [
    {
      "hero_class": "aaa",
      "item_lists": [
        { "type": "supply", "id": "antivenom", "amount": 1 }
      ]
    }
  ]
}
```

### 老路初始背包与修改方法（2026-11-07）

原版文件事实：`DarkestDungeon\scripts\starting_save\persist.raid.json:63–73` 的 `party.inventory` 预置了老路初始背包。`items` 的 `"0"` 条目为 `{"id": "", "type": "provision", "amount": 2}`，即初始携带2个食物；食物的 `id` 在该实例中确实为空字符串。`system_config_type` 为 `"raid"`，同层另有 `hunger_room_buffer: 2`，不能把后者误当作食物数量。

原始文件快照：`Sources/portable_evidence/old_road_starting_inventory_20261107/persist.raid.json`。本条来自本地原版文件核对；当前用户明确授权将下面的修改办法按推测记录，尚未完成游戏内验证。

**修改办法（推断／待实测）**：在目标 Mod 内按原相对路径放置完整的 `scripts/starting_save/persist.raid.json`，复制原版完整模板后仅修改 `party.inventory.items`。修改食物数量可调整原条目的 `amount`；替换物品则调整其 `type`、`id`、`amount`；添加多种物品可保留 `"0"`，再增加 `"1"`、`"2"` 等不重复的数字字符串键，每项包含对应三字段。具体道具、饰品或其他物品的 `type/id` 必须核对其真实定义或已有存档序列化实例，不能把显示名称当作 ID，也不能假定所有类型均用空 ID。饰品候选写法为 `{"id": "<实际饰品ID>", "type": "trinket", "amount": 1}`，此处仅是待验证结构说明，不是已验证可运行案例。

该方法旨在修改新建存档进入老路时的背包物品；向背包放饰品不等于给雷纳德或迪斯马装备饰品。修改该初始模板能否由 Mod 同路径覆盖加载、是否影响已创建存档、物品类型支持范围、堆叠及容量限制均未实测；不得承诺其会追溯更新已有存档。不要只保留 inventory 片段覆盖完整文件，其他初始任务、队伍和状态内容应完整保留。此路径与 `campaign\provision\<hero_id>.provision.json` 的英雄职业出发补给机制分开记录。

### 英雄出发自带 Estate 与 `.estate_can_be_provision`

原表作者 KKU/TPN 的历史测试记录：当 `estate` 型物品设置 `.estate_can_be_provision true`，且该物品由英雄出发自带补给带入副本时，该字段不能让这份出发自带物品在任务结束后带回城；原表据此称不能“空手套白狼”。

原表还报告了该场景的库存异常：仓库中对应物品取出后可能无法售回；取消出发界面可解决这一项不可售回现象。即使相关英雄不在当前队伍中，异常也可能仍然出现；在副本内消耗这份自带物品后，仓库中该 `estate` 的库存数量也可能减少。后两项仅按原表报告记录，不推断其触发顺序、稳定复现条件或适用于其他获取路径。

原表建议不要对英雄出发自带的 `estate` 启用 `.estate_can_be_provision true`：此用法不能实现带回城，并伴随上述历史库存异常。此边界仅针对英雄初始补给中的 `estate`；不推广到副本掉落、商店购买、任务奖励等其他获得路径，也不声称当前版本已复测。

证据：迂回表第121条 P1871–P1874/X2400–X2403；当前用户于2026-11-05确认按此边界补入，非本轮新增游戏测试。字段 `.estate_can_be_provision true` 的官方 DLC 实例为 `DarkestDungeon\dlc\702540_shieldbreaker\inventory\shieldbreaker.estate.inventory.items.darkest:1`，该静态实例只证明字段写法存在，不证明上述历史行为。

## 名册容量差分
职业或 DLC 可通过：

```text
campaign\roster\<prefix>.roster.additional_variables.json
```

增加名册容量：

```json
{
  "additional": {
    "roster_size": 1
  }
}
```

该文件支持**前缀差分**：以 `.` 分割文件名时，第一个 `.` 前的部分为前缀。多个前缀不同、文件名不同的 `*.roster.additional_variables.json` 会同时加载，其 `roster_size` 相互叠加。

例如官方破盾者提供 `1`，另一职业 Mod 以不同文件名再提供 `1`，两者同时启用时名册容量总计增加 `2`。文件名完全相同时仍应按文件覆盖规则检查，而不是按差分叠加。

单个 roster 存档文件过大及已招募／阵亡英雄数据累积的历史风险，见 [存档溢出与64位环境边界](29-区域建筑与英雄标签.md#存档溢出的历史风险与64位环境转述)；不要将名册人数容量与存档文件体积混为同一上限。
