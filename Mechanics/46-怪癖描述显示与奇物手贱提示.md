## 2026-11-05 新版更新

知识库编写者明确：清除指定怪癖可替代原有“进化到空”迂回，且比进化到空更好用，适用的移除需求优先采用直接清除。本字段按怪癖标签选择，不擅自写成按任意怪癖ID；必须核对标签命中范围，避免删除其他同标签怪癖。 新版还修复多个怪癖Tray图标重复，并新增按quirk_tag_id的肖像/角色面板图及combat_end/quest_end进化时间单位。

详见[新版字段与修复](96-新版Modding更新Buff技能地牢饰品怪癖.md)及`Sources/modding_update_20261105_remaining.json`。

怪癖库通常位于：

```text
shared\quirk\*.quirk_library.json
```

本页只说明怪癖条目中的三个描述显示开关。它们不改变怪癖所引用 Buff 的实际机制。

## `show_explicit_buff_description`

```json
"show_explicit_buff_description": true
```

- 当玩家把鼠标悬停在该怪癖上时，在怪癖描述中显示其引用 Buff 的具体效果描述。
- Buff 描述的显示顺序与该怪癖定义中 `buffs` 数组的引用顺序一致。
- 该字段控制的是描述展示，不应解释成是否实际施加 `buffs` 中的 Buff。

例如：

```json
"buffs": [
  "example_buff_a",
  "example_buff_b"
]
```

若两个 Buff 都能生成可见描述，则怪癖悬停说明中按 `example_buff_a`、`example_buff_b` 的引用顺序显示。

## `show_flavor_description`

```json
"show_flavor_description": true
```

- 在怪癖悬停说明中显示该怪癖单独配置的风味描述。
- 开启后需要为该怪癖的描述准备对应本地化；不能只依靠 Buff 的自动描述。
- 可与 `show_explicit_buff_description: true` 同时存在，即同一个怪癖可以同时显示风味描述和具体 Buff 描述。
- 按现有观察，风味描述似乎显示在 Buff 描述上方；该上下顺序暂以“实测印象、待进一步确认”记录。

## `show_explicit_curio_tag_description`

```json
"show_explicit_curio_tag_description": true
```

该字段当前仅能作有限说明：它疑似只在怪癖具有奇物强制互动倾向时有用，用于显示与该奇物 Tag 相关的明确说明；具体显示文本、显示位置和所有触发条件尚未确认。

这里的“手贱”是社区口语，指：具有该怪癖的英雄经过特定类型的奇物时，有概率不经玩家主动命令便自行与奇物互动；其互动方式等同于玩家主动让该英雄**空手触摸**该奇物。

与此相关的怪癖字段通常还包括：

```json
"curio_tag": "<奇物tag>",
"curio_tag_chance": 0.0
```

但当前资料尚不足以仅凭字段名断言三者的完整联动公式。编写具有手贱行为的新怪癖时，应优先仿照原版相同用途条目，并将未确认部分保留为待实机验证。

## 组合关系

| 配置 | 怪癖悬停时的预期展示 |
|---|---|
| 仅开启 `show_explicit_buff_description` | 显示引用 Buff 的具体效果，顺序同 `buffs` 数组 |
| 仅开启 `show_flavor_description` | 显示需单独本地化的怪癖风味描述 |
| 两者同时开启 | 两类描述同时存在；风味描述疑似位于 Buff 描述上方 |
| 开启 `show_explicit_curio_tag_description` | 疑似补充显示手贱/奇物 Tag 相关说明，具体行为未完全确认 |

## `is_positive` 与 `is_disease`

```json
"is_positive": true,
"is_disease": false
```

- `is_positive` 决定该条目属于正面怪癖还是负面怪癖：`true` 为正面怪癖，`false` 为负面怪癖。
- 怪癖在游戏界面中的颜色会随其类型变化，因此该字段会间接影响正面/负面怪癖的颜色表现；它不是一个单独填写颜色 ID 的字段。
- `is_disease` 决定该条目是否属于疾病。
- 当 `is_disease: true` 时，条目按疾病处理；现有理解是此时 `is_positive` 应当失去实际意义。该点暂以强经验结论记录，若今后发现“正面疾病”等反例应再修订。
- 不得仅凭 `is_positive` 推断一个疾病会按普通正面或负面怪癖占槽、替换或治疗。

## `classification`：自然获得倾向

```json
"classification": "physical"
```

当前官方实例只确认两种常见值：

```text
physical
mental
```

`physical` 表示生理类，`mental` 表示心理类。先区分“出本时是否获得红癖、黄癖或疾病”与“获得哪一个具体条目”；分类对获得倾向的影响，不等于已经掌握这两步各自的概率公式。

**出本红癖的定性参考（2026-11-19 记录，非本轮实测或精确算法）**：

| 情形 | 暂记的获得倾向 | 证据与边界 |
|---|---|---|
| 高压力出本 | 更容易获得 `mental` 类红癖 | 知识库编写者明确表示记得这一规律；按经验记忆保留，未提供本轮对照测试、阈值或权重 |
| 低剩余生命值出本 | 更容易获得 `physical` 类红癖 | 知识库编写者转述听说过这一规律；官方指南也提到低血量出本偏向 `physical` 怪癖，但未单独明确红癖的算法 |
| 黄癖、疾病 | 上述分类倾向是否同样适用，暂不确定 | 不得把红癖的经验直接推广，也不得反过来声称黄癖或疾病不受分类影响 |

来源与状态：

- 知识库编写者于 2026-11-19 说明：“我确实记得高压出本更容易获得mental类红癖，我也听说过低血出本更容易得physical类红癖，但黄癖和疾病我不确定，先记录一下大概吧”。本条保留的是定性经验与转述，不升级为实测确认。
- 红钩《Darkest Dungeon - Modding Guide [Official]》的 Quirks / `classification` 行明确提及低剩余生命值出本时更容易获得 `physical` 怪癖；紧接着的 `mental` 说明在网页中未写完整，不能自行补全为官方高压结论。指南最后更新于 2017-07-10，不能据此声称当前引擎已重新验证。来源：<https://steamcommunity.com/sharedfiles/filedetails/?id=819597757>。
- 完整证据与本次修订边界见 `Sources/quirk_classification_tendency_20261119.json`。原先笼统的“心理怪癖更容易受压力阈值影响”收紧为上表的红癖定性记忆；原先“除获得倾向外不影响其他机制”不再作为已证实的穷尽结论。

目前没有证据支持仅凭 `classification` 推导以下机制：

- 限制怪癖只能在哪一座城镇建筑中治疗；
- 决定怪癖能否被移除或锁定；
- 改变怪癖 Buff 的实际效果；
- 为疾病额外增加治疗规则。

原版黄癖、红癖和疾病均有 `physical` 与 `mental` 条目；这些分类不是正负面或疾病身份的替代字段。疾病的身份仍由 `is_disease` 决定，不能仅凭 `classification` 判定；原版存在分类字段也不能单独证明出本疾病选择实际使用了它。

完整的出本随机授予公式、压力或生命值阈值、两种分类的权重变化、作用于获得判定还是候选选择的具体环节，以及栏位已满时的替换规则均未确定；需要精确复刻时另行调查，不得补造数值。

## `curio_tag` 与 `curio_tag_chance`：奇物“手贱”

```json
"curio_tag": "kleptomaniac",
"curio_tag_chance": 0.4
```

当前理解如下：

- `curio_tag` 指定该怪癖会尝试主动互动的奇物类型 Tag。
- 具有该怪癖的英雄经过带有对应 Tag 的奇物时，按 `curio_tag_chance` 判定是否触发“手贱”。
- `curio_tag_chance` 按 `0～1` 的概率比例理解，例如 `0.4` 表示约 `40%`。
- 判定成功后，英雄自行执行一次等同于玩家让该英雄**空手触摸**该奇物的互动，而不是自动选择或消耗补给品。
- 当 `curio_tag` 为空字符串、`curio_tag_chance` 为 `0` 时，通常表示没有这类定向主动互动行为。

字段本身是单个 JSON 字符串而不是数组。结合现有结构，当前应按“一个怪癖条目只能直接填写一个 `curio_tag`”理解；若希望覆盖多个 Tag，不得把多个值强塞进同一字符串，应考虑多个怪癖或其他已验证结构。由于尚未完成专门的多 Tag 实机测试，这一点保留为强结构推断，而不表述成已逆向确认的引擎上限。

与 `show_explicit_curio_tag_description` 的完整联动仍不完全明确。现阶段可以认为后者用于控制是否在怪癖悬停说明中明确展示相关奇物倾向，但具体生成文本与显示条件仍待确认。

## `tags`：怪癖标签列表

```json
"tags": [
  "example_tag_a",
  "example_tag_b"
]
```

- `tags` 是数组，一个怪癖可以同时填写多个 Tag。
- 这些 Tag 疑似会被“怪癖进化速度”一类 Buff 或机制用作筛选条件。
- 当前尚未确认具体由哪些 Buff 类型、Effect、城镇事件或其他系统读取，也未确认 Tag 是否可以完全自定义。
- 因此，除照抄已有实例或经过专项测试外，不得把某个自定义 Tag 断言为必定会被游戏机制识别；更不得仅凭字段名补造怪癖进化、分类或触发规则。

## `buffs`：怪癖附带的 Buff 列表

```json
"buffs": [
  "example_quirk_buff_a",
  "example_quirk_buff_b"
]
```

英雄持有该怪癖期间，`buffs` 数组中引用的所有 Buff 都会附着在该英雄身上并持续参与结算：

- 数组元素填写 Buff ID，必须能在 Buff 定义中找到对应条目；
- 这些 Buff 的来源为 `bsrc_quirk`；
- 怪癖被移除时，由该怪癖附带的 Buff 也随之移除；
- 怪癖被锁定只会保护怪癖不被新怪癖顶掉，不会停用、强化或以其他方式改变这些 Buff；
- 当 `show_explicit_buff_description: true` 时，悬停怪癖所显示的 Buff 描述顺序与 `buffs` 数组的引用顺序一致。

实际结算顺序推测也与数组书写顺序一致，但当前没有足够证据将其列为严格时序保证。因此：

- 可以按人类阅读与逻辑依赖顺序排列 Buff；
- 不得让关键迂回、驱散链或瞬时条件依赖尚未确认的怪癖 Buff 严格结算顺序；
- 若多个 Buff 的先后会改变结果，应改用已有明确时序保障的 Effect 链或进行专项测试。

## `slot_size`：怪癖/疾病槽位占用量

```json
"slot_size": 1
```

`slot_size` 决定该怪癖或疾病占用多少个对应类型的槽位。

### 常规值

- 大多数原版普通怪癖没有显式书写该字段；结合其正常占用一个槽位的行为，省略时应按默认值 `1` 理解。
- `slot_size: 0`：条目实际不占用怪癖/疾病槽位。
- `slot_size: 1`：占用一个槽位。
- 更大的正整数：占用对应数量的槽位。

猩红诅咒的多个阶段均使用：

```json
"slot_size": 3
```

原版在未修改全局规则时，英雄的疾病槽位上限为 `3`。猩红诅咒占满全部三个疾病槽，因此英雄获得猩红诅咒后不能再自然获得其他疾病；这正是原版利用 `slot_size` 实现的机制，而不是猩红诅咒另有一条独立的“禁止其他疾病”规则。

### 大于槽位上限的条目

若某怪癖的 `slot_size` 大于对应类型的槽位总上限，常规情况下该怪癖无法获得。例如槽位上限为 `5`、新怪癖 `slot_size: 6` 时，正常空槽不足，条目不会出现。

但怪癖替换流程存在一个特殊边界：若英雄已有四个锁定怪癖和一个未锁定怪癖，则 `slot_size: 6` 的新怪癖仍有可能顶替那个未锁定怪癖。这里的锁定既包括怪癖本身天然不可被顶替，也包括在疗养院中被玩家锁定。由此可知，不能只用“新条目尺寸必须小于等于槽位上限”概括所有替换行为。

该异常替换的完整算法、为何尺寸超过总上限仍能在这种局面进入，以及替换后内部槽位计数如何保存，目前未完全逆向；创作时不应依赖此边界实现稳定功能。

### `slot_size: 0` 的重启行为与风险

`slot_size: 0` 可作为不占常规槽位的特殊迂回，但存在类型相关的重启行为：

- **正面怪癖（黄癖）**：当英雄持有的非 `slot_size: 0` 黄癖的**数量**等于正面怪癖栏位上限时，游戏重启后，`slot_size: 0` 的黄癖会消失。判定条件是怪癖数量，不是各怪癖占用槽位数的总和。
- 若非 Size-0 黄癖的数量少于该上限，即使其中存在 `slot_size > 1` 的黄癖、看起来已经占满全部黄癖栏位，`slot_size: 0` 黄癖也不会因此在重启时自动消失。此数量边界来自迂回表第 4 条 P375/X401，经当前用户于 2026-11-02 确认，用于修正原先笼统的“黄癖槽满”说法；非本轮新增实机测试，不据此补造存档序号的底层实现。
- 这里的“游戏重启”包括：
  - 退回主菜单后重新进入存档；
  - 完全关闭游戏后重新启动并进入存档。
- **负面怪癖（红癖）和疾病**：目前没有发现上述黄癖的重启自动消失特性。

**非 Size-0 怪癖数量少于对应栏位上限时的显示规则**：设该数量为 N、对应上限为 L，N < L 时，重启后最多 L−N 个 Size-0 怪癖会与**最后一个**非 Size-0 怪癖重叠在同一行，即使有多个也会叠在一起。此规则来自迂回表第 4 条 P376/X403，经当前用户于 2026-11-02 确认，替换原先笼统的“全部位于第一个怪癖位置”的说法。这里确认的是该条件下的显示规则，不推断超过该数量的条目去向，也不外推 N 为 0 时不存在“最后一个”非 Size-0 怪癖的显示结果。负面怪癖数量已达上限的情况不由此段覆盖。

**非 Size-0 负面怪癖数量等于对应栏位上限时**：Size-0 红癖在重启后仍然存在，并与**第一个未锁定的非 Size-0 红癖**重叠。此为迂回表第 4 条 P379/X407 的最后更正，经当前用户于 2026-11-02 确认；P377、P378 的删除线旧文不得作为现行依据。原段未说明所有非 Size-0 红癖均锁定时的显示位置，暂不推断。本条为当前用户确认，非本轮新增实机测试。

Size-0 怪癖或疾病在界面上的显示和互动碰撞箱可能重叠，妨碍玩家正确悬停或选择相应条目；不能只把它当作视觉问题。

### 设计要求

1. 普通怪癖若无特殊需求，省略 `slot_size` 或显式写 `1`。
2. 使用 `0` 前必须接受重启后的排序重叠风险。
3. 不得将 `slot_size: 0` 黄癖视为可靠的永久隐藏槽外怪癖；非 Size-0 黄癖的数量等于正面怪癖栏位上限时，重启会使其消失。不能只根据 `slot_size` 总占用量是否已满作判断。
4. `slot_size: 0` 红癖和疾病虽未发现同类消失行为，仍存在重启后显示及碰撞箱重叠的问题；具体重叠位置必须按相应数量条件判断，不能统一说成第一个怪癖。
5. 不得依赖大于槽位上限的怪癖在特殊锁定布局下顶替成功；该行为只作为已观察边界记录。

### Size-0 临时怪癖与“进化到空”

Size-0 怪癖可用于必须借助怪癖机制承载的临时效果，例如饰品与临时怪癖绑定。此处只记录用途，不据此补造具体 Mod 的实现或执行时序。

进化式怪癖需要“进化到空”时，目标必须是 **ID 真实存在、名称本地化文本为空、无内容、`slot_size: 0` 的正面怪癖**。当前用户于 2026-11-02 明确：“无标题”指名字的本地化文本为空；不是怪癖 ID 为空，也不是缺少怪癖定义或省略名称本地化。

- 目标 ID 为 `""`（空字符串）时，怪癖不会进化。
- 目标 ID 不存在时（原表示例为 `" "`，内含单个空格），会使该英雄在战斗内卡死，无法使用任何技能，包括跳过回合；不得用这种写法实现“进化到空”。
- 进化目标的 ID 必须能解析到真实的怪癖定义；名称本地化文本为空和无内容不能替代该定义。
- 该 Size-0 黄癖后续在重启时自动消失，仍须满足上文的数量条件：非 Size-0 黄癖数量等于正面怪癖栏位上限。不能把进化成功、界面无内容或槽位占满等同于已删除目标怪癖。

依据：迂回表第 4 条 P381/X411、P382/X412，经当前用户于 2026-11-02 确认完整边界。此为方案与风险确认，非本轮新增实机测试；不补造进化触发字段、完整配置或任意场景下的结算时序。

## `can_remove_with_camping_skill`：扎营技能移除疾病

```json
"can_remove_with_camping_skill": false
```

该字段与扎营技能移除条目有关，但必须区分普通怪癖与疾病：

- 目前没有发现能够直接移除普通正面/负面怪癖的扎营技能效果；
- 疾病则确实可能被扎营技能移除；
- 因此，该字段当前主要应按“该疾病是否允许被相应扎营技能移除”理解。

不得因为字段位于通用怪癖条目结构中，就声称游戏已经存在可删除红癖或黄癖的扎营效果。对非疾病条目设置该字段是否会在自定义机制中产生其他作用，目前未确认。

该字段只涉及扎营技能路径，不会让条目全局不可移除。疗养院 Activity、奇物、Effect、城镇事件等方式仍按各自机制以及其他字段判断。

## `can_be_replaced_by_new_quirk`：能否被新怪癖顶掉

```json
"can_be_replaced_by_new_quirk": false
```

该字段决定英雄在获得新怪癖、需要替换已有怪癖时，本怪癖能否成为被顶掉的旧条目：

- `true`：可以被后来获得的新怪癖顶掉；
- `false`：不会在这种怪癖替换流程中被新怪癖顶掉。

该字段只控制“被新怪癖替换”的资格，不等于全局不可移除。疗养院治疗、奇物、Effect、事件等能否删除该怪癖，应分别判断。

锁定怪癖在这一点上的行为，某种意义上相当于令该怪癖不可被新怪癖顶掉，即表现近似 `can_be_replaced_by_new_quirk: false`。但“锁定”仍是独立的游戏状态，不能据此把两者描述成底层完全相同的字段实现，也不能假定它们在费用、界面与其他怪癖处理上完全等价。

## `can_modify_in_activity`：城镇活动能否治疗/移除

```json
"can_modify_in_activity": false
```

该字段限制的是通过城镇 Activity 对怪癖进行修改。当前理解中，这里的“修改”主要指怪癖的治疗或移除：

- `true`：允许通过相应城镇活动治疗/移除该怪癖；
- `false`：不允许通过这类城镇活动治疗/移除该怪癖。

“锁定正面怪癖”似乎不受该字段控制，但这一边界尚未完全确认。因此不得仅凭 `can_modify_in_activity: false` 断言怪癖一定不能在疗养院锁定；需要精确处理锁定功能时应另查锁定相关字段或实机行为。

该字段只约束 Activity 路径，不能把怪癖变成全局不可移除：

- 奇物互动随机删除负面怪癖等其他怪癖移除效果不受它限制；
- Effect、事件及其他非 Activity 机制能否移除怪癖，应按各自机制判断；
- 因此，若设计要求怪癖无论通过什么方式都绝对无法移除，单独设置该字段为 `false` 并不足够。

社区常将正面怪癖俗称为“黄癖”，将负面怪癖俗称为“红癖”。文档或设计稿出现这些称呼时，应分别映射为 positive quirk 与 negative quirk；不得将“红癖”误解为疾病。

### 疗养院医疗室一次治愈全部疾病的配置

`campaign/town/buildings/sanitarium/sanitarium.building.json` 的 `disease_treatment` 活动用 `disease_quirk_cure_all_chance_upgrades` 配置一次治完所有可治疗疾病的概率。每条 `chance` 写小数概率，升级档通过 `upgrade_tree_id` 与 `upgrade_requirement_code` 指向升级节点。原版数值见[疗养院医疗室治病](../Reference/vanilla_raid_tables.md#疗养院医疗室治病)。

疾病在医疗室的治疗资格受 `can_modify_in_activity` 限制。原版猩红诅咒的四种状态均写 `false`。扎营技能的治疗资格由 `can_remove_with_camping_skill` 控制，详见[扎营技能治病](49-扎营技能文件、通用专属分类与图标.md#治愈疾病-remove_disease)。

## `keep_loot`：手贱奖励被英雄私吞

```json
"keep_loot": true
```

该字段与怪癖触发的奇物主动互动有关：

- `keep_loot: true` 时，由这次奇物互动产生的奖励会表现为“被英雄收下”。
- 玩家能够看见生成的奖励，但无法将其拿走；从玩家实际收益看，等同于这些奖励被强制丢弃。
- `keep_loot: false` 时，不启用上述私吞处理；奇物奖励按常规互动流程供玩家取得。

原版明确实例包括：

| 怪癖 ID | `curio_tag` | `curio_tag_chance` | `keep_loot` |
|---|---|---:|---|
| `tapeworm` | `Food` | `0.60` | `true` |
| `kleptomaniac` | `Treasure` | `0.35` | `true` |
| `egomania` | `Reflective` | `0.40` | `true` |

因此，`keep_loot` 不应仅按字段字面翻译成“保留战利品”而省略其玩家侧结果；准确说明应包含“英雄私吞，玩家看得见但拿不到”。其是否会影响没有 `curio_tag` 主动互动的其他奇物调用方式，当前未单独确认，创作时应将它用于同类手贱怪癖结构。

## `incompatible_quirks`：怪癖定向互斥

```json
"id": "A",
"incompatible_quirks": [
  "B"
]
```

`incompatible_quirks` 填写与本怪癖不兼容的怪癖 ID。现有结论不能把该列表视为天然双向关系：

- 当英雄已经持有怪癖 `A`，随后尝试获得 `A.incompatible_quirks` 中列出的怪癖 `B` 时，`B` 一定不会真正出现。
- 只在 `A` 中列出 `B`，并不能据此确认“已经持有 `B` 后再获得 `A”时也会被阻止。
- 已经持有 `B` 的英雄获得 `A` 时，究竟是 `A` 被阻止、`B` 被替换/移除，还是发生其他处理，目前未知。

因此，需要可靠实现双向互斥时，建议显式在双方列表中分别填写对方：

```json
{
  "id": "A",
  "incompatible_quirks": ["B"]
},
{
  "id": "B",
  "incompatible_quirks": ["A"]
}
```

这是规避未确认单向边界的安全写法，不应表述成“引擎硬性要求所有互斥都必须双向填写”。不得在没有测试的情况下断言单向定义会移除英雄已经持有的旧怪癖。

## `random_chance`：随机抽取权重

```json
"random_chance": 1
```

- `random_chance` 是该怪癖参与随机怪癖抽取时使用的**相对权重**，不是固定百分比，也不只是布尔式的“是否允许随机获得”。
- 可以填写小数，也可以填写大于 `1` 的值。
- 权重必须和同一候选池内其他符合条件的怪癖一起比较。例如两个怪癖的权重分别为 `0.5` 和 `2`，在忽略其他筛选条件时，其相对抽取比例应按 `0.5:2` 理解，而不是分别解释成 `0.5%` 和 `2%`。
- `random_chance: 0` 表示该怪癖在常规随机抽取中的权重为零；它仍可能被 Effect、城镇事件或其他定向机制直接授予，不能据此断言该怪癖绝对无法取得。
- 负数权重的引擎行为未知。创作时不得使用负数，也不得推测它代表反向权重或禁止获取。

## Agent 审查要求

1. 不得把 `show_explicit_buff_description` 当成 Buff 是否生效的开关。
2. 开启 `show_flavor_description` 时，必须检查对应怪癖描述本地化是否存在。
3. 多个 Buff 的说明顺序应按 `buffs` 数组顺序理解，不得自行重排。
4. `show_explicit_curio_tag_description` 的完整语义尚未确认，不得按字段名补造确定规则。
5. “手贱”只描述英雄自动空手互动奇物的行为，不等于玩家主动使用补给品与奇物互动。
