## 英雄技能如何被识别为友方技能

英雄 `combat_skill:` 的 `.target` 决定技能指向敌方还是友方：

- 完全不写 `.target`：该技能必定被识别为指向英雄自身的友方技能；
- 写出 `.target`，但参数为空：等同于没有填写 `.target`，同样是指向英雄自身的友方技能；
- `.target` 参数带有 `@` 前缀：该技能指向友方，例如 `@12` 表示友方一、二号位是可选目标范围。

`@12` 本身不表示 AOE；它表示可以在友方一、二号位中选择目标。是否群体作用仍须由具体技能与目标表达式另行判断。

示意：

```darkest
// 未填写 target，指向英雄自身
combat_skill: .id "self_friendly_skill" .level 0 .launch 1234

// target 参数为空，效果等同于未填写 target
combat_skill: .id "empty_target_friendly_skill" .level 0 .launch 1234 .target

// 指向友方一、二号位的可选目标
combat_skill: .id "ally_friendly_skill" .level 0 .launch 1234 .target @12
```

## 增援的基础时间条件与加速

常规拖延增援按**整轮**统计全队的合格技能使用次数，不是按英雄个人回合统计。区分**开始计时、重置计时、压力惩罚、实际召怪**；原版默认数值与「二回合／三回合增援」的时序见[原版副本数据速查表](../Reference/vanilla_raid_tables.md#常规拖延与增援)。

| 配置位置 | 用途与边界 |
|---|---|
| `shared/rules.json` 及难度规则 | `stall_number_of_invalidating_skills_threshold` 可调同轮所需的防增援技能次数；`stall_party_size_threshold` 可调英雄侧门槛，同处还有敌方门槛 `stall_enemy_size_threshold`。历史《全局规则整理》将两侧门槛解释为存活单位体积和，不能拿原版常规 Size 1 英雄的“人数”表述套所有 Mod 阵容。 |
| 同上 | `stall_round_stress_effect_threshold`、`stall_round_summon_effect_threshold` 分别配置压力和召怪阈值；另见 `stall_round_reset_threshold`、`stall_extra_round_size_threshold`、`stall_extra_round_size_amount`、`stall_round_accelerated_only_consecutive_increment`、`stall_round_accelerated_only_increment` 和 `stall_stress_effect_name`。这些字段的精确组合与边界不能仅凭名字反推。 |
| 怪物 `.info.darkest` 的 `battle_modifier:` | `.accelerate_stall_penalty true` 标记加速，`false` 不加速；`.disable_stall_penalty true` 表示禁止常规拖延增援，`false` 不由该字段禁止。原版混合加速与非加速时按较慢一档，存在阻止增援的怪物时优先阻止（视频观察）。撤回旧文“只要有一只加速怪就加速”的说法。 |
| `campaign/quest/quest.plot_quests.json` | 遗迹教学任务实例在外层 `plot_quests[]` 条目写 `"is_stall_enabled": false`，不在内层 `quest`。不能据此给老路或其他调用域推定同一开关。老路专属入口未定位，也未实测改法。 |
| 地区 `.mash.darkest` | `stall:` 定义地区的拖延增援阵容池，与触发条件或倒计时不是同一配置。 |

原版大型怪物、Boss 等无增援实例不能证明 Size、Boss 身份和 `.disable_stall_penalty` 是同一个条件；分析 Mod 时应分别核对。无尽农庄进度条增援是另一机制，不由上述拖延规则阻止，见[专题 74](74-无尽任务心控怪物与增援风险.md)。

## 友方技能无法阻止增援

`.is_stall_invalidating` 是英雄侧技能字段，默认值为 `true`。在攻击技能等适用场合，它用于参与拖延／增援判定；但**友方技能是明确例外**：

- 友方技能写 `.is_stall_invalidating true`，仍然无法阻止增援；
- 友方技能写 `.is_stall_invalidating false`，同样无法阻止增援；
- 友方技能省略该字段，仍然无法阻止增援。

因此，不能通过切换、补写或省略 `.is_stall_invalidating`，让友方技能获得阻止增援的能力。判断技能是否能拖延增援时，必须先判断它是不是友方技能；一旦属于友方技能，该字段怎样填写都不能改变结果。

敌方目标技能是否计入防增援，不由伤害修正 `.dmg` 判定。无伤害的敌方技能可以计入；带伤害的技能若写 `.is_stall_invalidating false`，则不计入。不能把面向原版游戏玩家的“用输出技能防增援”简化成技能制作规则。

## 与无等级共用分行的关系

若某等级的第一条 `combat_skill:` 定义没有有效 `.target`，仅在同等级后续分行或无等级共用行填写目标，仍视为未写目标，按指向自身的友方技能处理，无法阻止增援。非自身目标应在每个等级的第一条定义填写非空 `.target`；其余分行无须重复填写，下方无等级行可覆盖已建立的目标站位。详见[技能同 ID 分行与无等级共用分行](37-技能同ID分行与无等级共用分行.md)。

## Agent 实现检查

1. 英雄技能最终是否具有参数非空的有效 `.target`？
2. 若没有有效 `.target`，是否已经按“指向英雄自身的友方技能”理解，而不是当作待补字段或敌方技能？
3. `.target` 是否带 `@`；若是，是否按友方目标理解，并避免把可选站位误判为 AOE？
4. 技能若为友方技能，是否没有错误声称 `.is_stall_invalidating true` 能阻止增援？
5. 是否按整轮统计合格技能次数，检查当前难度的规则配置，并区分计时、压力与召怪？
6. 是否分别核对双方体积、怪物的加速／禁用设置及任务开关，而不是把原版实例或“出现一只加速怪”当成通用条件？
7. 使用无等级共用分行时，是否已检查每个等级行的 `.target` 特殊合并规则？
## 友方技能的暴击边界

当前用户于 2026-10-10 经测试确认：友方技能不可暴击；至少不会获得普通攻击技能暴击带来的 `20%` Effect 概率加成。因此，不应再把友方技能视为可能暴击，也不应把友方技能的 `.crit` 当作会提高其 Effect 概率的字段。

这里的“友方技能不可暴击”与治疗暴击是两个独立问题：治疗暴击由治疗 Effect 的 `.can_crit_heal` 与治疗源等机制决定，不能用友方技能的暴击规则解释，也不能把二者混称。此前关于友方技能可能暴击、可能提高 Effect 概率、或需要用 `.is_crit_valid false` 防止友方技能暴击的描述已撤回。

## 攻击技能的 `.atk` 与 `.can_miss`

当前用户于 2026-10-10 确认，在攻击技能场景中：

- 即使写 `.can_miss false`，如果没有声明 `.atk`，技能仍无法命中目标；
- 在该 `.can_miss false` 场景中，只要声明了 `.atk`，即使写为 `.atk 0`，也会必定命中目标。

因此，`.can_miss false` 不能替代 `.atk`；这里的结论限定于当前确认的攻击技能调用场景，不外推到友方技能、反击、道具或其他非普通攻击调用方。
