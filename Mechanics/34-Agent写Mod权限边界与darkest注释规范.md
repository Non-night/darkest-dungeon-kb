# Agent 写 Mod 的文件权限与注释规范

## 权限从用户任务而来
知识库只提供技术依据，不自动授予文件写入权限。

- 用户只要求阅读、解释、审计、比较或提出方案时：默认只读，不修改任何 Mod。
- 用户明确要求创建、实现、修复或完善某个 Mod 时：可在用户明确指定的**目标 Mod 根目录**内进行完成该任务所必需的写入。
- 目标 Mod 不明确时，不得猜测并修改任意 Mod；应先根据上下文可靠定位，无法定位时再询问用户。
- 用户明确限制修改范围时，以用户限制为准；不得因为某个文件“顺便能修”就越界。
- 实现机制时还必须遵守目标最小化：没有绝对必要时，任何 Effect 都不得作用于设计范围之外的目标；不得用群体目标代替单体目标来绕开简写限制或崩溃组合。

## 写 Mod 时允许创建或修改
在用户已经明确要求实现目标 Mod 的前提下，可以在该 Mod 根目录内创建或修改与需求直接相关的配置，例如：

```text
effects\*.effects.darkest
shared\buffs\*.buffs.json
heroes\<hero_id>\*.info.darkest
heroes\<hero_id>\*.art.darkest
upgrades\heroes\*.upgrades.json
campaign\...
raid\...
trinkets\...
localization\*.string_table.xml
```

也可以创建实现机制所需的标准目录。允许内容包括：

- 为设计功能创建自定义 Effect ID、Buff ID及其定义；
- 在 Info、饰品、ActorDot、spawn、城镇事件等调用位置补齐引用；
- 创建升级、初始补给、事件、区域建筑、战斗技能和本地化源文件；
- 修复目标 Mod 内与用户要求直接相关的缺失引用、参数、路径和定义闭包；
- 为新 Mod 创建必要的 `project.xml` 和 `preview_icon.png`，前提是任务确实要求创建完整 Mod。

设计稿通常描述效果而不是最终代码。只要目标、数值、持续时间和条件足够明确，Agent 应自行命名稳定的自定义 ID 并创建定义；不能回复“设计没有提供现成 Buff/Effect 定义，所以未实现”。

## 自定义定义优先与原版 ID 隔离
写 Mod 时，**永远不得优先复用原版已经存在的 Effect 或 Buff**。即使某个原版定义当前看起来与设计需求完全一致，默认实现仍应：

1. 使用目标 Mod 的统一前缀创建新的、唯一的 Effect/Buff ID；
2. 在目标 Mod 自己的 `effects\*.effects.darkest` 或 `shared\buffs\*.buffs.json` 中完整定义；
3. 让目标 Mod 的技能、饰品、附魔 Buff、ActorDot 等只引用这些自定义 ID。

原因是直接引用原版 ID 会把当前 Mod 的行为绑定到外部定义：同名 Effect 可能被其他文件分行追加或修改，同 ID Buff 也可能被其他 Mod 或后续加载内容覆盖。这样即使当前 Mod 自身没有改动，也可能因加载顺序、兼容补丁或其他 Mod 对原版定义的修改而改变行为。

不得为了少写代码而：

- 直接引用“效果看起来相同”的原版 Effect/Buff；
- 对原版 Effect 使用相同 `.name` 进行分行追加；
- 使用原版 Buff ID 创建覆盖定义；
- 把当前 Mod 的核心机制建立在“原版该 ID 永远不会被修改”的假设上。

只有当用户明确要求复用原版定义，或者某项引擎机制必须依赖特定原版特殊 ID、无法通过新的自定义 ID 等价实现时，才可以例外使用；此时必须说明依赖关系与兼容风险。原版代码可以作为字段写法和数值结构的参考，但应复制所需结构并更换成目标 Mod 的唯一 ID，而不是直接复用其引用。

## 修改目标 Mod 时的最小变更原则
- 只修改实现当前需求所必需的文件和字段。
- 保留用户已有的 ID、注释、文件布局和未涉及机制。
- 新 ID 使用目标 Mod 统一前缀，避免与原版、DLC 和其他 Mod 冲突；默认创建自定义 Effect/Buff，不复用原版已有 ID。
- 完成前检查所有 Effect、Buff、ActorDot、技能、饰品和事件引用是否能找到定义。
- 阅读或编写 `localization\*.string_table.xml` 时，不得把所有 `<entry id="...">` 都视为可任意命名的普通文本键。必须结合 ID 前缀、固定后缀、对应的 Buff rule/stat、技能/饰品/事件引用以及原版同名条目，判断它是引擎固定格式条目、覆盖修复条目还是 Mod 自定义引用；同时检查正文中的格式化占位符。无法解释某个 ID 的消费位置或命名组成时，应把它列为知识缺口。
- 不得只创建空目录或空 Header 后宣称功能已实现。
- 存在行为歧义时，应选择已有知识支持的保守实现并说明；只有歧义会实质改变设计且无法合理判断时才需要询问。

## 不建议顺手进行的修改
除非与当前需求直接相关，不建议：

- 对整个 Mod 批量重排、格式化或改名；
- 改动大量既有 ID，并迫使所有引用连锁更新；
- 为了“整洁”删除看似未引用但可能供兼容或外部 Mod 使用的定义；
- 使用空格、标点、非稳定特殊字符作为 `*.effects.darkest` 或 `*.buffs.json` 的文件名前缀；
- 创建与原版文件完全同名、从而可能意外覆盖原版的定义文件；
- 直接手工修改编译产物 `*.loc2`，而不是维护本地化 XML 源文件；
- 在没有对应工具和任务需求时改写 `.skel`、`.bank` 等二进制资源；
- 为了补一项代码功能顺带替换角色图片、音频或其他表现资源；
- 未经说明更改现有 Mod 的标题、发布 ID、版本、可见性和上传模式。

## 未经用户允许不得修改
写 Mod 的授权只覆盖明确目标 Mod，不覆盖其他内容。未经用户明确允许，不得修改：

- `DarkestDungeon` 游戏本体文件；
- 官方 DLC 文件；
- 目标以外的本地 Mod；
- Workshop 中的其他 Mod；
- 插件、语法检查器、生成器、辅助软件及其源码；
- 知识库自身；
- 用户的设计稿、教学文档、表格和其他源资料；
- 目标 Mod 根目录之外的任意项目；
- 用户没有要求处理的二进制、美术和音频资源。

未经允许也不得执行大范围删除、移动、重命名或覆盖。若用户只要求检查现有 Mod，必须保持只读。

## Effect 与 Buff 文件位置
### Effect
```text
effects\<自定义前缀>.effects.darkest
```

- 前缀可自定义，必须非空。
- 通常只使用英文字母、数字和下划线；避免特殊字符。

### Buff
```text
shared\buffs\<自定义前缀>.buffs.json
```

- 前缀可自定义，必须非空。
- 同样建议使用稳定、无特殊字符的前缀。

创建引用时必须同时创建定义文件；不能让 Info 或饰品引用一个不存在的自定义 Effect/Buff。

## `.darkest` 注释规范
`.darkest` 使用 `//` 注释，但注释必须独立成行：

```darkest
// 一级技能减益

effect: .name "AAA Debuff 1" .target "target" .chance 100% .duration 3 .combat_stat_buff 1 .attack_rating_add -5 .on_hit true .on_miss false
```

禁止行内注释：

```darkest
effect: .name "AAA Debuff 1" .target "target" // 一级技能减益
```

行内注释存在引擎识别异常风险。知识库中的 `.darkest` 示例也不得使用 `...` 作为省略号。

### 罕见的独立注释识别异常
独立行注释一般应正常使用，以保证可读性。但若用户反馈：

- 某条注释之后的多条定义都像没有写入；
- 从某一注释下方开始，技能、Effect 或 Header 连续不被识别；

应把该注释列为排查对象，暂时删除、重新输入或移动注释，再检查后续内容是否恢复。这类问题不常见，正常写代码时无需因此取消必要注释。
