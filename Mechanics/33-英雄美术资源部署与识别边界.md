## Art 字段引用的是动画名
英雄 `*.art.darkest` 中涉及动画的字段，例如：

```darkest
combat_skill: .id "skill_id" .anim "attack_cast" .fx "skill_fx" .targfx "target_fx" .targchestfx "target_chest_fx"
```

`.anim` 指定 Skeleton 内部的**动画名**，不是 `.skel`、`.atlas` 或 `.png` 文件名。其他 FX 调用字段须按各自的资源查找规则核对；不能从 `.anim` 的语义直接断言 `.targfx` 等字段必须对应某个同名内部动画。尤其 `.targfx` 当前只确认调用名与 FX 文件中缀一致，其内部动画名未确认，见下文专项边界。

文件通常按相同中缀命名，使动画名和资源组容易对应，例如：

```text
Art:   .anim "attack_pistol"
Skel:  highwayman.sprite.attack_pistol.skel
Atlas: highwayman.sprite.attack_pistol.atlas
动画:  attack_pistol
```

判断 Art 引用是否存在时，应核对 `.skel` 内的实际动画名，模式差分按下一节核对。当前用户于 2026-11-21 明确 `.anim` 必须匹配内部动画名。资源文件中缀是否也必须匹配仍未确认，推荐沿用原版惯例，至少保留一组中缀与 `.anim` 同名的 `.skel/.atlas`。

复制原版职业时可以保留 `.anim` 值、资源中缀和内部动画名，只迁移职业绑定的文件前缀。若需要重命名内部动画，用兼容版本的 Spine 编辑工程，或用支持该版本的转换器编辑数据并写回游戏可读的 Spine 2.1.27 `.skel`。随后更新所有相应 Art 动作引用，按推荐命名一并更新 `.skel/.atlas` 的共同中缀。十字军 `attack_sword` 同时用于技能 `.anim` 与 `.attack_friendly_anim`。依据见 `Sources/tutorial_corrections_20261121.json`。

## 动画名的模式差分与默认动画

知识库编写者确认（2026-09-24）：`.anim` 后填写动画名，不是动画文件名。技能/Art 中 `.anim` 仍写基础动画名；若当前模式 ID 为 `aaa`，Skeleton 中可以提供 `<动画名>_aaa`，引擎会在该模式调用时自动识别对应模式后缀动画。例如：

```darkest
combat_skill: .id "example_skill" .anim "xxx"
```

```text
Skeleton animation: xxx_aaa
当前 mode ID: aaa
```

如果同一动画要被多个模式使用，且这些模式使用的动画内容相同，则只提供不带模式后缀的基础动画名（如 `xxx`），不必为每个模式重复制作 `xxx_<mode_id>`；不带模式 ID 后缀的动画作为全模式共用的默认动画。若各模式动画内容不同，则按对应模式 ID 提供 `<动画名>_<mode_id>`。不要把模式后缀写进 `.anim` 参数，也不要误当作资源文件名后缀规则。

单位的三大基本动画是 `idle`、`combat`、`walk`。这三项不能也无需在 Art 中另行指定；只要 Skeleton 内部动画名正确、动画资源位于对应单位要求的可识别路径，游戏会自动识别并使用。模式专用版本可按前述后缀规则命名；角色页面等需要不带模式后缀的 `idle` 的场合，还必须保留基础 `idle`。

这里记录的是动画名解析约定，不代表所有调用上下文都存在模式动画；制作时仍须核对单位资源路径、Skeleton 内实际动画名及对应模式 ID。

## 技能动画的 56 帧播放边界

当前实测：技能 `.art.darkest` 中 `.anim` 所引用的技能动画在第 **56 帧**发生截断，超过该帧的动画内容不会继续播放。这里的“技能动画”只指 `.anim` 引用的 Spine 动画本体；同一技能另外引用的 `.fx`、`.targfx`、`.targchestfx`、`.misstargfx` 或 `.misstargchestfx` 不包含在该 56 帧截断结论内，必须分别检查其自身播放行为。

- 该结论是当前技能动画实测，不应自动推广到 FX、ActorDot、怪物动画或其他动画调用方；
- 超过 56 帧的关键动作应提前压缩或拆分到 FX 等独立调用中，但拆分后的时序和资源加载仍需单独验证；
- 56 帧是否受游戏版本、动画速度、调用字段或特殊技能流程影响，目前未知。

## 英雄本体动画目录
以英雄 ID `aaa` 为例，公共骨骼和图集通常位于：

```text
heroes\aaa\anim\aaa.sprite.<中缀>.skel
heroes\aaa\anim\aaa.sprite.<中缀>.atlas
```

各皮肤差分的 PNG 位于：

```text
heroes\aaa\aaa_A\anim\aaa.sprite.<中缀>.png
heroes\aaa\aaa_B\anim\aaa.sprite.<中缀>.png
heroes\aaa\aaa_C\anim\aaa.sprite.<中缀>.png
heroes\aaa\aaa_D\anim\aaa.sprite.<中缀>.png
```

官方 20 个英雄当前扫描到的 `269` 组本体动画均符合：

- `.skel` 与 `.atlas` 文件基名完全一致；
- 文件基名以 `<hero_id>.sprite.` 开头；
- 原版惯例将第一页命名为共同基名加 `.png`。实际绑定由 Atlas PNG 页名与皮肤目录中的对应文件名建立；
- Atlas 第一行为空行，复用时保留该空行；
- 该 PNG 能在每个对应英雄皮肤差分的 `anim` 目录中找到。

英雄本体的公共 `anim` 目录通常不放皮肤 PNG；同一套 `.skel/.atlas` 通过差分目录中的同名 PNG 显示不同皮肤。

### 命名安全边界
当前尚未证明引擎是否允许：

- `.skel` 与 `.atlas` 使用不同基名；
- 英雄动画 Skeleton 不以 `<hero_id>.sprite.` 开头；
- 任意修改上述前缀和目录结构。

但官方资源全部遵守该格式，因此 Agent 生成或迁移职业美术时必须按 `<hero_id>.sprite.<中缀>` 命名，不依赖未确认的宽松容错。

## 英雄 FX 目录
职业自定义 FX 通常位于：

```text
heroes\aaa\fx\aaa.sprite.<中缀>.skel
heroes\aaa\fx\aaa.sprite.<中缀>.atlas
heroes\aaa\fx\aaa.sprite.<中缀>.png
```

官方英雄当前扫描到的 `191` 组 FX 均符合：

- `.skel` 与 `.atlas` 文件基名完全一致；
- Atlas 第一页引用同基名 `.png`；
- PNG 与 `.skel/.atlas` 同处英雄 `fx` 文件夹。

例如：

```darkest
.fx "pistol_shot"
```

对应资源组通常命名为：

```text
heroes\highwayman\fx\highwayman.sprite.pistol_shot.skel
heroes\highwayman\fx\highwayman.sprite.pistol_shot.atlas
heroes\highwayman\fx\highwayman.sprite.pistol_shot.png
```

此处展示该常见资源组的命名对应；不能仅凭这组文件名证明所有 FX 字段的内部动画名解析规则。内部动画仍须读取实际 Skeleton 并按调用字段核对。

### `.targfx` 与 FX 文件中缀

当前用户于 2026-10-04 更正：目前只能确认 `.targfx` 的调用名必须与 FX 文件中缀一致。例如英雄代码名为 `xxx` 时：

```darkest
.targfx "aaa"
```

通常要求在该英雄的 `fx` 文件夹中存在：

```text
heroes\xxx\fx\xxx.sprite.aaa.skel
heroes\xxx\fx\xxx.sprite.aaa.atlas
heroes\xxx\fx\xxx.sprite.aaa.png
```

目前只能确认以下关系：

- `.targfx` 的调用名为 `aaa`；
- FX 文件共同基名的中缀必须为 `aaa`。

至于 Skeleton 内实际需要存在什么动画名，目前尚未确认，不能把动画名必须是 `aaa` 写成定论。模式差分动画可以继续作为同一 FX 资源的一部分，也可能拆到其他可被读取的资源文件中；具体动画名、拆分文件的扫描、覆盖和同名冲突边界均需进一步核对。

### 全局共用 FX
部分 `.targfx` 或 `.targchestfx` 可以引用游戏全局共用 FX，而不位于当前职业文件夹。例如：

```darkest
.targchestfx "blood_splatter"
```

对应游戏本体资源：

```text
DarkestDungeon\fx\blood_splatter\blood_splatter.sprite.skel
```

`mark_target` 也存在于游戏本体全局 `fx`。因此检查目标 FX 时：

1. 先检查职业自身 `heroes\<hero_id>\fx`；
2. 再检查游戏或依赖内容提供的全局共用 FX；
3. 不得因为职业 `fx` 中没有 `blood_splatter` 就误判引用必然缺失。

自定义 FX 若不打算作为全局依赖，仍应放在职业自己的 `fx` 文件夹中。

## Atlas 与 PNG 的强绑定
Atlas 文本开头记录其使用的 PNG 页面文件名。例如：

```text
highwayman.sprite.attack_pistol.png
size: 698,600
format: RGBA8888
```

该文件名必须能在引擎期望的位置找到：

- 职业 FX：同一 `fx` 文件夹；
- 英雄本体动画：各 `<hero_id>_<差分>\anim` 文件夹。

如果修改 PNG 文件名，必须同时修改 Atlas 内记录的 PNG 页面名。只重命名磁盘上的 PNG、却不修改 Atlas，会使 Atlas 继续查找旧文件名。

官方已扫描的英雄动画和 FX Atlas 使用共同基名加 `.png` 作为页面名。当前用户于 2026-11-21 补充：复用到新职业时，PNG 可以保留原职业前缀，各页仍按 Atlas 写的页名放置。改 PNG 名时，同步更新 Atlas 对应的页名以及使用该页的全部皮肤差分，保留 Atlas 的首行空行和多页间的分隔空行。仅修改动作名时，PNG 与页名可以成对沿用，Skeleton 附件与 Atlas 区域名也可成对沿用。动画名由 Skeleton 定义，区域名标识 Atlas 页内的贴图块。依据为当前用户说明、十字军原版文件和 [Spine 官方 Atlas 格式](https://esotericsoftware.com/spine-atlas-format)。本轮为静态核对。

### Spine 2.1.x Atlas 字段


页面级常见结构：

```text
<页面 PNG 文件名>
size: 252,532
format: RGBA8888
filter: Linear,Linear
repeat: none
```

- `size`：图集页面的像素宽、高；省略时官方格式默认 `0,0`。它应与对应 PNG 页面匹配，但 Atlas loader 可能在载入图片后使用实际尺寸。
- `format`：页面像素格式。官方候选包括 `Alpha`、`Intensity`、`LuminanceAlpha`、`RGB565`、`RGBA4444`、`RGB888`、`RGBA8888`；省略时默认 `RGBA8888`。Atlas loader 可能忽略该字段。`RGBA8888` 表示红、绿、蓝、透明度各使用 8 bit。
- `filter`：两个值分别是纹理缩小时和放大时的过滤方式；官方候选为 `Nearest`、`Linear`、`MipMap`、`MipMapNearestNearest`、`MipMapLinearNearest`、`MipMapNearestLinear`、`MipMapLinearLinear`，省略时默认 `Nearest`。`Linear,Linear` 表示二者均使用线性过滤；Atlas loader 可能忽略该字段。
- `repeat`：纹理坐标越界时是否重复；合法值为 `x`、`y`、`xy`、`none`，省略时默认 `none`。Atlas loader 可能忽略该字段。

区域级常见结构：

```text
backcloth
  rotate: false
  xy: 233, 188
  size: 17, 42
  orig: 19, 44
  offset: 1, 1
  index: -1
```

- 第一行 `backcloth` 是该图块／attachment region 的名称，Skeleton 的 attachment 会按此名称查找图集区域。
- `rotate`：该区域在图集打包时是否经过旋转；旧格式的 `true` 表示区域在页面 PNG 中逆时针旋转了 90°。运行时会调整 UV 还原，不能只改该值而不重排 PNG 中的实际像素。
- `xy`：区域在图集页面中的起始坐标。
- `size`：PNG 页面中实际打包区域的宽、高；若被旋转，读取时还需要结合 `rotate` 解释。
- `orig`：裁掉透明边缘以前的原始区域宽、高。
- `offset`：打包区域相对原始未裁切区域的偏移，用来把裁切后的图块恢复到正确位置。
- `index`：序列图块索引；`-1` 表示没有序列索引。非负值可参与同名序列区域的排序。

这些字段彼此强相关。若页面尺寸、区域坐标、裁切尺寸、旋转、原始尺寸、偏移或实际 PNG 像素不匹配，运行时可能采样到相邻区域或空白像素。暗黑地牢中的常见表现大概率是白边、白块、局部错图、错位或裁切异常；具体错误表现仍取决于损坏方式，不把所有 Atlas 错误统一断言为同一种结果。

### Spine 2.1.x Skeleton JSON 的读取边界
`*.sprite.json` 是 Spine 的文本 Skeleton 数据；其中常见顶层字段可按 Spine 数据格式理解：

- `skeleton`：导出元数据，如项目 hash、导出 Spine 版本、骨架边界和图片基准路径；`spine: "2.1.27"` 是导出版本声明。
- `bones`：骨骼列表；`parent` 建立父子层级，`x/y`、`rotation`、`scaleX/scaleY` 等是局部变换。
- `slots`：插槽列表；每个 slot 绑定某根 bone，并可指定默认 attachment。
- `skins`：皮肤及 attachment 数据；attachment 名通常需要与 Atlas 区域名对应。
- `animations`：动画名及各类时间轴，例如骨骼的旋转、位移、缩放和插槽变化。Art 字段最终引用这里的动画名。

JSON 中省略的数值字段通常使用 Spine Runtime 的默认值；但默认值和旧版时间轴兼容性仍应按 `2.1.27` 资源验证。

在没有修改主程序的前提下，暗黑地牢**只能读取 `.skel`，不能直接读取 Spine `.json`**，并且只能正常识别 Spine `2.1.27` 动画；高版本 Spine 动画无法被游戏正常读取。因此：

- 交付给游戏加载的动画必须保留或生成兼容 `2.1.27` 的 `.skel`；
- `.json` 只用于人工检查、修改和中间交换，不能代替游戏资源中的 `.skel`；
- 不得使用高版本 Spine 打开后直接重新导出，并假定结果仍与暗黑地牢兼容；
- 地牢还对部分动画资源的文件名、部分 Skeleton 内部动画名有硬性要求，但目前尚未完整整理具体名单。检查时不能因为 Spine 文件本身可解析，就断言它一定满足地牢的命名要求。

知识库根目录已提供：

```text
Spine.Converter.v1.0.5\Spine Converter v1.0.5.exe
```

通常只要动画资源本身正常、完整且可读取，就可以把 `.skel` 文件拖到该转换器 EXE 上转换成可读 `.json`；反过来把兼容的 `.json` 拖到转换器上，也可以转回 `.skel`。因此 Agent 需要检查动画内部内容时，应优先：

1. 保留原始 `.skel`，不要直接覆盖；
2. 使用该转换器把副本转为 `.json`；
3. 从 JSON 检查 `bones`、`slots`、`skins`、`animations`、动画事件及 Atlas attachment 对应；
4. 若进行了修改，转回 `.skel` 后仍须确认其版本兼容 `2.1.27`，并检查游戏要求的文件名和动画名。

转换器能成功转换，只能证明输入至少达到了工具可解析的程度，不能单独证明动画在暗黑地牢内必定正常显示或符合全部命名要求。

上述 Atlas 与 Skeleton 字段语义参考 Esoteric Software 官方 Texture Atlas Format、JSON export format 与 Spine Runtime 数据结构；新旧 Spine 版本的文本格式存在演进，处理暗黑地牢资源时不得用新版导出器直接覆盖 2.1.27 资源而不做兼容验证。

## 龙骨导出裁剪与最终版本约束

使用龙骨制作动画、再经 SpineConverter 转换为 Spine 的工作流中，龙骨导出不得勾选“去除空白区域”。原表指出该选项会使模型按错误的纵横比缩放；素材本身空白不明显时，失真可能不易察觉，但不能据肉眼不明显就当作没有失真。应在导入龙骨制作动画之前，先用图像编辑工具手动去除素材多余空白。

原生 Spine 的“去除空白区域”功能不会导致这里所述的比例缩放 Bug，不应把龙骨导出限制一并套到 Spine；本项不解除 Atlas 区域、原始尺寸与偏移必须相互匹配的既有要求。

当前用户于2026-11-03说明，这套工作流本来就有严格版本约束：未修改主程序的地牢只接受 Spine `2.1.27`；龙骨统一使用最新版制作后再经转换器处理，关键是最终产出符合地牢可读取的 Spine `2.1` 格式。当前用户进一步明确：本知识库及上述地牢制作语境中的“Spine 2.1”就是“Spine 2.1.27”的简称，两者指同一版本，不是两个兼容级别或任意 `2.1.x` 范围；不能仅改版本字符串就当作完成转换。也不把“最新版龙骨”固化为未经提供的具体版本号。若主程序被修改，其扩展兼容范围须另有依据。

证据：迂回表第50条 P1109/X1290–P1111/X1292，当前用户于2026-11-03要求按原表收录，并补充上述严格版本及转换工作流；非本轮新增实机测试。此处不再把是否已有严格版本限制当作未确认问题，也不冒称逐版测试了所有工具版本。

## 龙骨转换后的 Premultiply Alpha 与纹理压缩缺陷

迂回表第102条 P1593–P1595/X1984–X1986 记录了龙骨加转换器工作流的两项素材观察：龙骨的 Premultiply Alpha（预乘 Alpha）设置可能无法被转换器保留，透明光效在地牢的全局暗化滤镜下可能出现大片白斑或过曝；龙骨导出还会对 PNG 进行压图，透明渐变光效可能出现边缘锯齿和图像质量损失。这里保留原表的工作流与现象范围，不把它们扩大为所有龙骨素材、所有转换器版本或所有透明 PNG 的绝对结论。

原表 P1597–P1608/X1990–X2007 给出的处理思路是使用高版本 Spine 的纹理集解包与重新打包功能，重制 Atlas/PNG，同时保留原有 .skel，不降低 Spine 版本、不修改 Skeleton 文件。针对 Alpha，可在重新打包时让 Spine 写入所需的 Premultiply Alpha 参数；针对压图，可先按 Atlas 将合并纹理拆成独立 PNG，再用未经龙骨压缩的原始素材替换对应碎片，最后重新打包回纹理集。现行文字讨论的是 PNG/Atlas 纹理重制；原段删除线中的“Atlas 文件重制 Atlas”不作为额外结论。

如果只需要给 PNG 补充 Alpha，原表 P1610/X2010 另提到 png_alpha_colour_remover 工具。该名称和用途按原表记录，不据此保证工具来源、版本、批处理行为或对任意 PNG 都安全。本节方案的共同边界是最终仍须满足地牢可读取的 Spine 2.1.27 .skel、Atlas 与 PNG 页面及区域绑定；纹理重制不等于可以跳过版本和资源闭合检查。本补录依据第102条原表记录，当前用户于2026-11-04确认，未新增实机测试。

### writeVarInt 负整数、版本字段与转换边界

来源指出上游／A／C 的 `spBinaryWriter.writeVarInt`（上游第39–50行）对负整数右移最终保持 `-1`，循环不能结束，持续追加字节而可能卡住／耗尽内存。B 新增 `if value < 0: raise ValueError('Something non-negative is negative')`，只是立即报错终止，不是把负值正确转换，也不保证没有其他问题。

来源列出的直通入口：`drawOrder` 的负 `offset`（Reader285→Writer226）、事件负整型 `int`（Reader535/305→Writer442/239）、异常为负的 FFD offset（Reader246→Writer205）与 hull/edges（Reader358–360→Writer290–296）。负浮点坐标／旋转经 `writeFloat`（`struct.pack('>f', value)`），不属于该问题；`findSlotIndexByName`／`findBoneIndexByName` 未命中返回 `None` 导致的是 `TypeError`，不是负整数死循环。

空版本差异：来源报告上游／B／C 的 `spJsonWriter.writeSkeletonDataFile`（上游第218行）直接复制 version，`None` 导出为 JSON `null`；A 回填 `2.1.27`。文档称 DD 运行时不依赖该字段、第三方查看器可能报未知版本；这保留为来源说法，不据此解除本专题既有的 `.skel` 2.1.27 兼容要求，**改版本字符串不等于转换实际格式**。

社区经验部分另记：龙骨可能将 `XspriteY` 的 Y 识别为动画名，往返后生成零帧空壳动画，来源认为不调用该名字就不影响运行；龙骨压图可能使渐变毛边／色阶明显，部分模型仍有兼容问题。不要将这些经验混同为上述三个样本均经实机测试；转换后仍需核对动画、atlas 与纹理并在游戏内播放确认。本节不改写前述龙骨裁剪、预乘 Alpha 和纹理重制的既有条件边界。

## 技能演出坐标偏移方向

对进攻技能，迂回表第103条 P1613–P1615/X2014–X2017 记录了两个 Art 偏移字段的方向：

- area_pos_offset：X 正值向左、即向施术者身后；X 负值向右、即向施术者面前。
- target_area_pos_offset：X 正值向右、即向目标身后；X 负值向左、即向目标面前。
- 两个字段的 Y 轴相同：正值向上，负值向下。

这里描述的是技能镜头缩放期间的演出位置偏移，不改变实际站位、目标选择或结算对象。P1616/X2019 明确这组 X 轴方向只适用于进攻技能；友方技能的 X 轴方向另按第104条核对，不能把本节方向推广过去。本补录依据原表及当前用户2026-11-04确认，未新增实机测试。

友方技能的 X 轴方向相反。原表第104条 P1621/X2026 记录：当希望施术者和目标都向各自起始点前方、上方偏移时，施术者 area_pos_offset 与友方目标 target_area_pos_offset 均使用 X 正值；进攻技能中对应的 X 方向则与本节上一段相反。该观察不因目标随机、友方目标是否包含施术者、单体或群体而改变。P1622/X2028 还记录，即使友方 target_area 包含施术者，目标侧偏移也不会反过来作用于施术者的 area 偏移；施术者指向其他友方时，两者起始点仍按前后站位保持一个站位距离。

原表 P1623/X2029 的具体对照是：英雄位于1号位并对全体友方施法时，area_pos_offset -150 0 的演出位置会与2号位重叠，改为 -450 0 时会与4号位重叠，原表据此观察同侧站位间距约为150。这个150只作为该英雄友方技能演出测试的历史数值观察，不推广为所有阵营、镜头或版本的通用坐标单位。本节依据第103–104条及当前用户2026-11-04确认，未新增实机测试。

## 图标对应关系
### 技能图标
技能 Art 中：

```darkest
combat_skill: .id "skill_id" .icon "one"
```

通常对应英雄职业根目录中的：

```text
heroes\aaa\aaa.ability.one.png
```

其对应规则可写为：

```text
<职业id>.ability.<图标中缀>.png
```

Art 的 `.icon` 参数只填写最后的图标中缀，不填写职业 ID、`ability` 或 `.png`。例如文件名为 `aaa.ability.one.png`，则 `.icon` 写 `"one"`；文件名为 `aaa.ability.two.png`，则写 `"two"`。

`one`、`two` 并非已知的封闭枚举。根据现有命名与引用关系，该中缀大概率可以由作者自由命名，只要 PNG 文件名和 Art 的 `.icon` 参数严格对应；但“可使用任意字符”的宽松范围尚未确认。为规避未知解析问题，新图标中缀应使用简洁的 ASCII 字母、数字或下划线，不使用空格和特殊符号。

`generic_move` 是游戏提供的通用移动图标，不要求职业根目录存在 `aaa.ability.generic_move.png`。

## 音频事件的 GUID 覆盖：当前已知边界

音频目录中可能存在 `*.guid_overrides.json`，其 `event_guid_overrides` 列表使用如下结构：

```json
{
  "event_id": "event:/某个音频事件",
  "guid_override": "{某个 GUID}"
}
```

`guid_override` 指向 FMOD **事件**的 GUID，不是 WAV 文件、Bank 自身或 Bank 内单段采样的 GUID。多个默认事件映射到同一事件 GUID，会调用同一个 FMOD 事件；该事件仍可包含随机、多轨或参数控制，不能据此保证每次播放完全相同的采样。官方随附教程 `06_guids` 说明新事件由 FMOD 自动分配 GUID，可右键事件执行 `Copy GUID` 获取；本地工程中 Event 对象 ID 与配套 JSON 的十二个 GUID 已静态逐项核对。来源和证据快照见[专题97](97-音效制作与FMOD事件Bank接入.md)。不能仅凭外部文件名断言事件一定静音、时长为何或具有何种播放属性。

### 怪物大类的召唤与死亡音效事件 ID

知识库编写者确认（2026-09-23）：怪物（包括 size-0）的召唤与死亡音效，按怪物**大类 ID**组成的 `event_id` 分别为：

```text
event:/char/enemy/<怪物大类ID>_aggro
event:/char/enemy/<怪物大类ID>_death
```

`_aggro` 对应召唤音效，`_death` 对应死亡音效；这里应使用怪物大类名，不应把 `_A`、`_B` 等具体小类差分后缀拼入事件名。该事件路径是 `guid_overrides.json` 中 `event_id` 的值，不是音频 GUID 或 Bank 文件名。它们也不同于下文 size-0 通用音效覆盖中的 `event:/general/char/summon_enemy` 与 `event:/general/char/death_enemy`；两组事件路径不能混为一组。

## `*.narration.json`：以空旁白抑制 Size 0 死亡旁白的已知用法



```json
{
  "filters": [],
  "entries": [
    {
      "id": "kill_monster",
      "audio_events": [
        {
          "queue_only_on_empty": true,
          "queue_while_audio_playing": false,
          "audio_event": "",
          "chance": 1,
          "priority": 4,
          "max_raid_occurrences": 0,
          "max_town_visit_occurrences": 0,
          "max_campaign_occurrences": 0,
          "filter": "",
          "check_all_tags": true,
          "tags": ["某个用于识别 Size 0 的 Tag"]
        }
      ]
    }
  ]
}
```

当前能够确认或据 Mod 作者说明记录的内容：

- 文件名前缀可以自定义。
- 该实例的设计目的，是阻止 Size 0 死亡时播放老祖旁白。Size 0 并非设计上需要被当成实际怪物表现，但场上任意怪物死亡时都有可能触发老祖旁白，因此用空旁白条目抑制这一演出属于表现优化。
- `entries[].id` 使用 `kill_monster`，并由条目中的 Tag 将这一处理限制到对应的 Size 0。
- 当前用户补充并由 `NON_LP_empty.narration.json` 结构印证：对 `kill_monster` 的空旁白条目，`tags` 虽然是数组，但每个 audio_event 必须只写一个**怪物大类 ID**；不能写 `_A`、`_B`、`_1` 等小类/种族差分。写入多个时只保证其中一个生效，不要把多个 Tag 当作 AND/OR 组合筛选器。

### size-0 通用召唤/死亡音效的空白覆盖



```text
event:/general/char/summon_enemy
event:/general/char/death_enemy
```

指向同一个空白事件 GUID；对应 load_order 都加载同一个空白 secondary bank。当前实际检查到的 bank 路径是：

```text
audio\secondary_banks\Cathelia_empty_sound_single_instance.bank
```

配套 GUID 文本记录了该事件 GUID 与 bank GUID。这里的“多个作用域文件都写一遍”是为了提高覆盖原版事件的机会；当前文件集合证明了该 Mod 的覆盖设计，不把它升级为所有版本、所有音频作用域都必须使用的硬性白名单。

该覆盖的设计目的，是把通用召唤音效和通用死亡音效替换为空白音效，减少 size-0 作为中间单位时的细小召唤/死亡音效瑕疵。当前用户的观察是：召唤音效通常较小声，而普通怪物有各自的死亡音效，因此该通用覆盖主要处理 size-0 的通用演出；是否适合其他召唤物必须按实际音效和加载覆盖复核。

### 与空旁白抑制的配合

`NON_LP_empty.narration.json` 使用自定义文件前缀、`entries[].id: "kill_monster"`、空 `audio_event` 和每个事件一个 Tag，按 Tag 抑制指定 size-0/怪物大类的老祖旁白。文件前缀可以自定义；Tag 必须写怪物大类 ID，不能写小类/种族差分。多个大类目标应拆成多个 audio_event，每个只写一个大类 Tag。

这些音频覆盖和旁白抑制只属于演出优化，不改变 size-0 的死亡状态、spawn 调用链或死亡门。

除此之外，目前仍不知道顶层 `filters`、`audio_events` 的完整规则，空 `audio_event` 的底层处理，`queue_only_on_empty`、`queue_while_audio_playing`、`chance`、`priority`、三种 `max_*_occurrences`、`filter`、`check_all_tags` 的精确语义，以及多个 `*.narration.json` 文件之间的合并或覆盖关系。Agent 可以把上述结构作为“按 Tag 以空旁白抑制 Size 0 死亡旁白”的已验证用途，但不得把其余字段按名称猜成确定机制。

创建职业时，仍应以结构最接近的原版英雄或已验证职业为模板；但对上述已经明确的目录、命名、Atlas 页面和图标关系，Agent 可以直接检查，不再一概视为未知。
