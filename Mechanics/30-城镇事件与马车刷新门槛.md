## 文件与通用骨架
城镇事件定义文件使用：

```text
campaign\town_events\<prefix>.town_events.events.json
```

官方当前扫描到的事件都以顶层 `events` 数组保存。每个事件普遍包含：

```json
{
  "id": "event_id",
  "base_chance": 2.0,
  "per_not_rolled_additional_chance": 0.0,
  "cooldown": 2,
  "requirements": {
    "minimum_week": 6,
    "dead_heroes": 0,
    "hero_level_counts": [],
    "upgrades_purchased": [],
    "trinket_storage_count": 0
  },
  "town_ambience_paramater_ids": [],
  "tone": "neutral",
  "sprite": "",
  "sprite_attachment": "",
  "data": []
}
```

这是由现有游戏文件归纳出的通用骨架，不是已经证明的绝对最小字段集合；不理解的字段按同类官方事件保留。

## 常用字段
- `id`：事件 ID，也是本地化和英雄 `.town_event_dependency` 的引用对象。
- `base_chance`：事件基础抽取权重/概率值。
- `per_not_rolled_additional_chance`：事件未被抽中后追加的值。
- `cooldown`：事件的冷却参数；冷却长度和起算时点尚未完全确认。当前推测是事件实际发生或进入事件队列后开始计算，不能直接断言为“事件再次可用前的过周冷却”。
- `is_unique: true`：该事件在同一存档中只发生一次。
- `priority`：官方已见 `high`、`higher`、`highest`，部分事件省略。任务保证事件另有 `quest_type_event_guarantees`。完整竞争顺序、同级裁决与保证事件的关系待核验。原版运行观察见[原版副本专题](101-原版副本探索、扎营夜袭与出本结算.md)。
- `requirements`：事件进入候选池前必须满足的条件；数组型条件的内部结构应按官方对应事件仿写。
- `tone`：决定城镇事件播报窗口的色调边框；原版已见且应当只有 `good`、`neutral`、`bad` 三个常规合法值。
- `sprite`：城镇事件发生后显示在小镇场景中的 Spine 动画资源 ID，不是事件播报窗口内的插图。
- `sprite_attachment`：该动画在小镇场景中的建筑/锚点位置；空字符串表示不指定自定义事件动画。
- `data`：事件发生后执行的一个或多个事件效果。

### `tone`、默认边框与单事件自定义边框

`tone` 不决定事件实际效果的正负，也不负责小镇场景中的 `sprite`；它只决定城镇事件播报窗口使用哪张色调边框：

| `tone` | 原版对应图片 |
|---|---|
| `bad` | `campaign	own	own_event	own_event.tone_frame_bad.png` |
| `good` | `campaign	own	own_event	own_event.tone_frame_good.png` |
| `neutral` | `campaign	own	own_event	own_event.tone_frame_neutral.png` |

原版常规合法值应当只有上述三项；在没有新主程序或官方文件证据时，不得臆造第四种 `tone`。

如果只想让某个事件使用自定义边框，应参考猩红庭院等官方 DLC，在该事件中增加：

```json
"custom_frame_id": "crimson_court"
```

并提供：

```text
campaign	own	own_event	own_event.custom_frame_crimson_court.png
```

由官方实例可归纳命名规律：

```text
"custom_frame_id": "<id>"
→ campaign	own	own_event	own_event.custom_frame_<id>.png
```

星空 DLC 的 `custom_frame_id: "shard_priced"` 及 `town_event.custom_frame_shard_priced.png` 也符合该规律。此方案是按事件指定边框，不需要替换三张全局 `tone_frame`。

若希望全局替换某种 `tone` 的视觉效果，则可在 Mod 的对应路径放置与原版完全同名的 `town_event.tone_frame_bad.png`、`town_event.tone_frame_good.png` 或 `town_event.tone_frame_neutral.png`，依靠同路径同名覆盖改变所有使用该 `tone` 的事件。这样会影响全局，不应误用于只想修改单个事件的设计。

### 城镇事件 `sprite` 资源与附着位置

若事件写有：

```json
"sprite": "town_event_example",
"sprite_attachment": "statue"
```

通常在 Mod 中提供：

```text
fx	own_event_example├─ town_event_example.sprite.atlas
├─ town_event_example.sprite.png
└─ town_event_example.sprite.skel
```

已确认/强规律如下：

- `sprite` 对应的动画显示在**小镇场景**中，而不是城镇事件播报窗口内；
- 对应 Spine 动画不要求动画名必须为 `idle`，不得把 `idle` 写成城镇事件动画的硬性要求；
- `sprite_attachment: "statue"` 对应小镇雕像位置，约在游戏画面中央靠下；
- `sprite_attachment: "tavern"` 对应酒馆位置，约在画面左侧、刷新英雄的马车右边；这里的马车是驿站马车，不是饰品商店马车；
- `sprite_attachment` 的合法值应当是各城镇建筑/锚点 ID，但完整合法值表尚未整理，因此新增取值应从原版实例复制；
- 强规律推测 `sprite` ID、`fx` 子文件夹名以及 `.atlas`、`.png`、`.skel` 的共同资源前缀都必须严格同名；
- `.skel` 文件名推测要求使用 `<前缀>.sprite.skel` 形式。上述两项尚未通过系统性改名实验验证，不得写成完全确认的引擎规范；
- 同目录存在的 Spine 2.1.27 `.sprite.json` 可作为源文件或检查材料，但游戏实际读取动画仍使用 `.skel`。

制作新事件动画时，最安全的做法是完整复制原版或已验证 Mod 的目录、同名前缀及 `.sprite.*` 命名结构，只替换合法的 Spine 2.1.27 资源内容。

### 尚未确认：`town_ambience_paramater_ids`

字段名在游戏文件中确实拼作 `paramater`，不得擅自纠正为 `parameter`：

```json
"town_ambience_paramater_ids": []
```



```json
"town_ambience_paramater_ids": ["town_event"]
```

根据字段名和实例，只能推测它用于在事件期间向城镇 ambience/演出系统传入参数 ID，`town_event` 可能用于切换某种城镇事件环境状态；但具体影响对象、持续时间、是否涉及 FMOD 音频以及合法参数全集均未知。普通自制事件若没有明确演出需求，应按同类原版结构保留空列表，不得删除字段、改正拼写或臆造参数。

## 城镇事件结算与单次出征

**常规城镇事件以单次出征为单位结算。** 事件播报后的下一次出征返回城镇时结算，城镇周数保持原值时也会结算。事件 Buff 和闲置英雄升级（`idle_resolve_level`）都遵循这条通则。依据为知识库编写者于 2026-11-24 的补充。

头狼入侵是特殊事件。原版 `campaign/town_events/base.town_events.events.json:1302` 的 `plot_quest_town_invasion_0` 通过第 1324–1325 行的 `plot_quest` 效果引出 `plot_town_invasion_0`（`campaign/quest/quest.plot_quests.json:1731`）。这类例外的结算按具体事件核对。

## 赠送英雄
普通赠送英雄使用：

```json
{
  "type": "bonus_recruit",
  "string_data": "hero_class_id",
  "number_data": 1.0
}
```

- `string_data` 是英雄职业 ID。
- `number_data` 是赠送数量。
- 首次赠送职业通常同时写 `is_unique: true` 和较高 `priority`。

Fire's Edge 另有 `bonus_recruit_stage_coach_level`，它不是普通 `bonus_recruit` 的同义拼写；需要该新效果时按官方文件单独仿写。

## 闲置英雄提升决心等级：`idle_resolve_level`

城镇事件效果：









含义如下：

- `string_data`：指定英雄职业 ID；
- `number_data`：该职业符合条件的英雄提升多少级；
- 效果作用于**所有**符合条件的指定职业闲置英雄，不是随机一名；
- 这里改变的是英雄的**决心等级**，不是直接增加历练值；
- 满级英雄不受影响。

`idle_resolve_level` 的闲置英雄资格要求英雄仍在名册中，留在城镇且没有出征，同时没有被安排到疗养院、酒馆、教堂或其他城镇设施进行任何活动。留在城镇治病、处理怪癖或减压的英雄不符合闲置条件。

原版 `campaign/town_events/base.town_events.events.json:140` 的瘟疫医生事件在第 157 行使用 `idle_resolve_level`。事件文件提供效果类型、职业与升级级数，以上闲置条件由知识库编写者于 2026-11-24 补充。

`idle_resolve_level` 在事件播报后的**下一次出征返回城镇时**为符合条件的英雄结算升级，即使城镇周数没有增加也会结算。事件只维持一次任务，与同样按单次任务生效的城镇事件 Buff 一致。知识库编写者于 2026-11-24 补充了该结算时点。另见[过周条件与无尽农庄](101-原版副本探索、扎营夜袭与出本结算.md#过周条件与无尽农庄)。

另一个未确认边界是英雄当前历练值没有恰好处于某一级起点时，引擎如何同步其历练值与被直接改变的决心等级。不得把该效果解释为等价地增加某个固定历练值，也不要依赖未验证的历练值结算结果。

## 常规马车招募的 generation 配置

已正常加载的新职业可通过职业 Info 的 `generation:` 加入常规马车招募。启用 `.is_generation_enabled true`，配置 `.number_of_cards_in_deck` 与 `.card_chance`。当前用户在教程编写期间明确指出，单为常规马车刷新不必另建 `campaign\roster\*.roster.groups.json`。可沿用原版十字军的牌数 `6` 和 `.card_chance 1.0`，然后在测试档过周观察新候选。候选资格与某一周是否刷出分别判断。两参数的精确计算公式和上下限仍按 [Info 字段说明](../Info/headers/Info.generation.md)保留待定。

原版火枪手 DLC 会调整弩手的招募牌数。关闭 DLC 时，弩手有 `6` 张。开启后，火枪手加入 `3` 张，并以 `.reduce_number_of_cards_in_deck_hero_class_id arbalest .reduce_number_of_cards_in_deck_amount 3` 将弩手减为 `3` 张，两职业的 `.card_chance` 均为 `1.0`。火枪手的 Info 默认关闭常规生成，由 DLC 的 `musketeer.override.darkest` 启用。知识库编写者于 2026-11-21 确认，同等条件下，**开启火枪手 DLC 后，常规马车抽到火枪手或弩手的合计刷新概率，等于关闭 DLC 时抽到弩手的刷新概率**。两参数各自如何影响抽取、组合公式以及整周至少刷出一次的概率仍待确认。原版行号与说明见 [证据记录](../Sources/tutorial_corrections_20261121.json) 的 `musketeer_arbalest_stagecoach_cards`。

## `.town_event_dependency`
英雄 Info 中：

```darkest
generation: .is_generation_enabled true .town_event_dependency "event_id"
```

表示只有指定事件已经发生后，该英雄才可以在马车中自然刷新。

- 参数引用一个永远不会发生的事件 ID 时，英雄永远不会自然进入马车候选池。
- 参数引用一个根本不存在、没有定义的事件 ID，也可达到阻止自然刷新的效果。
- 这可以把职业获取数量限制在设计者提供的城镇事件、任务奖励或其他明确入口内。

### 仅能通过事件获得的英雄：强制要求
如果设计要求英雄**只能通过城镇事件获得**，那么 `generation:` 中 `.town_event_dependency` 的参数必须指向：

- 一个根本不存在、没有定义的事件 ID；或
- 一个虽然有定义，但按设计永远不会发生的事件 ID。

不得填写任何会实际发生的既有事件 ID，也不得填写负责赠送该英雄的事件 ID。原因是 `.town_event_dependency` 表达的是“该事件发生后解锁马车自然刷新”，而不是“由该事件负责赠送英雄”。只要所引用的既有事件实际发生，英雄之后就会进入马车自然刷新候选池，从而破坏“仅事件获取”的限制。

例如，唯一赠送事件 A 负责赠送一名英雄时：

```darkest
generation: .is_generation_enabled true .town_event_dependency "aaa_never_occurs"
```

其中 `aaa_never_occurs` 必须不存在或永不发生，不能写成事件 A 的实际 ID。唯一赠送事件与用于永久封锁马车刷新的依赖 ID 必须分开。

    {
      "id": "first_aaa",

      },
