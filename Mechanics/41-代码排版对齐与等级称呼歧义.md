## 代码排版也是生成质量的一部分

Agent 生成或整理 Mod 配置时，在不改变语义的前提下，应主动考虑可读性。相邻的同类 Header、同一技能的各等级定义、同一组武器／护甲升级定义以及结构重复的 Effect，可以按字段顺序和字段宽度进行纵向对齐，使读者能够直接比较各级差异。

例如，技能各等级的 `.atk` 位数不同，可以调整字段之间的空格：

```darkest
combat_skill: .id "example_skill" .level 0 .atk 95%  .crit 5% .target 34
combat_skill: .id "example_skill" .level 1 .atk 100% .crit 6% .target 34
```

这里在 `95%` 后保留两个空格、在 `100%` 后保留一个空格，使后续 `.crit` 纵向对齐。类似方法也可用于：

- 不同等级的 `.dmg`、`.crit`、`.atk`、`.level` 等字段；
- 武器、护甲和技能升级树中结构相同的多级条目；
- 同组 Effect 中重复出现的字段；
- JSON 数组或对象的缩进与换行。

## 优先按效果类别组织，而不是按等级打包

当同一文件需要定义一个技能多个等级的多类 Effect 时，默认应把**同类效果写在一起**，再在同类内部按等级排列；不建议先写完等级 0 的流血、减益、位移、善后，再写等级 1 的同一整套内容。

例如，若各等级的流血和减益数值不同，推荐的阅读顺序是：

1. 该技能所有等级的流血 Effect；
2. 该技能所有等级的减益 Effect；
3. 其他功能类别的 Effect；
4. 每一类别内部再按 `.level 0` 至 `.level 4` 对应关系或 ID 的等级后缀依次排列。

这样读者可以直接纵向比较同一类效果的等级成长，也更容易发现某一级参数遗漏、目标不同或时序写错。对于完全相同的效果，还应进一步复用同一个自定义 Effect，而不是保留多份按等级复制的定义。

### 不应拆散的例外

若若干 Effect 一起组成一个迂回、施加—结算—清理链、标记—读取—善后链或其他依赖紧邻关系才能被人正确理解的逻辑单元，则应把这组定义作为一个整体连续排列。此时“迂回整体”本身就是更高优先级的同类逻辑块，不应为了把单个流血、减益或驱散 Effect 分到各自类别而拆散。

推荐排序优先级：

1. 引擎语义、实际引用顺序和触发时序正确；
2. 迂回或逻辑链保持完整；
3. 同类效果聚合；
4. 同类内部按等级排列并纵向对齐；
5. 纯视觉上的整齐。

需要区分**定义排序**与**引用排序**：整理 `*.effects.darkest` 中各 `effect:` 定义的先后，通常是为了阅读；而技能 `.effect` 列表等调用位置的书写顺序可能决定实际触发顺序。不得为了让定义文件分组整齐而擅自改变调用方的引用顺序。

排版对齐属于**建议**，不属于引擎机制或字段语义。实施时必须遵守：

1. 只在字段之间增加普通空格或进行合理换行，不得在字符串、ID、数字、百分号或站位参数内部插入空格；
2. 不得为了对齐改变字段顺序所承载的 Effect 时序；
3. 不得把本应独立成行的 `//` 注释改成行尾注释；
4. 不得在 `.darkest` 代码中使用 `...` 作为省略号；
5. 对齐不能掩盖等级差异。若某一级缺少字段有实际语义，不应为了版面整齐伪造占位字段；
6. 语义正确和可运行性优先于视觉对齐。若强制对齐会造成极长行或降低可读性，应改用合理分行，而不是堆叠大量空格。

## 技能、武器和护甲的等级称呼可能有两套编号

英雄技能、武器与护甲通常会同时遇到：

- **文件／代码等级**：常见写法从 `0` 开始，例如 `.level 0` 至 `.level 4`；
- **玩家口语等级**：常把五个成长阶段称为 `1` 级至 `5` 级。

因此，用户单独说“1级”“2级”“3级”或“4级”时，可能是在说代码等级，也可能是在说玩家口语中的第几个等级。两种解释会相差一级，Agent 不得自行猜测后直接写代码。

### 不需要确认的常见情况

- 用户明确说“代码里的 `.level 1`”或明确给出 `.level` 参数：按代码等级理解；
- 用户明确说“游戏显示的第 1 级／初始一级”：按玩家口语等级理解；
- 用户完整地说“1～5级”并按五级成长给出数据：通常可确定为玩家口语等级，对应代码 `0～4`；
- 用户提到“0级”：通常只能指代码等级 `0`；
- 在标准五级技能／刀甲体系中，用户提到“5级”：通常只能指玩家口语的第 5 级，对应代码等级 `4`；
- 用户完整给出“0～4级”：按代码等级理解。

上述映射以目标定义确实采用标准五级结构为前提；若目标 Mod 自行增加等级数量或使用非标准编号，仍应读取实际文件，不得套用标准五级映射。

### 必须向用户确认的情况

当用户只说“1级”“2级”等中间等级，且上下文没有明确说明采用哪套编号时，必须在写入代码前提出简短确认，例如：

> 这里的“1级”是指文件中的 `.level 1`，还是玩家口语中的第1级（文件 `.level 0`）？

该确认要求同样适用于：

- `combat_skill:` 的技能等级；
- `*.upgrades.json` 中的武器等级；
- `*.upgrades.json` 中的护甲等级；
- 任何复用零基代码编号、但玩家可能按一基顺序称呼的五级内容。

不能因为原版通常有五级，就默认把用户孤立提到的“1级”解释成 `.level 1` 或 `.level 0`。若用户已经给出完整的 `1～5`、`0～4`、字段原文或其他明确映射，则不得重复追问。

## Agent 生成前检查

1. 多个等级、多类效果并存时，是否优先按效果类别聚合，再在同类内部按等级排列，而没有机械地按等级打包全部效果？
2. 若若干 Effect 共同组成迂回或严格逻辑链，是否把整套定义连续保留，而没有为了分类将其拆散？
3. 是否区分了定义文件中的阅读排序与调用方决定触发先后的引用排序，没有为排版擅改 `.effect` 引用顺序？
4. 相邻同类定义是否采用一致的字段顺序，并在不改变语义的情况下进行了合理对齐？
5. 空格是否只用于字段分隔和排版，没有进入参数或字符串内部？
6. 是否把视觉对齐误当成必须满足的引擎格式？
7. 用户提到技能、武器或护甲的中间等级时，是否存在零基／一基歧义？
8. 若存在歧义，是否先确认了用户所指的编号体系，再进行代码写入？
9. 若用户已经明确给出 `1～5`、`0～4`、`.level N` 或显示等级，是否避免了无意义的重复询问？
