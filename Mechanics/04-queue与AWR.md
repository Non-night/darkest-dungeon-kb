## queue 的两个主要层
- `.queue false` 是靠前层；省略 `.queue` 时默认值也是 `false`。可近似理解为与技能动画同时发生。
- `.queue true` 是靠后层；可近似理解为等待技能动画结束后发生。

这是用于理解技能 Effect 的近似模型，不是精确帧级时钟：具体表现时间可能随动画长度变化，底层分界尚未确认。size-0 的 Spawn 调用时序由召唤实际发生的阶段决定。

## `queue false` 的跳字合并
- 同一 `queue false` 层中的减压、加压或真伤跳字，各自会按同类 Effect 的最终数值合并显示。即使连续写入大量同类 Effect，显示的是各段结果的合计，而不是按 Effect 数量分别弹出许多跳字。
- 该结论只说明 Popup 的视觉合并，不改变每条 Effect 的独立结算、生命反馈或其他后续机制。
- 过抗类 Effect 的 Pop 当前观察为：相同概率可能共用一个 Pop，不同概率可能出现多个 Pop。该观察尚未覆盖所有 Pop 类型或所有时序，不能据此推断通用合并规则。

## 眩晕 Effect 的防红字时序
- 当同一逻辑 Effect 中的 `.stun` 参数不为 `0` 时，通常应写 `.queue true`。
- 若省略 `.queue`，其默认值为 `false`；这种非零 `.stun` 配置会产生红字报错。
- 因此，常规眩晕 Effect 应写 `.queue true`。若特殊设计刻意需要 AWR/`queue false` 眩晕，可以保留该时序并接受红字报错；红字不等于眩晕一定不生效，但这种写法不能描述成无报错方案。

## AWR
AWR 是 `.apply_with_result true .queue false` 的简称，也称直伤前时序。由于 `.queue` 默认是 `false`，只写 `.apply_with_result true` 也可进入 AWR。


### 技能 `.move` 与两次伤害结算
知识库编写者于 2026-10-22 在当前会话明确确认以下相对时序；证据为社区确认，不冒称原版代码或反编译结论。“两次伤害结算”是知识库编写者采用的描述术语，不是已确认的引擎内部阶段名称。

**第一次伤害结算 → 技能 `.move` 自带位移 → AWR → 第二次伤害结算。**

- 第一次：计算各种 Buff、防御等加成，但不包括易伤；早于技能 `.move`，也早于 AWR 开始。
- 技能 `.move`：施术者技能自带位移，在初次计算之后、AWR 之前发生；不是 Effect `.pull` / `.push`，不得套用它们的暂存位移时序。
- 第二次：计算易伤并应用最终伤害，晚于 AWR。“AWR 是直伤前时序”指早于最终伤害应用，不是早于第一次伤害计算。
- 已确认例子：英雄原本站在一号位，并拥有“一号位时 +50% 伤害”的 Buff，使用后退 1 的攻击技能时，本次攻击仍享受该 +50% 伤害加成；不会因随后离开一号位而失去这次已参与初次计算的加成。
- 本次确认不枚举所有属性所属阶段，不补充易伤以外的具体属性分类，也不据此扩展到反击、友方技能或非技能调用。

### AWR 适用边界

AWR 只在普通攻击技能中形成独立时序：
- `.queue true` 时，`.apply_with_result` 没有时序意义。
- 友方技能中没有时序意义。
- 反击在伤害、暴击等常规数值结算上属于特殊攻击技能，但不属于这里所称的普通攻击技能，不能据此套用普通攻击技能的 AWR 分层。
- AWR 不等同于 `skill_instant`。

## `act_out` 的友军攻击不是攻击技能
英雄因美德、折磨、怪癖或疾病触发 `act_out` 而攻击友军时，演出中可以播放攻击动画，也可以引用一条 Effect；但该调用方**不是技能，更不是攻击技能**。

- 它不进入普通攻击技能的命中、AWR、暴击特效或 ActorDot 调用链。
- 它不会触发任何攻击相关 Trigger，包括攻击、近战、远程、暴击，以及由这些类别派生的饰品 Trigger。
- 不得因画面表现为“英雄攻击友军”而把 `act_out` 当成友方攻击技能，或据此推导攻击类 Trigger、命中门或攻击技能概率骰子行为。
- `act_out` 可引用的 Effect 自身仍按实际调用方和字段语义结算；仅“存在动画和 Effect 引用”不赋予它技能／攻击技能身份。

## 普通攻击技能的完整 Effect 次序
一次普通攻击技能依次进入：

1. 技能 AWR。
2. 饰品 Trigger AWR。
3. 暴击特效 AWR；仅在发生暴击时存在。
4. 技能 `queue false`。
5. 饰品 Trigger `queue false`。
6. 暴击特效 `queue false`；仅在发生暴击时存在。
7. 技能 `queue true`。
8. 饰品 Trigger `queue true`。
9. 暴击特效 `queue true`；仅在发生暴击时存在。
10. 对应类型的 ActorDot 内容；仅在行动者身上存在对应 AD 时进入。

同一时序、同一来源引用多个**常规** Effect 时，通常按引用处的书写顺序生效。例如：

```darkest
combat_skill: .id "aaa" .effect "xxx" "yyy" "zzz"
```

如果三个 Effect 都是普通 `queue false`，通常按 `xxx` → `yyy` → `zzz` 生效。该规则写作“通常”，因为部分特殊 Effect 可能发生引擎重排；`.pull`、`.push` 与 `.immobilize` 是已确认例外，必须看本页的位移专题。

## 技能 Effect 依赖链必须同时检查两级时序
书写技能 Effect 时，必须同时检查以下两级时序，不能只检查引用列表中的先后顺序：

1. **大时序／时序层**：AWR → 普通 `queue false` → `queue true`，并结合技能、饰品 Trigger、暴击特效等来源层级判断实际先后。
2. **严格时序／书写顺序**：只有处于同一个大时序、同一来源的多个常规 Effect，才通常按照引用处从左到右的书写顺序依次生效；推拉与定身另有已确认的特殊规则。

大时序优先于书写顺序。即使某个 Effect 在 `.effect` 列表中写得更靠前，只要它属于 `queue true`，它仍会晚于列表中属于普通 `queue false` 的 Effect。不得用跨大时序的文本排列构造“先施加状态，再让后续 Effect 读取该状态”的依赖链。

典型错误：技能设计为“先眩晕，再对已眩晕目标降低闪避”，并让降低闪避的 Buff 在条件不满足时移除；但眩晕 Effect 按常规防红字写成 `queue true`，降低闪避 Effect 却是默认的 `queue false`。实际执行时降低闪避会先于眩晕检查目标，因此它无法读取本技能稍后才施加的眩晕，无法按预期生效；若目标原本已经眩晕，则应另行按既有状态分析，不能把它误认为读取到了本次技能的新眩晕。

因此，任何存在“前置 Effect 建立状态／Buff／标记，后续 Effect 读取、消费、驱散或依赖该结果”的技能链，都必须逐项验证：

- 前置 Effect 的大时序是否确实早于或等于依赖 Effect；
- 若二者处于同一大时序，引用书写顺序是否为“前置 → 依赖 → 善后”；
- AOE 分层遍历、饰品 Trigger、暴击特效或 ActorDot 是否会插入或改变预期窗口；
- 条件 Buff 的 `remove_if_not_active`、Rule 检测和清除时机是否会在前置状态建立前就使其失效。

若实现要求后续 Effect 读取本技能刚建立的状态，必须调整两者的大时序与严格顺序，使依赖关系在实际执行顺序中成立；不能仅交换 `.effect` 参数的书写位置后就认定问题已解决。

## AOE 的分层遍历
AOE 不会先完成一个目标的全部时序再处理下一个目标，而是先完成一个时序层的全部目标：

1. 按目标站位从前到后，依次结算每个目标的全部 AWR。
2. 再按相同目标顺序，依次结算每个目标的全部 `queue false`。
3. 再按相同目标顺序，依次结算每个目标的全部 `queue true`。

每个目标内部仍按“技能 → 饰品 Trigger → 暴击特效”的来源顺序处理当前时序层。

## 迂回表“全部 Effect”的同层边界
迂回表第83条 P1359–P1361/X1619–X1623 的“对上一个目标执行了全部 Effect 后才处理下一个目标”，其中“全部”仅指同一时序层内，不包括跨 AWR、`queue false`、`queue true` 的处理。当前用户于2026-11-04明确确认知识库现有分层结算方式准确；此前将该段列为相反模型的冲突状态已解除。本轮未新增实机测试，也不将原表的解释段改称独立测试记录。

因此，同层内对 X 执行 A、B、C、D 后再对 Y 执行 A、B、C、D；仍须先遍历该层的全部目标，再进入下一时序层。原表以旧式真驱散说明共享修正被提前清除：若首个目标的同层处理末尾清除了施术者身上后续目标仍需使用的 Buff，后续目标便无法再使用该 Buff。这是逐目标遍历与共享状态清理的结果，不表示真驱散无视书写顺序，也不表示各目标跨层完整执行。旧式真驱散的方案背景不撤销当前优先按 Buff ID 定向驱散的要求；采用定向清理时仍须核对共享 Buff 是否已完成所有预期用途。

## 暴击特效
暴击特效定义在单位的 `*.info.darkest` 中：

```darkest
crit: .effects "effect_id_1" "effect_id_2"
```

- 单位使用攻击技能并造成暴击时，引用的 Effect 才进入上述暴击特效时序。
- 英雄 Info 的 `crit: .effects` 所调用暴击特效，默认 `target` 是当前技能目标，因此可以正常指向敌方。迂回表第31条 P800/X930 所称“默认目标为英雄自身、不能指向敌方”的说法已由当前用户于2026-11-03纠正，应排除该旧说法。此处只确认该调用方的默认目标及可指向敌方，不推导所有特殊 `.target` 参数、饰品暴击 Trigger 或怪物同名 Header 的目标行为；暴击导致 skill Rule 残留的阵营范围仍按独立未确认项记录。本轮未新增实机测试。
- 最多引用 `4` 个 Effect ID；每个 ID 最长 `64` 个字符。
- 原版英雄实例：`DarkestDungeon\heroes\abomination\abomination.info.darkest:2`。

```darkest
crit: .effects "on_crit_dmg"
```

原版游戏及官方 DLC 的怪物 `*.info.darkest` 中未找到直接定义实例。有经验结论认为怪物也可使用该结构，但当前缺少原版直接证据，应标为尚未完全确认。

## 即时响应与已知延迟例外
在没有专项证据说明延迟时，绝大多数机制按**状态变化后即时响应**处理。这是当前知识库的默认推理原则，不可据此把未测试的特殊机制断言为已验证。

- 英雄在技能处理期间因普通伤害、真伤等常规生命归零原因进入死亡之门时，死亡之门 Rule 及相关判定即时响应；目前未发现延迟。最大生命值减益同步压低当前生命至0的路径未观察到给予死门 Buff，不能并入这个“进入死门”结论，见[死门边界](31-英雄标签、同队限制、死门与技能选择.md)。
- 真光环机制生成的 Buff 消失在下一次游戏 `Update`，不是在移除条件出现的瞬间。
- 迂回表第78条 P1329–P1330/X1580–X1581 的历史观察：怪物 `battle_modifier` 真光环随游戏 `Update` 刷新，任意敌我单位个人回合结束是原表记录的 `Update` 时点之一；在下一次 `Update` 前瞬间生成并自灭的 Size-0 不会实际获得该真光环 Buff。这里指真光环机制本身，不等同于单独使用 `bsrc_battle_modifier` 来源的 Buff；不推定主动施加路径或所有版本。当前用户于2026-11-03确认并澄清刷新时点；非本轮新增实机测试。
- `has_buff` Rule 的“由有效变无效／由无效变有效”转换检测有已知延迟；具体检查时点尚未确认。
- `.pull` / `.push` 的过抗判定与实际位移表现分离，见下一节。

## `.pull` / `.push` 的时序、暂存与同层选择
本节“推拉”只指 `.pull`（拉前）和 `.push`（击退），**不包括**延迟扰乱、单体扰乱、群体扰乱或 `.instant_shuffle`，也不外推到无动画翻页迂回和道具中的推拉。

### AWR 与 `queue false`
- 在 AWR 和普通 `queue false` 中，推拉的“理论是否成功”（概率、位移施加率、位移抗性等）遵循严格书写顺序。
- 因此，夹在两个推拉之间的位移施加率或位移抗性 Buff 可以影响后一个推拉，不能回头改变前一个已经判定的推拉。
- 实际站位变化不会在每条推拉刚判定后立即表现：这些推拉会被暂存，在 `queue false` 结束、`queue true` 开始前结算实际位移。

### `queue true`
- `queue true` 中的推拉不遵循同层严格书写顺序，而处于该层末尾；它们在 `queue true` 结束后才结算实际位移，后续接入哪一阶段尚未确认。
- `.pull` / `.push` 写在 `queue true` 会产生红字报错。已有测试虽能观察到其时序行为，但这不是可作为安全常规实现的写法。

### 同一时序的多个推拉
- 同一时序存在多个推拉时，先分别按该层规则判断每一条是否理论成功。
- 所有理论成功的候选中，**只有严格书写顺序最后一个**会实际生效；其余候选不会实际改变站位。
- 理论被抵抗的推拉不进入候选，不占用这个唯一结果。因此可以在 AWR 或 `queue false` 内按严格顺序控制各候选的过抗状态，从而条件化选择最终推拉。
- 该结论已由两个、三个推拉的测试确认，并可暂按任意数量推拉处理。实际位移表现被暂存，不表示推拉的理论成功判定脱离严格时序。

## 定身 `.immobilize` 与推拉
- 当 `.immobilize` 与 `.pull` 或 `.push` 位于同一个时序时，无论二者的文本书写顺序，定身总是先于推拉生效；若设计要求先推拉后定身，必须将二者置于不同的大时序。
- 此规则只说明定身相对推拉的优先级，**不能**推广为定身早于所有 Effect：群体扰乱和瞬间扰乱早于定身。
- 定身阻止推拉时存在目标错乱 Bug。对目标 X 的击退被定身阻止，会错误击退 X 在同阵营站位上向后的相邻有效单位 Y；对 X 的拉前被定身阻止，会错误拉前 X 在同阵营站位上向前的相邻有效单位 Y。
- X 可以是施术者自身、友方或敌方目标；错误目标遵循 X 所在阵营和站位，与技能初始目标是友方还是敌方无关。若 Y 已无法继续向对应方向移动，Bug 不可见，表现为没有发生位移。
- 上述定身结论同样只适用于 `.pull` / `.push`，不适用于扰乱。

## 后续机制边界
- size-0 的 `spawn: .effects` 直接引用项在召唤实际发生的时序执行。若 size-0 在 `queue false` 被召出，其 Spawn Effect 就在 `queue false` 执行。被引用 Effect 定义上的 `.queue` 和 `.apply_with_result` 不决定这次 Spawn 调用的时序。召唤后立即执行整段 Spawn 序列，执行完毕才继续父序列中的下一条 Effect，详见 [Spawn 执行链](28-spawn、生命反馈与size0执行链.md)。
- hp_reaction 不能仅靠自身写 AWR 跑到触发它的伤害或治疗之前。
- 死亡、ActorDot、动画与战斗胜利仍有各自的延迟点。
- AWR 与回合外 initiative、spawn 定向或最后一杀组合时风险较高，应按已收录的时序与目标结论逐项检查；仅对未确认组合进行针对性测试或避免使用。
