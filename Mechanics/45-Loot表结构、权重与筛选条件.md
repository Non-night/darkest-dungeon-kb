## 文件和引用

Loot 表通常定义在：

```text
loot\<自定义前缀>.loot.json
```

顶层使用 `loot_tables` 数组，每个表通过 `id` 被其他配置引用。例如 Effect：

```darkest
.gain_random_trinket "T_LOADED_DICE"
```

会引用 ID 为 `T_LOADED_DICE` 的 Loot 表。表 ID 应唯一，引用必须完全一致。

## 基本结构

```json
{
  "loot_tables": [
    {
      "id": "T_LOADED_DICE",
      "difficulty": 0,
      "dungeon": "",
      "entries": [
        { "type": "nothing", "chances": 50, "data": {} },
        { "type": "trinket", "chances": 30, "data": { "rarity": "very_common" } }
      ]
    }
  ]
}
```

## `chances` 是权重

`entries[].chances` 是各候选项之间的抽取权重，不应笼统解释成固定百分比。若所有可用项权重总和刚好为 100，其数值在结果上可表现得像百分比，但机制解释仍应写成权重。例如权重 `50` 与 `30` 的两项，在不考虑其他筛选或引擎特殊处理时，应按 `50:30` 的相对比例参与抽取。

当前尚未确认以下边界：

- 权重允许的完整数值范围；
- 零权重、负权重或所有项总权重为零时的行为；
- 浮点权重的精确舍入方式。

因此应使用非负的常规整数或简单小数，并参考原版实例，不要依赖异常值。

## `type` 与 `data` 联动

- `type` 决定该候选项产出的对象/行为类型；
- `data` 的结构和合法字段随 `type` 改变，不能脱离 `type` 单独列出一套通用参数；
- `nothing` 表示本次抽中后不产出任何物品；Loot 表仍视为已经正常完成了一次抽取，只是抽取结果为空。通过 `.gain_random_trinket` 调用时，抽中该项即为本次不获得饰品。通常搭配空对象 `data: {}`；
- 已见 `trinket` 表示产出饰品，可在 `data.rarity` 中指定饰品稀有度；当该候选项被抽中后，会从所有当前可以正常生成的对应稀有度饰品中产生最终饰品。现阶段倾向认为同一稀有度内的合格饰品是等权随机，但尚未专项验证，必须保留“应该／倾向”的不确定性；
- 受 `limit` 或 `origin_dungeon` 等条件制约、在当前场景下不应正常生成的饰品，是否会在二次选择前被直接排除、是否仍会参与候选权重，以及若参与后被抽中会发生重抽、空结果还是其他行为，目前均未知。不得在关键掉落设计中依赖这些未确认边界。

当前知识库没有完整确认 `type` 的合法值全集，也没有确认每种 `type` 对应的 `data` 字段全集。编写新表时只能优先复制原版相同用途的结构，再做简单、可验证的拓展；不得凭字段名称臆造新类型或跨类型复用 `data`。

## `difficulty` 和 `dungeon` 筛选

这两个字段都是 Loot 表的适用条件：

- `difficulty: 0`：按现有经验表示不限难度；
- `difficulty: 1` 或更高：用于限定难度，但目前不能确认是“仅指定难度”还是“指定难度及以上”。后者的可能性较大，但必须标为未确认；
- `dungeon: ""`：任意区域；
- `dungeon: "<地区id>"`：限定到对应地区 ID。

需要精确限制难度时，应反查原版多个相邻难度实例或实机测试，不得依据数字直觉直接断言比较方式。

## 审查清单

1. 调用方引用的 Loot 表 ID 是否存在且完全一致？
2. `chances` 是否按相对权重理解，而非误写成必须合计 100 的百分比？
3. 每条 `data` 是否来自相同 `type` 的原版/已验证实例？
4. 通用表是否使用 `difficulty: 0` 与 `dungeon: ""`？
5. 限区表的 `dungeon` 是否填写合法地区 ID？
6. 对非零 `difficulty` 是否明确保留“精确筛选规则未确认”的边界？
7. `type: "trinket"` 是否只指向当前可正常生成的对应稀有度池？是否避免断言池内一定等权，并避免擅自假设受 `limit`、`origin_dungeon` 等条件制约的饰品会被排除、重抽或产出空结果？
