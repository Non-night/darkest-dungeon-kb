## 字段归属与位置

`transform_on_quest_complete_chance` 是**饰品条目配置项**，不是 Effect 关键字，也不是 Buff 字段。它写在：

```text
trinkets\<自定义前缀>.entries.trinkets.json
```

中的单个饰品 JSON 对象内，与 `id`、`trigger_limit`、`transform_on_quest_complete`、`transform_on_wearer_killed` 等饰品配置字段同级。

## 参数与含义

```json
"transform_on_quest_complete_chance" : 0.5
```

- 参数类型：浮点数；按 JSON 数值书写，不加引号。
- 含义：任务**完成**时，该饰品执行 `transform_on_quest_complete` 转化的成功率。
- 默认值：`1`。省略该字段时，按成功率 `1` 理解。
- 该字段只规定转化成功率；实际转化目标由同一饰品条目的 `transform_on_quest_complete` 指定。因此，只有同时存在有效的转化目标时，它才有实际的转化对象。

官方实例使用过 `0.5` 和 `0.2`。当前资料没有单独确认异常值或超出常规概率区间的行为，不应依赖未验证的异常数值。

## 触发条件、所在位置与替换行为

这里的“任务完成”特指**任务成功**。撤退、任务失败以及其他未成功完成任务的结算不属于已确认的触发条件。

当前已确认或保留的饰品位置边界如下：

- 饰品装备在参加并成功完成任务的英雄身上时，可以执行转化；
- 饰品留在城镇饰品仓库中时，确定不会因为另一支队伍任务成功而转化；
- 饰品位于副本背包中时是否会转化，尚未确认。

转化后的表现当前理解为：原饰品被 `transform_on_quest_complete` 指向的目标饰品替换，而不是额外复制出一件目标饰品。但“是否严格保留原装备槽或背包位置”等更细节表现尚未逐项测试，因此替换模型应标记为高可信推测，而不是完整引擎保证。

## “进化饰品”的歧义处理

当前用户说“进化饰品”而没有进一步说明时，不得自行选择唯一实现方式。该说法至少可能指：

1. 任务成功完成时，通过 `transform_on_quest_complete` 转化为指定饰品；
2. 饰品的 Trigger 可用次数（如 `trigger_limit`）耗尽时转化为指定饰品；
3. 饰品不替换 ID，而是通过 Buff 为饰品自身增加或改变数值；Fire's Edge DLC 的 `crumbling_timekeeper` 饰品是此类参考；
4. 佩戴者死亡时，通过 `transform_on_wearer_killed` 转化为指定饰品。

原版相关汉化将后一类表现译为“还原”，但这不意味着它与“进化”是不同机制：原版只是把它用于任务完成后已经转化的饰品在佩戴者死亡时回到转化前饰品。实现前必须确认当前用户所说的触发时机、目标饰品以及是替换饰品 ID 还是修改饰品自身数值。

## 进化产物与常规获取渠道

由进化而来的饰品**很有可能**被设计为不能通过常规手段获取，但这不是必然规则；确实存在既可由进化获得、也可通过常规方式获得的饰品。这里的常规手段主要包括：

- 饰品商店；
- 战斗或奇物掉落；
- 特殊扎营技能掉落；
- 任务奖励。

如果当前用户明确要求进化产物不应通过这些常规手段获得，通常不要把该饰品的实际 `rarity` 设置为原版已经存在、且会参与常规生成的稀有度；`visual_rarity` 只负责外观显示，不影响这一获取限制，因此可以独立使用。若为进化产物新设稀有度，则该稀有度的 `award_category` 不得使用：

- `universal`：表示该稀有度下的饰品可通过所有常规生成方式出现，包括商店等常规渠道；
- `quest`：表示该稀有度下的饰品可以作为任务奖励出现。

补充边界：未修改的原版商店实际上不会刷新原版不存在的自定义稀有度饰品，但这不改变 `universal` 的语义；稀有度的获取分类仍应与设计目标一致，不能把商店当前未刷新误当作安全的获取限制。

## 与 `limit` 的疑似关联

通过 `transform_on_quest_complete` 相互关联的饰品，疑似共享 `limit` 计数。该结论尚未完成专项验证：

- 不得把相互转化的两个 ID 简单视为彼此完全独立的数量上限；
- 也不得在关键获取逻辑中直接依赖“必定共享”；
- 若设计要求精确控制相互转化饰品的持有数量，应先进行实际测试。

## 完整结构示例

```json
{
  "id": "example_trinket",
  "trigger_limit": 6,
  "transform_on_quest_complete": "example_trinket_transformed",
  "transform_on_quest_complete_chance": 0.5
}
```

这是字段层级与书写形式示例；自定义饰品仍需补齐其实际所需的其他条目字段，并确保 `example_trinket_transformed` 确实是可被引用的饰品 ID。

## 官方实例

`DarkestDungeon\dlc\735730_color_of_madness\trinkets\com.entries.trinkets.json` 中存在：

```json
"transform_on_quest_complete" : "rw_sunstone_scorching",
"transform_on_wearer_killed" : "rw_sunstone_inert",
"transform_on_quest_complete_chance" : 0.5
```

以及成功率为 `0.2` 的同类条目。Fire's Edge 的本地化还提供了“任务完成时按百分比概率转化”的显示文本，可作为该字段语义的补充证据。

## Agent 生成前检查

1. 是否把该字段写在单个饰品条目对象中，而没有错误写成 `.transform_on_quest_complete_chance` Effect 关键字？
2. 参数是否为不加引号的 JSON 数值？
3. 是否同时提供了有效的 `transform_on_quest_complete` 目标？
4. 省略该字段时，是否按默认值 `1` 理解？
5. 是否只在任务成功时判断转化，没有把撤退或失败算作任务完成？
6. 是否确认饰品装备在参战英雄身上；是否避免假设仓库饰品会转化；副本背包转化是否保留为未知？
7. 是否把转化理解为原饰品被目标饰品替换，同时没有擅自保证所有位置细节？
8. 是否注意相互转化饰品疑似共享 `limit`，并避免把尚未验证的共享行为用于关键数量控制？
9. 是否避免擅自假设尚未确认的异常值行为或数值范围限制？
