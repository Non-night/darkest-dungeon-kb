## 定义目录与文件名

饰品条目定义放在 Mod 的：

```text
trinkets\
```

目录内，文件名格式为：

```text
<自定义前缀>.entries.trinkets.json
```

即完整通配格式为：

```text
trinkets\*.entries.trinkets.json
```

`*` 是该文件的前缀。当前只确认这种文件名结构；前缀允许的完整字符范围及异常字符行为尚未专项确认，创作时应使用简单且不冲突的前缀。

饰品条目通常位于顶层 `entries` 数组中：

```json
{
  "entries": [
    {
      "id": "example_trinket",
      "buffs": [
        "example_trinket_buff_a",
        "example_trinket_buff_b"
      ]
    }
  ]
}
```

上例的自定义前缀用于添加采用唯一 ID 的新饰品。要修改原版，复制定义该饰品的原版整份文件，在 Mod 中保留相同的相对路径和文件名，例如 `trinkets\base.entries.trinkets.json`。同路径整文件取高优先级，不同文件的重复饰品 ID 按低优先级取用，见[文件覆盖专题](13-文件覆盖、逆序覆盖与同ID合并.md#已知逆序覆盖)。

## `buffs`：装备期间附着的 Buff

- `buffs` 是 Buff ID 数组。
- 英雄装备该饰品期间，数组内引用的所有 Buff 都会附着到装备者身上并参与结算。
- 英雄卸下饰品后，由该饰品附带的这些 Buff 随之移除。
- 这些 Buff 的 Buff 源为 `bsrc_trinket`。
- 数组中填写的 Buff ID 必须存在；不得优先借用或修改原版已有 Buff，应为目标 Mod 创建自有定义。

### 非法 Buff 影响饰品的常规获取

当前用户于 2026-11-21 说明，饰品条目的 `buffs` 中任一引用的 Buff 非法时，通过副本任务奖励、饰品马车商店、战斗 Loot 和奇物 Loot 等常规途径均无法取得该饰品。排查时对 `buffs` 每一项检查 ID、实际加载的 Buff 定义及字段合法性。结果与饰品 JSON 能通过语法校验可以同时存在。

当前用户报告的重进存档现象：同一任务已经刷新并显示该饰品为奖励。将饰品某个 Buff 改成非法值，或追加一个非法 Buff，再重进该存档，任务上的饰品奖励消失。观察对象是尚未领取的任务奖励。直接指定 `.gain_trinket`、启动项指定饰品及已持有饰品的行为均未确认。目前也没有逐类验证所有可能的 Buff 错误或引擎筛选阶段。

见[本轮证据记录](../Sources/tutorial_corrections_20261121.json)。

### 数组顺序边界

实际结算顺序**推测**与 `buffs` 数组的书写顺序一致，但目前仍不明确，不能列为已经确认的严格时序保证。因此：

- 可以为了可读性按预期逻辑顺序排列 Buff；
- 不得让关键迂回、条件链、驱散链或瞬时机制依赖饰品 `buffs` 数组的严格结算顺序；
- 若先后次序会改变结果，应改用已有明确时序的 Effect 链，或先进行专项实机测试。

## 静态 Buff 的重新取得与恢复边界

知识库编写者于 2026-10-28 在当前维护会话中明确确认：**重新装备饰品一定会重新获得该饰品提供的全部静态 Buff，无论这些 Buff 此前因何种原因失去。** 这不只适用于 `remove_on_battle_complete`；也不能把 ID 定向驱散或其他移除原因当作永久耗尽饰品静态 Buff 的办法。

- **重新取得不等于保证留下**：重新取得之后，仍须按当前 Rule、ID 定向驱散、持续时间、`remove_if_not_active` 等条件判断是否再次失去。
- **失去后不会仅因进入下一场战斗而自动补回**：第 17 条已确认由 `remove_on_battle_complete` 清除的饰品／套装 Buff 在不重启、不重新装备时不会在后续战斗自动恢复；不要把此范围外所有移除原因的自动补回时点一并宣称为已测。
- **重进存档能否重新提供这些 Buff，保持未知**；不能从重新装备的结论推导读档恢复，也不能根据 Buff 源表的退出清除列倒推读档重建。
- 本条“全部静态 Buff”指饰品条目 `buffs` 所提供的 Buff，不等于饰品 Trigger 经 Effect 临时施加的所有 Buff；后者按自己的来源和生命周期判断。
- 因此不能用“清掉装备静态附魔且不留独立状态”代表“本场已经触发”。每场首次设计还需核对本场记忆、战斗结束重置、重复安装及重装边界；这是一项设计检查，不是任何完整实现已通过实机验证的声明。

证据等级：知识库编写者明确确认。既有清除与重进存档未知边界见 [Buff 持续时间类型与实际清除](17-Buff持续时间类型与实际清除.md#remove_on_battle_complete-的强制清除)。

## 每场首次效果的生命周期审查

本节为基于已收录结论的**设计审查清单／推断**，不是某个完整实现已通过实机测试的声明。适用于饰品、附魔、定向驱散组合的每场首次或一次性需求：

1. **实际释放**：`skill` Rule 在选中技能时已开始判定；不要把条件成立直接当作实际释放事件。见 `Buff/rule_type/skill.md`。
2. **同次去重**：`.apply_once true` 只抑制同次技能／调用流程重复，不提供跨技能、整场战斗的使用次数记忆。见 `Effect/keyword/Effect.apply_once.md`。
3. **本场记忆**：若用独立临时 Buff 记录已触发，分别核对来源、持续类型、再施加、定向清理及残留。不能仅凭清掉装备静态 Buff 就宣称完成每场限次。
4. **下场重置**：战斗结束和撤退时移除什么、下一场如何重新允许触发，都要有明确状态转移；`remove_on_battle_complete` 的对象与自动恢复边界见第 17 条。
5. **恢复边界**：重新装备会重新取得全部饰品静态 Buff，重新取得后仍可能再次失去；重进存档是否恢复维持未知，不可借退出清除表代替读档重建证据。
6. **时序与取消**：ID 定向驱散的持有者范围和链式行为见第 25 条；附魔安装／清理的大时序、发生与生效、队列冻结的推测边界见第 92 条。不能由驱散 Buff 直接推导所有已入队 Effect 都被取消。

本清单不新增触发字段，不要求 size0 或 ActorDot，也不将任何“临时附魔＋本场锁”的组合自动标为已实机验证。

## 饰品定义容量与旧版饰品溢出

**64 位 Build 28385（2026-11-05 更新）实测能加载至少 144,000 个不同 ID 的饰品定义。** 旧版 `2048`／`4096` 的饰品溢出限制在该构建已失效。这里数的是定义条数。背包、仓库、英雄持有件数和单件饰品的 `limit` 分别计算。

2026-11-06 社区实测用单个 `gameKiller144000` Mod 对照资源入口设置。`.max_resource_entries 32768` 时加载黑屏，改为 `2097152` 后能进入游戏。过周后在水晶商店同时见到首条 `gameKiller` 和末条 `gameKiller143999`。核对附件 JSON 共 `144000` 条、ID 全部唯一。首尾为 `comet`、`shard: 200`，中间 143,998 条为 `crow`、`price: 200`。商店实测只验证了首尾可生成。

测试包的饰品贴图目录为空，本地化也未覆盖全部条目。按实测说明，缺失本地化时显示蓝字，缺贴图时稀有度框左上角有白点，悬停白点仍可显示名称与描述。大量定义须给资源条目表留足空间，测试用值及启动内存成本见第 80 章。

**证据边界。** 饰品定义的精确上限、内部整数类型及触顶表现未知，`int` 级仅是推测。多个 Mod 合计 144,000 条，以及 `estate`／`supply`／`heirloom` 与饰品在此规模下的共享计数，均未复测。



## `hero_class_requirements`：可装备职业列表

```json
"hero_class_requirements": [
  "class_a",
  "class_b"
]
```

- 数组元素填写英雄职业 ID。
- 非空数组表示只有列表内职业可以装备该饰品。
- 空数组 `[]` 表示不限制职业，所有英雄均可装备。
- 填写多个职业 ID 时采用“任一满足”关系：英雄职业只要是列表中的任意一个即可装备；不是要求同一英雄同时满足全部职业。
- 这里应填写职业 ID，而不是本地化名称、英雄实例名或英雄 Tag。

## `rarity`：饰品稀有度

```json
"rarity": "collector"
```

`rarity` 为饰品指定稀有度 ID。自定义稀有度通常定义在：

```text
trinkets\*.rarities.trinkets.json
```

其本地化显示名使用类似以下 Entry ID：

```text
trinket_rarity_<稀有度id>
```

稀有度名称会在游戏内实际显示。鼠标悬停在饰品碰撞箱上时，已确认的内容排列顺序为：

1. 饰品名称；
2. 饰品稀有度名称；
3. 饰品的可见 Buff；
4. 饰品 Trigger 的可见 Effect；
5. 饰品套装描述——仅饰品属于套装时出现；
6. 饰品套装的可见 Buff。

稀有度还与以下机制绑定：

- 饰品的获取方式或所属获取池；
- 饰品仓库中的“按稀有度排序”。

不能把 `rarity` 仅理解为颜色或装饰文本。具体获取方式如何由稀有度定义中的其他字段控制，需要继续逐项整理。

### 稀有度 `award_category`：生成方式分类

稀有度定义中的：

```json
"award_category": "battle"
```

决定该稀有度采用的生成方式。当前已知合法值为：

| 合法值 | 当前含义与边界 |
|---|---|
| `dd` | 合法，但被标记为不建议使用；具体生成范围暂未整理，不得用于新设计。 |
| `trophy` | 原版“猎获”稀有度采用的类别。原版各地区 Boss 的最高难度任务奖励会给予猎获饰品；该类别完整的掉落与奖励规则未知。 |
| `battle` | 疑似仅通过战斗掉落；尚未完成所有奖励渠道的排除测试，应保留“疑似”。 |
| `universal` | 可通过所有常规生成方式出现。 |
| `quest` | 仅作为任务奖励出现。 |
| `kickstarter` | 不按普通掉落池获取，而使用饰品仓库的特殊名称输入机制。 |

#### `kickstarter` 的特殊获取方式

当存在 `award_category: "kickstarter"` 的饰品时，玩家可在饰品仓库界面按下回车，唤起特殊输入框；输入目标饰品在当前游戏语言下的**本地化显示名称**，再次按回车后获得该饰品。

因此：

- 输入的是本地化后的饰品名称，不是饰品内部 ID；
- 使用哪一种语言的名称取决于当前游戏语言设置；
- 不应把 `kickstarter` 当作普通战利品、商店或任务奖励类别；
- 同名、缺失本地化、大小写或其他文本匹配细节尚未确认，关键设计不应依赖未经测试的名称冲突行为。
### 稀有度 `insert_before`：仓库排序插入位置

```json
"insert_before": "ancestral"
```

`insert_before` 只影响饰品仓库使用“按稀有度排序”时，该稀有度相对于其他稀有度的排列位置。可将其理解为把当前稀有度插入到参数指定的稀有度之前。

- 它不会影响饰品掉落、生成概率、获取池或 `award_category`；
- 不能根据排序位置推导该稀有度更容易或更难获得；
- 指定不存在的稀有度时如何处理，尚未确认；
- 多个自定义稀有度同时插入同一目标之前时，它们之间的具体先后顺序未知；
- 对饰品仓库以外的其他界面排序是否也有影响，尚未确认。

关键生成逻辑不得依赖 `insert_before`，它是已确认的仓库排序字段，不是掉落控制字段。
### `visual_rarity`：外观稀有度／视觉稀有度覆盖

“外观稀有度”和“视觉稀有度”在本知识库中均指字段 `visual_rarity`。

```json
"rarity": "ancestral_shambler",
"visual_rarity": "NON_rhodes_island"
```

`rarity` 与 `visual_rarity` 必须区分：

- `rarity` 是实际机制稀有度，决定获取池、获取方式、仓库稀有度排序等实际规则；
- `visual_rarity` 只覆盖玩家看到的稀有度名称及相应视觉表现，不改变饰品的实际获取池和排序；
- `visual_rarity` 与实际 `rarity` **不能填写同一个 ID**；需要显示与实际稀有度相同的外观时，应省略视觉覆盖，而不是重复填写同值；
- `visual_rarity` 不能只提供本地化字符串或颜色。它引用的 ID 也必须在 `trinkets\*.rarities.trinkets.json` 中具有一条完整稀有度定义。

**相同 ID 的错误配置特例**：迂回表第69条 P1242/X1458 记录，若 `rarity` 与 `visual_rarity` 填成同一个 ID，饰品可能出现类似“空稀有度”的生成错乱，进入原本不该出现的掉落场合，甚至进入未编入该稀有度的商店。正常情况下“`visual_rarity` 只改变显示、不改变获取池”的规则，不能用来为这一错误配置背书。当前用户于2026-11-03确认按历史表现补入；不写成每次必现或所有版本已复测，也不补造底层原因。

### 饰品图标与稀有度背景框

已核对的资源目录为：

```text
panels\icons_equip\trinket\
```

注意实际目录名是复数 `icons_equip`，末级目录是单数 `trinket`，不是 `icon_equips/trinkets`。

常见命名关系为：

```text
inv_trinket+<饰品ID>.png
rarity_<稀有度ID>.png
```

- `inv_trinket+<饰品ID>.png` 是饰品自身图像；
- `rarity_<稀有度ID>.png` 是该稀有度使用的饰品背景框；
- 未写 `visual_rarity` 时，背景框和显示稀有度使用实际 `rarity`；
- 写有 `visual_rarity` 时，显示名称和背景框按视觉稀有度处理，而实际生成与排序仍按 `rarity` 处理。

因此，自定义视觉稀有度通常至少需要完整稀有度定义、对应本地化／颜色，以及 `rarity_<visual_rarity>.png` 背景框资源。缺失其中某项的具体报错或回退表现仍需另行测试。
### 缺失稀有度定义

饰品引用不存在或已经被删除的稀有度时，准确行为尚未实测确认。当前推测：

- 新饰品可能无法正常出现在游戏内；
- 已经存在的饰品若失去对应稀有度定义，进入游戏时大概率会产生红字报错，并且该饰品消失。

以上只能作为高风险警告，不能写成已确认的固定结果。制作 Mod 时必须保证饰品引用的稀有度 ID 存在，并提供相应本地化。

## `price`：商店购买基础价格

```json
"price": 15000
```

- `price` 是该饰品在商店中供玩家购买时的**初始价格／基础价格**，以金币数值填写。
- 最终购买价仍可能受到商店、城镇升级、折扣或其他相关机制影响；本字段不能概括为所有场合固定不变的成交价。
- 玩家出售饰品时，基础卖出价按 `price` 的 **0.15 倍**计算。
- 卖出价的取整方式尚未确认，不得擅自断言向上取整、向下取整或四舍五入。
- `price: 0` 时，该饰品无法由玩家卖出。
- 对于**非水晶饰品**：若当前用户要求实现一个原版稀有度的饰品，但没有明确指定饰品价值，应将 `price` 写成该原版稀有度对应的原版数值；不能凭稀有度名称自行估算。若稀有度或对应原版价格尚未确认，应保留未知并先查找原版实例。
- 对于 `rarity: "comet"` 的水晶饰品：在当前用户没有明确提出特殊设计时，不得写 `price`，应写 `shard`。水晶饰品使用 `price` 时无法正常出现在水晶饰品商店中。
- 原版存在 `price: 1` 的饰品，这些饰品卖出时可以获得 `1` 金币。因此不能简单使用普通除法后向下取整来推导所有卖价；正数卖价可能存在最低值保护或其他特殊处理，但具体算法未知。
- 负数和省略字段的行为尚未确认，创作时不应使用负数，且应显式填写正常的非负整数价格。

## `shard`：水晶饰品商店购买价格

```json
"shard": 40
```

- `shard` 表示该饰品在**水晶饰品商店**中的基础水晶购买价格。
- 使用 `shard` 定价的饰品，其 `rarity` 必须填写原版已经存在的水晶饰品稀有度；不能仅创建任意自定义稀有度后期待它进入水晶商店。
- `shard` 与 `price` **不能在同一个饰品条目中同时出现**。二者并存时，该饰品大概率无法正常刷新；因此 Agent 必须根据其预期商店选择且只保留其中一个价格字段。
- 对 `rarity: "comet"` 的水晶饰品，当前用户未明确要求其他定价方式时，应使用 `shard` 而不是 `price`。
- 如果设计希望该水晶饰品出现在水晶饰品商店中，`shard` 必须填写正数；在没有特殊说明时，水晶饰品通常应按这种可进店的设计处理。`shard: 0` 或负数不是“普遍非法”的价格写法，而是会阻止该饰品正常出现在水晶饰品商店中。
- 由进化获得、且设计上不希望通过常规方式获得的水晶饰品，可以将 `shard` 写为 `0` 以阻止其进入水晶饰品商店；Fire's Edge DLC 中 Runaway 的水晶饰品及其后续进化饰品是该模式的原版参考。
- 使用 `price` 定价的水晶饰品也不能正常在水晶饰品商店出现。
- `shard: 0` 在 **2026 年 8 月 19 日更新以前**曾经可以正常刷新；其失效发生在 2026 年 8 月 19 日更新或紧随其后的下一次更新，确切版本分界尚未确认。不得依据旧版行为设计当前 Mod。
- 负数 `shard` 推测在各已知版本中都不能使饰品正常刷新；由于尚未逐版本完整验证，应保留“推测”边界，但创作时一律禁止使用。
- `shard` 是否影响饰品卖出、任务奖励或其他非水晶商店获取方式，目前没有单独确认，不得从价格字段名称继续外推。
## `limit`：同 ID 饰品的常规生成上限

```json
"limit": 1
```

`limit` 控制同一饰品 ID 通过游戏内常规渠道生成时采用的持有数量上限：

- `limit: 0`：不设置持有数量上限，该饰品可以常规重复生成；
- `limit: N` 且 `N` 为正整数：同 ID 饰品的常规持有上限为 `N`；
- 负数行为未知，创作时不得使用或依赖。

当正整数上限已经达到后，该饰品不会再从以下渠道生成：

- 战利品；
- 商店；
- 任务奖励。

该字段不是绝对禁止游戏状态中出现超额副本。以下局外或特殊方式可以突破上限：

- `-alltrinkets` 启动项；
- 外置修改器等局外修改手段。

通过 Effect 直接给予饰品时能否突破 `limit` 尚未测试；当前倾向于认为不能突破，但必须标记为推测，不得据此构造关键获取逻辑。

`limit` 的当前持有数量会合并统计以下位置中的同 ID 饰品：

- 饰品仓库；
- 英雄身上已经装备的饰品；
- 副本背包。

例如 `limit: 1` 的饰品已经装备在某个英雄身上时，商店、战利品和任务奖励不会再常规生成第二个。任务中暂存但尚未进入背包或仓库的其他特殊状态是否另有边界，目前没有单独测试。

> **个案备注（其他测试者未遇到）**。文和曾报告开新档时饰品爆率偏高，其他人测试同一 Mod 时未遇到相同情况。初次结果可能只是随机波动，原因仍不明。
>
> 据知识库编写者于 2026-11-26 转述，文和给火之边缘（Fire’s Edge）以外的所有原版饰品加了 `limit`。白色和绿色限 4，蓝色限 2，橙色及英雄专属限 1。他还将同范围内各职业的白色、绿色专属饰品改成通用饰品，并报告未修改任何含饰品的 Loot 表。

## `quest_uses`：饰品可用任务次数

`quest_uses` 是单件饰品的可用任务次数，与同 ID 持有数量上限 `limit`、饰品扳机次数 `trigger_limit`、任务成功时的 `transform_on_quest_complete` 分开。官方 Fire's Edge DLC 的饰品定义中有 `"quest_uses": 5` 的实例（`dlc/4964110_fires_edge/features/fires_edge/trinkets/rd.entries.trinkets.json:18`）。

- **副本中途获得后一直放在背包里**：知识库编写者报告，本次出本不会扣除该饰品的可用任务次数。不能仅凭饰品进入了副本背包就把本次任务算作已使用。
- **副本中途尝试装备**：会弹出确认框，提示若装备该饰品，任务结束时将扣除 1 次可用任务次数，是否仍要装备。截图验证的是弹窗与提示；提示说的是任务结束时扣次，不是装备当场扣次。
- **装备后在出本前卸下、装备后撤退**：知识库编写者预计这两种情况仍会扣 1 次，均待实测；不要把「出本时在背包里」等同于「全程未装备」。
- **团灭后饰品被尖叫魔捡走**：是否扣次未知，不能按主动撤退的判断外推。

证据：知识库编写者提供的装备确认截图 `codex-clipboard-00540666-6870-40ed-89cd-f4e3d2081e51.png`（SHA-256：`d94ef50a1dab6c8137830fa096feda4aba8c4568b5d9193df08e0bb421248045`）；官方本地化 `dlc/4964110_fires_edge/localization/rd.string_table.xml` 的 `trinket_quest_uses_equip_confirm_dialog_question`。

## `origin_dungeon`：来源地区限制

```json
"origin_dungeon": "courtyard"
```

- `origin_dungeon` 填写地区 ID，用于指定该饰品的明确来源地区。
- 对猩红庭院稀有度（通常称为 CC 饰品）的饰品，在当前用户没有专门设计其他获取范围时，通常写：

```json
"origin_dungeon": "courtyard"
```

  这样可以使其保持猩红庭院来源，避免在其他地区的常规生成流程中刷新。该默认做法不是不可改变的硬规则；如果当前用户明确要求 CC 饰品也能在其他地区获取，应按设计省略或改写该字段。
- 当该字段填写有效地区 ID 时，饰品只能在对应地区通过地区内的常规生成渠道出现，包括但不限于：
  - 战斗战利品；
  - 奇物互动奖励；
  - 任务奖励。
- `origin_dungeon: ""` 表示不限定明确来源地区，可进入不受该地区条件限制的常规生成流程。
- 该字段是生成来源筛选，不应仅解释成风味文本。
- `origin_dungeon` 不会影响饰品的界面显示，也不会影响饰品仓库排序。
- 通过 Effect、启动项、外置修改等非上述常规渠道能否无视地区限制，应按各自机制另行判断，不能仅从 `origin_dungeon` 推导。

## `set_id` 与饰品套装定义

饰品套装名称的 XML 本地化 Entry ID 为：

```text
str_inventory_set_title_<套装ID>
```

例如套装 ID 为 `example_set` 时，应使用：

```text
str_inventory_set_title_example_set
```

这里的 `set_title` 与套装 ID 之间使用下划线；该格式不要与饰品名称 Entry ID 的写法混淆。

饰品条目可使用：

```json
"set_id": "example_set"
```

将该饰品关联到同 ID 的套装。套装定义文件位于：

```text
trinkets\*.sets.trinkets.json
```

文件基本结构为：

```json
{
  "sets": [
    {
      "id": "example_set",
      "buffs": [
        "example_set_buff"
      ]
    }
  ]
}
```

### 关联数量

- 每个饰品至多只能通过一个 `set_id` 属于一个套装。
- 一个套装可以关联任意数量的饰品，不限于原版常见的两件套。
- 套装定义可以只有一件关联饰品，甚至暂时没有任何饰品引用。
- “可以定义”不等于“一定能激活”：套装 Buff 的激活门槛仍为同一英雄实际装备至少两件属于该套装的饰品。

### 套装 Buff 激活

- 当同一个英雄装备任意两件或更多件具有相同 `set_id` 的饰品时，套装定义的 `buffs` 被激活。
- 不要求装备该套装的全部饰品；若套装共有三件，装备其中任意两件即可激活。
- 原版每个英雄通常只能装备两件饰品，因此常规环境下最多只会以两件触发；饰品装备槽数量可以被全局规则修改。
- 当已装备的同套装饰品降到两件以下时，套装 Buff 不再激活。
- 单件套装即使只有这一件可用饰品，也不能仅凭一件达到“两件及以上”的激活门槛。

### 套装 Buff 的显示颜色

饰品悬停说明中，套装 Buff 在未激活时通常显示为灰色，激活后显示为绿色。该套装状态赋色的优先级低于 Buff 本地化文本自身的颜色标记：

- 若 Buff 文本没有更高优先级的局部颜色，未激活为灰色、激活为绿色；
- 若某段文本自身带有颜色，例如流血相关文字被本地化为红色，则该段文字可始终保持红色，不会被套装状态的灰色或绿色覆盖。

## Agent 审查要求

1. 饰品定义文件是否位于 `trinkets` 目录，且文件名符合 `*.entries.trinkets.json`？
2. `buffs` 数组中的每个 Buff ID 是否均有目标 Mod 自有定义？
3. 是否把这些 Buff 的来源按 `bsrc_trinket` 理解？
4. `hero_class_requirements` 是否填写职业 ID；空数组是否按无限制理解；多项是否按任一满足理解？
5. `rarity` 引用的稀有度 ID 及 `trinket_rarity_<id>` 本地化是否存在？其 `award_category` 是否只使用已知合法值，并按 `dd` 不建议、`trophy` 边界未知、`battle` 疑似仅战斗、`universal` 全常规方式、`quest` 仅任务奖励、`kickstarter` 仓库名称输入理解？`insert_before` 是否只用于饰品仓库按稀有度排序，并避免误认为它影响掉落？是否对不存在目标和多个稀有度插入同一位置的顺序保留未知？是否错误地把稀有度仅当作颜色字段？若使用 `visual_rarity`，它是否与实际 `rarity` 不同，并具有完整的稀有度定义、本地化／颜色和 `panels\icons_equip\trinket\rarity_<id>.png` 背景框？是否避免用视觉稀有度改变实际获取池或排序？饰品自身图像是否按 `inv_trinket+<饰品ID>.png` 命名？
6. `price` 是否按商店购买基础价格理解；卖出基础价是否按 `price × 0.15` 计算，同时对取整方式保留未知？若希望允许玩家出售，是否避免填写 `0`？
7. 若使用 `shard`，是否将其作为水晶饰品商店的正数基础水晶价格；`rarity` 是否为原版已有的水晶稀有度；是否确保 `shard` 与 `price` 不会同时存在；是否避免使用当前版本不能刷新的 `0` 或负数？`limit` 是否正确区分 `0`（无限制）与正整数（对应持有上限）；是否避免使用行为未知的负数？计数是否同时包括仓库、英雄已装备饰品和副本背包？达到正整数上限后是否停止从战利品、商店和任务奖励生成？是否避免把它误写成任何外部手段都不能突破的绝对上限？
8. `origin_dungeon` 是否填写合法地区 ID；有明确来源地区时，是否只允许其从该地区的战利品、奇物互动奖励和任务奖励等常规渠道生成？是否避免误认为它影响显示或排序？
9. 饰品的 `set_id` 是否能在 `*.sets.trinkets.json` 的 `sets[].id` 中找到对应套装？是否按同一英雄装备任意两件及以上同套装饰品激活套装 Buff？
10. 是否错误地让关键机制依赖尚未确认的数组严格结算顺序？
11. 是否对尚未整理的饰品字段保留未知边界，而没有按字段名补造规则？
