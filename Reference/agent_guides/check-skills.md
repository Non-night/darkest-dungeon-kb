只在当前任务涉及本组时展开。若本页历史维护建议与现行专题或当前用户明确约束冲突，先核对适用范围；不要机械执行所有检查。

- 字段名和参数形式是否有原版实例、可靠文档或明确标记的 Mod 回退证据？

- 设计稿中的“技能伤害修正”是否仍按技能自身参数实现，而没有被错误替换成固定值或百分比伤害 Buff？

- 技能 Art 的 `.icon` 是否只填写图标中缀，并与 `<职业id>.ability.<图标中缀>.png` 严格对应？

- 技能 `.anim` 是否考虑第 56 帧截断边界？是否把该限制仅应用于 `.anim` 技能动画本体，而没有错误套用于其引用的 FX？

- 用户孤立提到技能、武器或护甲的 `1` 至 `4` 级时，是否先确认其指代码等级还是玩家口语等级？明确的 `1～5`、`0～4`、`.level N`、`0` 级或标准五级体系中的 `5` 级是否按已明确的编号体系处理，而没有重复追问？

- 生成多个等级、多类 Effect 时，是否优先按效果类别聚合并在同类内部按等级排列，而非按等级打包所有效果？若若干 Effect 共同组成迂回或严格逻辑链，是否把整套逻辑连续保留？是否区分定义排序与会影响触发时序的引用排序？

- 生成的同类多行代码是否在不改变字段顺序、参数内容和语义的前提下适当对齐，便于比较各等级差异？是否避免为了对齐伪造字段、插入参数内部空格或制造过长代码行？

- 使用 `.is_stall_invalidating` 时，是否确认调用方位于英雄侧？是否把省略值按默认 `true` 处理，并把 `false` 理解为不能拖延增援？若技能未写有效 `.target` 或 `.target` 带 `@` 而属于友方技能，是否识别到无论该字段怎样填写都无法阻止增援？

- 仅当相关结论明确标记为未确认、未知、推测或证据冲突时，才可建议最小范围的针对性测试；若风险较高，应优先建议避免使用该未确认行为。

4a-skill. 所有翻页技能及无限使用且不结束回合的英雄技能都应写 `combat_skill:` 的 `.ai_valid false`，排除Act-Out与心控调用；`.counts_towards_skill_limit false`、`.skill_visible false`、`.force_selection true`按设计分别控制装备计数、面板可见与不可取消装备。

4c. 处理同 ID 技能分行时，若所有等级的 `valid_modes` 完全相同，应在最后用无等级共用分行写一次；只有模式集合随等级变化时，才按等级分别写。不要为了逐级对齐而重复复制相同的 `valid_modes`。
