只在当前任务涉及本组时展开。若本页历史维护建议与现行专题或当前用户明确约束冲突，先核对适用范围；不要机械执行所有检查。

- 若英雄被设计为仅能通过事件获得，`generation:.town_event_dependency` 是否明确指向不存在或永不发生的事件 ID？是否错误引用了负责赠送英雄的事件或任何会实际发生的既有事件，从而在事件发生后解锁马车自然刷新？

- 实现可使用道具时，是否创建了与道具 ID 同名的 Effect，并在其中写了 `.item 1`？

- 非零 `.stun` 在常规情况下是否明确写了 `.queue true`？若刻意使用 AWR/`queue false` 眩晕，是否保留设计时序并接受红字？有效 DOT、`.push` 或 `.pull` 是否明确写了 `.can_apply_on_death true`？

- 是否按 `Buff/buff_schema.md` 区分规范必写项、条件必写项和可选项，并完整填写 `stat_sub_type`、`is_clear_debuff_valid`、`has_description` 等标准骨架字段？有明显玩家可读意义的常规 Buff 是否默认使用 `has_description: true`，仅将纯寄存器／逻辑门／自清理等辅助 Buff 或用户明确要求的 Buff 写为 `false`？

- 迂回表及其他测试记录中的测试过程用于保留条件和保证结论可复现，不表示学习者需要重新执行这些测试。

- 对已收录的明确结论，直接用于代码生成和行为推理，不得要求用户重复测试。

1. **代码**：只给最小可运行片段。

2. **逐字段解释**：引用精确词条。

3. **行为预期**：明确哪些来自原版实例、社区实测、Mod 回退或推断。

- 阅读、解释、比较、审计任务默认只读。

- 用户明确要求补充、维护、修复或扩展本知识库时，先说明拟修改的知识库文件范围并请求一次确认；若用户已明确授权修改知识库本身且写明允许范围（例如生成源、路由、锚点和索引），则视为已确认，不再重复询问。该授权不包含任何 Mod 或游戏文件，除非用户另行明确授权。

- 完整边界见：[Agent 写 Mod 的文件权限与注释规范](../../Mechanics/34-Agent写Mod权限边界与darkest注释规范.md)。

- 使用 `//`，且注释必须独立成行；禁止把注释追加到代码行末尾。

- 正常情况下保留必要注释。若从某条独立注释下方开始的所有内容都被游戏视为未写，应删除、重写或移动该注释进行排查。

- `.darkest` 示例不得使用 `...` 作为省略号。

- 完整说明见：[Mod 识别与职业 Mod 目录结构](../../Mechanics/24-Mod识别与职业Mod目录结构.md)。

4f. 自定义文本默认优先 `description_tooltip_id`；它支持 `%d` 等占位符读取 Buff 的 `amount` 并堆叠显示，不能仅因需要动态合计值就强制改用打折或进化方案；具体数值格式与合并条件仍须核验。
