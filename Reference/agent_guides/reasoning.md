## 三种不同的结论

已有确认是来源在记录条件下给出的事实。从确认前提推得的结论可以用于设计论证，但应列前提与计算，不能改称“已有实测”。依赖新引擎行为的推测应说明缺的那一步，并提出能区分候选解释的最小测试；不因暂缺测试就否定整个设计。

证据等级解决“这句话由什么支持”，适用条件解决“可推广到哪”。原版实例能证明字段存在，却未必比后续社区实测更能解释某个运行顺序。不要只按来源名机械排序；先确认双方是否在回答同一个问题。

## 做关联时检查什么

| 维度 | 常见可联想内容 | 防止误套的检查 |
|---|---|---|
| 目标 | `.target`、交换施受、站位、群体、定向 | 最终是谁向谁施术？条件检查在交换前还是后？是否重复作用？ |
| 概率 | 基础概率、施加率、抗性、补集、`effect_chance` | 哪两个环节共享骰子？是否跨技能/召唤单位？截断前后是否等价？ |
| 时序 | AWR、queue、附魔、Trigger、spawn、生命反馈 | 前置状态在消费它的阶段是否已存在？同阶段新追加能否参与？ |
| 状态 | Buff 来源、Rule、生效/存在、驱散、持续时间 | Rule 生效不等于重新施加；清理是否先于消费；是否跨回合/战斗？ |
| 环境 | build、DLC、全局规则、BR、样本版本 | 是语法通用，还是环境限定的行为？后续更正撤回了哪一部分？ |

可以沿 `requires` 查必需前提，沿 `related` 或正文交叉链接找替代方法，沿 `supersedes` 找修正。`conflicts_with` 中的文字可能是被否定说法，不是另一条成立的事实。边只是检索线索，不自行证明两个机制可组合。

## 两个推理例子

概率补集：若某个抑制环节成功率为 `100%-r`，且失败时允许另一个必成的最终 Effect 执行，可以推得最终等效成功率 `r`。真正需要核对的是 `r` 指谁的抗性、谁的施加率、在哪个概率域内、是否需要分段，以及实际输出是否仍受其他判定影响；不能因数学成立就跳过这些前提。完整读取方案见专题03、51。

附魔队列：AWR 自附魔在 Rule 生效时能引出本次后续 queue；同阶段自附魔不能回头引出本次同阶段。不能把用于解释同阶段限制的“队列冻结”扩大成“整个附魔机制可能不可用”。见专题92。机制关系是推理的前提，不是对所有来源统一套用的时序表。

## 遇到冲突或未命中

先查看修正状态、版本、对象、调用方、条件与时序，再决定是真冲突还是不同边界。原词、别名、字段和相关机制都查过后仍缺证据，才报告“当前未找到”。已记录的测试不要求当前用户重复证明；若要扩大适用范围，明确新增测试只验证哪一条边界。
