只在当前任务涉及本组时展开。若本页历史维护建议与现行专题或当前用户明确约束冲突，先核对适用范围；不要机械执行所有检查。

- 处理 `Tags` 时，是否保留外层 `<Tags>` 与内层 `<Tags>` 的嵌套格式？是否区分 Workshop 的分组标题、实际标签和标签后的动态项目数量，并避免把括号数字写入配置？

- 处理 `VersionMajor` 与 `VersionMinor` 时，是否将二者组合为游戏内显示版本号，并避免在用户未要求时擅自改版？遇到 `TargetBuild` 时是否按官方说明解释为目标游戏构建版本，并保留解析／兼容性检查边界未知？

- 读取或生成 `UploadMode` 时，是否明确 `direct_upload` 会直接上传到 Steam，而 `dont_submit` 只编译、不上传？是否在两种模式编译前确认每份 XML 都包含 `<language id="english">...</language>`（内容可以为空），并在编译后同时检查控制台诊断和预期的 `loc2` 产物？是否检查编译生成的 `modfiles.txt` 和 `steam_workshop_uploader.log`？

- 修改 Mod 后是否删除了旧 `modfiles.txt`？若使用 `Cursors\arrow.png`、`Fx\torch_load` 或 `Dungeons\_shared\shared.json` 等已知特例，是否在全部修改完成后重新生成了匹配当前内容的新验证文件，而不是让这些资源在无验证文件时失效？是否区分 mods、DLC 与游戏根目录直接覆盖三种加载方式？

- 读取或生成 `Visibility` 时，是否明确 `public` 表示上传后自动公开、`private` 表示上传后仅自己可见？是否避免编造其他参数，或断言更新时会如何处理已有可见性？

- 读取或生成 `UpdateDetails` 时，是否允许无需求时留空，并将“本次更新说明”保留为依据官方范本得到的推测？是否避免为本地运行强行填写，或擅自生成更新日志？

- 读取或生成 `Language` 时，是否将其理解为 Mod 所属语言，并优先采用游戏 `localization` 目录中已有的语言内部名称？是否避免把该字段的实际作用范围、省略行为或错误参数结果说成已确认？

- 读取或生成 `ModDataPath` 时，是否确认它指向包含 `project.xml` 的 Mod 根目录？是否正确区分“路径不匹配导致上传器无法识别”和“游戏仍可加载本地 Mod”？是否把反斜杠疑似不可用、末尾斜杠疑似可省略保留为未确认结论？

- 遇到 `ItemDescription` 时，是否按上传器官方帮助解释为可选的 Steam 描述并保守控制为少于 8000 字符？无用户专门要求时是否保持为空，并保留 Steam 更新覆盖行为、字符计数或格式支持等未知边界？

- 遇到 `PublishedFileId` 时，是否把它识别为 Steam Workshop 项目 ID，并避免在首次上传前手动写 `0` 或伪造 ID？是否同步检查编译后的 `loc2` 文件没有 `0_` 前缀、无前缀通用名称或同名覆盖风险？

- 遇到 `ItemDescriptionShort` 时，是否识别其可能与 Mod 简介有关但具体用途未确认？无用户专门要求时是否保持为空，并避免擅自生成介绍文字或断言其必写性、显示位置和格式限制？

- 读取或生成 `project.xml` 时，是否识别 `PreviewIconFile` 为合法的 Mod 封面指向字段？是否在无明确需求时保留其指向根目录 `preview_icon.png`，并避免把必写性、省略行为、相对路径支持或具体影响范围说成已确认？

- 创建、重命名或排查无法识别的 Mod 时，根文件夹名是否包含 `error` 的任意大小写组合？是否已经避免依赖尚未完全确认的大小写差异？

- 每个新建、修改或引用的文件是否已经核对功能目录、文件名格式、前缀差分规则、内部 ID 对应关系及配套资源位置？是否避免把“字段语法合法”误判成“任意路径和任意文件名都能被加载”？

- 所有新建或改写的 `*.json`、`*.darkest` 文件是否确认为 UTF-8 无 BOM？是否检查文件开头不存在 `EF BB BF`，且写入工具没有使用 `utf-8-sig` 或含 BOM 的 UTF-8 模式？

- 新建或改写任何 `*.json`、`*.darkest` 配置时，最终文件必须保存为 UTF-8 无 BOM；若原文件带 BOM，改写时必须移除。不得使用 `utf-8-sig` 写入。详见：[JSON 与 Darkest 文件的 UTF-8 无 BOM 硬性要求](../../Mechanics/42-JSON与Darkest文件的UTF-8无BOM硬性要求.md)。

- 对每一个准备读取、创建、修改或引用的文件，必须同时检查其功能目录、文件名格式、前缀差分规则、内部 ID 对应关系和配套资源位置；文件内部字段合法并不能证明该文件会被引擎扫描。

- 不得只知道 `*.info.darkest`、`*.json` 等扩展名便随意选择目录或文件名。知识库已有对应文件专题时必须读取；知识库尚缺路径或命名结论时，先参考原版／官方 DLC 的同类结构，仍不能确认且会影响实现时必须向用户说明或询问。
